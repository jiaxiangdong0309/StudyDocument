# JVM 面试篇（Android 视角）

> 面试官问 JVM，本质是想看你能不能把复杂的东西讲清楚，以及有没有实战经验。作为 Android 开发者，回答时要关联 ART 和实际开发场景。

## 一、基础概念类

### Q1：说说 JVM 的内存结构？在 Android 中有什么对应？

**答**（先说结论）：JVM 内存分为 5 个区域，Android ART 虽然实现不同，但概念相通。

| JVM 区域 | 存什么 | 线程共享？ | Android Profiler 对应 |
|---------|--------|----------|---------------------|
| **堆** | 对象、数组 | 共享 | Java Heap |
| **方法区** | 类信息、静态变量 | 共享 | Code（部分） |
| **虚拟机栈** | 局部变量、方法调用 | 私有 | Stack |
| **本地方法栈** | native 方法 | 私有 | Native |
| **程序计数器** | 当前执行行号 | 私有 | - |

**Android 关联**：在 Android Profiler 中，"Java" 对应堆，"Native" 包含 Bitmap 像素数据和 JNI 分配的内存。ART 的内存结构更复杂，包含 Image Space（预加载的类）、Zygote Space（fork 共享的内存）、Allocation Space（运行时分配）等。

### Q2：堆和栈有什么区别？

**答**：

| 对比项 | 堆（Heap） | 栈（Stack） |
|-------|-----------|------------|
| **存储内容** | 对象实体 | 局部变量、方法调用 |
| **线程** | 所有线程共享 | 每个线程私有 |
| **生命周期** | GC 回收时才释放 | 方法结束自动释放 |
| **速度** | 相对慢（需要 GC） | 快（指针移动即可） |
| **错误** | OutOfMemoryError | StackOverflowError |

**Kotlin 代码示例**：

```kotlin
class UserRepository {
    fun getUser(id: String): User {
        // id 是基本类型（实际是 String 引用），在栈中
        // cached 是引用，在栈中
        val cached = cache[id]  
        
        // User 对象在堆中，user 引用在栈中
        val user = User(id, "张三")
        return user
    }
    // 方法结束，id、cached、user 这些栈中的变量自动释放
    // 但 User 对象还在堆中，等待 GC 回收
}
```

**Android 实战关联**：这就是为什么局部变量不会导致内存泄漏，而成员变量可能会——成员变量跟着对象在堆中，对象不释放它就不释放。

### Q3：静态变量、成员变量、局部变量有什么区别？

**答**：

| 对比项 | 静态变量 | 成员变量 | 局部变量 |
|-------|---------|---------|---------|
| **定义位置** | 类中，companion object | 类中，方法外 | 方法/代码块内 |
| **存储位置** | 方法区 | 堆（跟对象走） | 栈 |
| **生命周期** | 类加载到卸载（≈进程） | 对象创建到销毁 | 方法开始到结束 |
| **默认值** | 有（null/0/false） | 有 | 无，必须初始化 |

**Android 内存泄漏的高发区**：

```kotlin
class MainActivity : AppCompatActivity() {
    
    // ⚠️ 静态变量：生命周期 = 进程，最容易泄漏！
    companion object {
        // ❌ 绝对不要这样！Activity 会泄漏
        var leakedActivity: MainActivity? = null
        
        // ✅ 如果必须用静态，存 ApplicationContext
        lateinit var appContext: Context
    }
    
    // ✅ 成员变量：生命周期 = Activity，跟 Activity 一起销毁
    private lateinit var binding: ActivityMainBinding
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        
        // ✅ 局部变量：onCreate 结束就销毁，最安全
        val tempData = intent.getStringExtra("data")
    }
}
```

### Q4：对象创建的过程是怎样的？

**答**：`User("张三")` 执行时经历以下步骤：

1. **类加载检查**：User 类加载了吗？没有先加载
2. **内存分配**：在堆的年轻代分配空间
3. **初始化零值**：所有字段设为零值（null/0/false）
4. **设置对象头**：Mark Word（哈希码、GC 年龄）+ 类型指针
5. **执行构造函数**：执行 init 块和构造参数赋值
6. **返回引用**：将堆地址赋给栈中的变量

**Android 性能关联**：这就是为什么在 `onDraw`、`onBindViewHolder` 等高频方法中要避免创建对象——每次 new 都要经历这些步骤，频繁创建会导致频繁 GC。

```kotlin
// ❌ onDraw 每秒调用 60 次，每次都 new = 每秒创建 60 个对象
override fun onDraw(canvas: Canvas) {
    val paint = Paint()  // 触发对象创建的完整流程
    val rect = RectF()
    // ...
}

// ✅ 提前创建，复用
private val paint = Paint()
private val rect = RectF()

override fun onDraw(canvas: Canvas) {
    // 只是使用已有对象，不触发对象创建
    rect.set(0f, 0f, width.toFloat(), height.toFloat())
    canvas.drawRect(rect, paint)
}
```

### Q5：JVM 和 ART 有什么区别？

**答**：这是 Android 开发者必须知道的区别。

| 对比项 | JVM (HotSpot) | ART |
|-------|---------------|-----|
| **字节码** | .class | .dex（更紧凑，适合移动端） |
| **编译方式** | JIT（运行时编译） | AOT（安装时编译）+ JIT |
| **启动速度** | 慢（需要预热） | 快（AOT 预编译） |
| **运行性能** | JIT 预热后很快 | AOT 代码直接执行，但缺少运行时优化 |
| **存储占用** | 小（只存字节码） | 大（存 oat 文件，空间换时间） |
| **GC** | 分代收集，STW | 并发收集，STW 极短（2-3ms） |

**通俗理解**：
- JVM 像边看菜谱边做饭，熟练后速度很快
- ART 像提前把菜谱背熟，做饭时不用翻，但学习时间长（安装时编译）

**Android 8.0+ 的混合编译**：

```
安装时：只做简单优化（快速安装）
     ↓
首次运行：解释执行 + 收集热点
     ↓
后台编译：把热点代码 AOT 编译
     ↓
再次运行：热点走 AOT，其他走解释
```

## 二、垃圾回收类

### Q6：什么是垃圾？怎么判断？

**答**：**垃圾 = 没有任何引用链可达的对象**。

JVM/ART 使用**可达性分析**：从 GC Roots 出发，遍历引用链，不可达的就是垃圾。

**GC Roots 包括**：
- 栈中的局部变量引用
- 静态变量引用
- JNI 引用
- 同步锁持有的对象

**Android 内存泄漏的本质**：

```kotlin
// 对象不再需要，但仍然可达（有引用指向它），就是泄漏
class LeakyActivity : AppCompatActivity() {
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        
        // ❌ 单例持有 Activity 引用
        // EventBus 内部的 Map<Class, List<Subscriber>> 就是 GC Root
        // Activity 被注册为订阅者，就会被单例持有
        EventBus.getDefault().register(this)
    }
    
    // 如果忘记在 onDestroy 中 unregister
    // Activity 销毁后，EventBus 单例仍持有它的引用
    // GC 从单例这个 GC Root 出发，能到达 Activity，所以不回收
    // = 内存泄漏
}
```

### Q7：说说 GC 算法？Android 用哪种？

**答**：

| 算法 | 原理 | 优点 | 缺点 |
|-----|------|------|------|
| **标记-清除** | 标记垃圾 → 清除 | 简单 | 内存碎片 |
| **复制算法** | 存活对象复制到另一半 → 清空原区域 | 无碎片，快 | 浪费一半空间 |
| **标记-整理** | 标记 → 存活对象向一端移动 | 无碎片 | 移动成本高 |
| **分代收集** | 年轻代用复制，老年代用标记-整理 | 综合最优 | 实现复杂 |

**Android ART 的 GC 策略**：

```
┌─────────────────────────────────────────────────────────────────┐
│                      ART GC 策略演进                             │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Dalvik（老版本）：                                               │
│  └─ Stop-The-World，全部线程暂停，GC 耗时 50-100ms               │
│                                                                 │
│  ART 初期（Android 5.0）：                                       │
│  └─ 并发标记，STW 降低到 5-10ms                                  │
│                                                                 │
│  ART 现代（Android 8.0+）：                                      │
│  ├─ Concurrent Copying GC（并发复制）                            │
│  ├─ 支持分代回收                                                 │
│  └─ STW 只有 2-3ms，几乎无感知                                  │
│                                                                 │
│  Android 10+：                                                  │
│  └─ 后台压缩（Back ground Compaction），空闲时整理碎片           │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### Q8：什么是 STW？为什么会导致卡顿？

**答**：**STW（Stop-The-World）= GC 时暂停所有用户线程**。

**为什么需要 STW**：GC 需要确保对象引用关系不变。如果用户线程还在跑，可能出现：
- 正在标记的对象突然被引用了（漏标）
- 刚标记完的引用突然断了（错标）

**对 Android 的影响**：

```
假设 GC STW = 50ms

  时间轴 →
  ├─────┼─────┼─────┼─────┼─────┼─────┼─────┼─────┤
  0    16    32    48    64    80    96   112   128 (ms)
  │     │     │     │     │     │     │     │     │
  帧1   帧2   帧3 ← GC 开始（STW）──────────→ 帧4
                    这 50ms 内无法绘制
                    = 丢了 3 帧
                    = 明显卡顿
```

**现代 ART 的优化**：大部分 GC 工作并发进行，STW 只在最后的原子操作（如引用更新），控制在 2-3ms 内。

### Q9：内存泄漏和内存溢出的区别？

**答**：

| 概念 | 说明 | Android 常见场景 |
|-----|------|-----------------|
| **内存泄漏（Memory Leak）** | 对象不再使用，但无法被回收 | Handler、单例持有 Context |
| **内存溢出（OOM）** | 内存真的不够用了 | 加载大图、泄漏累积 |

**关系**：内存泄漏积累到一定程度 → 可用内存越来越少 → 最终 OOM。

**Android 中的典型泄漏**：

```kotlin
// 1. Handler 泄漏（最常见）
class LeakyActivity : AppCompatActivity() {
    // ❌ 匿名内部类持有外部 Activity 引用
    private val handler = object : Handler(Looper.getMainLooper()) {
        override fun handleMessage(msg: Message) {
            updateUI()  // 隐式引用 this@LeakyActivity
        }
    }
}

// 2. 单例持有 Activity Context
object UserManager {
    // ❌ 单例持有 Activity Context = 泄漏
    private lateinit var context: Context
    
    fun init(context: Context) {
        this.context = context  // 如果传入 Activity，就泄漏了
    }
}

// 3. 监听器未注销
class LeakyFragment : Fragment() {
    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        // 注册了，但忘记注销
        LocationManager.addListener(this)
    }
    // 缺少 onDestroyView 中的 removeListener
}
```

## 三、类加载类

### Q10：类加载过程是怎样的？

**答**：分为 5 个阶段：

```
加载 → 验证 → 准备 → 解析 → 初始化
 │      │      │      │      │
 │      │      │      │      └─ 执行 <clinit>（静态块、静态变量赋值）
 │      │      │      └─ 符号引用 → 直接引用
 │      │      └─ 静态变量分配内存，设零值（不是赋值！）
 │      └─ 验证字节码格式
 └─ 读取 .class/.dex 到内存
```

**面试重点**：准备阶段只设零值，初始化阶段才真正赋值。

```kotlin
class Example {
    companion object {
        // 准备阶段：value = 0（零值）
        // 初始化阶段：value = 100
        val value = 100
        
        // 准备阶段：instance = null
        // 初始化阶段：instance = Example()
        val instance = Example()
    }
}
```

### Q11：什么是双亲委派？Android 有什么特殊处理？

**答**：**双亲委派 = 加载类时先让父加载器尝试，父加载器加载不了才自己加载**。

```
                BootstrapClassLoader（启动类加载器）
                        ↑ 委派
                ExtClassLoader（扩展类加载器）
                        ↑ 委派
                AppClassLoader（应用类加载器）
                        ↑ 委派
                  自定义 ClassLoader
```

**好处**：
1. 避免重复加载（父加载器加载过，子就不用加载）
2. 安全性（防止篡改核心类，如 java.lang.String）

**Android 的类加载器**：

```kotlin
// Android 的类加载器层级
BootClassLoader        // 加载核心类库
    ↑
PathClassLoader        // 加载已安装 APK 的类（默认 ClassLoader）
    ↑
DexClassLoader         // 加载任意路径的 dex（插件化、热修复用）
```

**热修复打破双亲委派**：

```kotlin
// 热修复的核心：让修复后的类优先被加载
// 原理：把补丁 dex 插到 dexElements 数组的最前面

// 补丁在前 → 补丁中的类先被加载 → 修复生效
```

### Q13：StackOverflowError 怎么解决？

**答**：栈溢出，原因是递归太深或方法调用链太长。

**解决方案**：

```kotlin
// 1. 添加递归终止条件
fun factorial(n: Int): Int {
    if (n <= 1) return 1  // 终止条件
    return n * factorial(n - 1)
}

// 2. 使用 Kotlin 尾递归优化
tailrec fun factorialTailRec(n: Int, acc: Int = 1): Int {
    if (n <= 1) return acc
    return factorialTailRec(n - 1, n * acc)  // 编译器优化为循环
}

// 3. 改用迭代
fun factorialIterative(n: Int): Int {
    var result = 1
    for (i in 2..n) {
        result *= i
    }
    return result
}

// 4. 调大栈空间（不推荐，治标不治本）
// -Xss2m
```

```kotlin
// 加载大图的正确姿势
fun loadBitmapOptimized(
    resources: Resources,
    resId: Int,
    reqWidth: Int,
    reqHeight: Int
): Bitmap {
    return BitmapFactory.Options().run {
        // 1. 先获取尺寸，不加载到内存
        inJustDecodeBounds = true
        BitmapFactory.decodeResource(resources, resId, this)
        
        // 2. 计算采样率
        inSampleSize = calculateInSampleSize(this, reqWidth, reqHeight)
        
        // 3. 使用 RGB_565 减少内存（如果不需要透明度）
        inPreferredConfig = Bitmap.Config.RGB_565  // 2 字节/像素，比 ARGB_8888 省一半
        
        // 4. 复用已有 Bitmap（避免重新分配内存）
        inMutable = true
        inBitmap = reusableBitmap  // 如果有的话
        
        // 5. 真正加载
        inJustDecodeBounds = false
        BitmapFactory.decodeResource(resources, resId, this)
    }
}
```

### Q15：LeakCanary 的原理是什么？

**答**：利用弱引用 + ReferenceQueue 检测内存泄漏。

**核心原理**：

```kotlin
// 简化版原理
class LeakCanary {
    // 弱引用队列：被回收的对象会进入这个队列
    private val referenceQueue = ReferenceQueue<Any>()
    
    // 监控中的对象
    private val watchedReferences = mutableMapOf<String, WeakReference<Any>>()
    
    fun watch(obj: Any, description: String) {
        val key = UUID.randomUUID().toString()
        
        // 创建弱引用，关联 ReferenceQueue
        val ref = WeakReference(obj, referenceQueue)
        watchedReferences[key] = ref
        
        // 延迟 5 秒后检查
        executor.execute {
            Thread.sleep(5000)
            checkRetained(key)
        }
    }
    
    private fun checkRetained(key: String) {
        // 从队列中移除已被回收的引用
        removeWeaklyReachableReferences()
        
        // 如果 5 秒后对象仍在 watchedReferences 中，说明没被回收
        if (watchedReferences.containsKey(key)) {
            // 触发 GC，再检查一次
            Runtime.getRuntime().gc()
            Thread.sleep(100)
            removeWeaklyReachableReferences()
            
            if (watchedReferences.containsKey(key)) {
                // 确认泄漏，dump hprof 分析引用链
                dumpHeap()
            }
        }
    }
    
    private fun removeWeaklyReachableReferences() {
        var ref: Reference<*>?
        while (referenceQueue.poll().also { ref = it } != null) {
            // 对象已被回收，从监控列表移除
            watchedReferences.remove(ref?.key)
        }
    }
}
```

**为什么弱引用可以检测泄漏？**

```
正常情况：
Activity 销毁 → 无强引用 → GC 时被回收 → 弱引用进入 ReferenceQueue → 不是泄漏

泄漏情况：
Activity 销毁 → 还有强引用（如被 Handler 持有） → GC 时不回收 → 弱引用不进入队列 → 检测到泄漏
```

### Q16：如何监控线上 OOM？

**答**：这需要结合 APM 方案。

```kotlin
// 1. 设置 OOM 时 dump hprof（需要注意性能影响）
// 在 Application 中配置
Thread.setDefaultUncaughtExceptionHandler { thread, throwable ->
    if (throwable is OutOfMemoryError) {
        // 上报 OOM 信息
        reportOOM(throwable)
        
        // dump hprof（可选，可能失败）
        try {
            val hprofPath = "${cacheDir}/oom_${System.currentTimeMillis()}.hprof"
            Debug.dumpHprofData(hprofPath)
            uploadHprof(hprofPath)
        } catch (e: Exception) {
            // dump 本身也可能 OOM
        }
    }
    // 调用原始处理
    defaultHandler?.uncaughtException(thread, throwable)
}

// 2. 定期采样内存信息
class MemoryMonitor {
    fun startMonitor() {
        CoroutineScope(Dispatchers.IO).launch {
            while (true) {
                val runtime = Runtime.getRuntime()
                val usedMemory = runtime.totalMemory() - runtime.freeMemory()
                val maxMemory = runtime.maxMemory()
                val usage = usedMemory.toFloat() / maxMemory
                
                // 内存使用超过 80% 告警
                if (usage > 0.8f) {
                    reportHighMemoryUsage(usage)
                }
                
                delay(30_000)  // 每 30 秒检查一次
            }
        }
    }
}
```

### Q17：说说你对 ART 内存管理的理解

**答**：ART 的内存管理比标准 JVM 更复杂，针对移动端做了很多优化。

**ART 内存空间划分**：

```
┌─────────────────────────────────────────────────────────────────────────┐
│                        ART 内存空间                                      │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Image Space（只读）                                                     │
│  └─ 预加载的核心类（framework 类），Zygote 启动时加载，所有 App 共享       │
│                                                                         │
│  Zygote Space（共享）                                                    │
│  └─ Zygote 进程预加载的资源，fork 子进程时 COW（Copy-On-Write）            │
│                                                                         │
│  Allocation Space（独占）                                                │
│  └─ App 运行时分配的对象，这是 GC 的主战场                                 │
│                                                                         │
│  Large Object Space                                                     │
│  └─ 大对象（>12KB）单独存放，避免碎片化                                    │
│                                                                         │
│  Non-Moving Space                                                       │
│  └─ 不能移动的对象（如 JNI 引用的对象）                                    │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**ART GC 类型**：

| GC 类型 | 触发条件 | STW 时间 | 说明 |
|--------|---------|---------|------|
| Sticky GC | 年轻代满 | ~1ms | 只回收上次 GC 后分配的对象 |
| Partial GC | Allocation Space 满 | ~3ms | 回收 Allocation Space |
| Full GC | 内存紧张或主动触发 | ~10ms | 回收所有空间 |

## 六、面试答题技巧

### 回答结构：先说结论 → 再说原理 → 最后用 Android 实例佐证

```
面试官：堆和栈有什么区别？

✅ 好的回答：
"堆存对象，栈存局部变量和方法调用（结论）。

堆是线程共享的，大小可配置，由 GC 管理；栈是线程私有的，方法结束自动释放（原理）。

在 Android 开发中，这就是为什么局部变量不会内存泄漏，而成员变量可能会。
比如一个 Handler 如果是 Activity 的成员变量，它在堆中，只要 Handler 不释放，Activity 也无法释放（Android 实例）。"

❌ 不好的回答：
"堆和栈都是内存区域，堆存对象，栈存变量..."（没有层次，没有实例）
```

## 七、快速记忆卡片

### 内存结构

```
堆：对象（new 出来的），GC 管理
方法区：类信息 + 静态变量，生命周期=进程
栈：局部变量 + 方法调用，方法结束自动释放
程序计数器：当前行号
```

### 变量存储

```
局部变量 → 栈（最安全，自动释放）
成员变量 → 堆（跟对象走）
静态变量 → 方法区（最危险，生命周期=进程）
```

### Android 内存泄漏高发区

```
1. Handler 匿名内部类 → 用 lifecycleScope
2. 单例持有 Activity → 用 ApplicationContext
3. 监听器未注销 → onDestroy 中注销
4. 静态变量持有 Context → 避免或用 WeakReference
```

### 排查 OOM 的工具

```
开发阶段：LeakCanary、Android Profiler
线上：KOOM、自定义 UncaughtExceptionHandler
分析工具：MAT、Android Studio Memory Profiler
```
