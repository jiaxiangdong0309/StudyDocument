# Flow 基础篇

## 技术演进：为什么需要 Flow？

### 痛点一：LiveData 功能太弱

LiveData 是 Android 官方的可观察数据容器，但它有明显的局限性：

```kotlin
// LiveData 的操作符只有这两个...
val userLiveData: LiveData<User> = repository.getUser()
    .map { user -> user.name }           // 转换
    .switchMap { name -> searchUser(name) }  // 切换数据源

// 想要 filter？没有！
// 想要 debounce？没有！
// 想要 combine 多个 LiveData？很麻烦！
```

**LiveData 的问题**：
- **操作符太少**：只有 map 和 switchMap，复杂场景很痛苦
- **只能在主线程**：setValue 必须在主线程调用
- **Android 专属**：不能用在纯 Kotlin 模块
- **没有背压处理**：生产者快、消费者慢的场景无法处理

### 痛点二：RxJava 太重太复杂

RxJava 功能强大，但代价也很大：

```kotlin
// RxJava：操作符太多了...
Observable.just(1, 2, 3)
    .subscribeOn(Schedulers.io())
    .observeOn(AndroidSchedulers.mainThread())
    .flatMap { ... }      // 还是 concatMap？还是 switchMap？
    .debounce(300, TimeUnit.MILLISECONDS)
    .distinctUntilChanged()
    .subscribe(
        { /* onNext */ },
        { /* onError */ },
        { /* onComplete */ }
    )
// 别忘了处理 Disposable！不然内存泄漏！
```

**RxJava 的问题**：
- **学习曲线陡峭**：几百个操作符，选择困难症
- **调试困难**：堆栈信息难以阅读
- **库体积大**：约 2MB，增加 APK 体积
- **非官方方案**：Google 不维护，未来不确定

### Flow 的诞生

2019 年，Kotlin 协程 1.3 推出了 Flow。它结合了 LiveData 的简单性和 RxJava 的功能性：

```kotlin
// Flow：简洁又强大
repository.observeUsers()
    .map { users -> users.filter { it.isActive } }  // 操作符丰富
    .debounce(300)                                   // 防抖
    .distinctUntilChanged()                          // 去重
    .flowOn(Dispatchers.IO)                         // 指定线程
    .collect { users ->                              // 收集
        updateUI(users)
    }
```

**Flow 的优势**：

| 对比 | Flow | LiveData | RxJava |
|-----|------|----------|--------|
| 操作符 | 丰富 | 很少 | 非常丰富 |
| 学习曲线 | 平缓 | 简单 | 陡峭 |
| 库体积 | 小（协程的一部分） | 小 | 大（~2MB） |
| 平台 | 跨平台 | Android 专属 | 跨平台 |
| 背压 | 支持 | 不支持 | 支持 |
| 官方支持 | Kotlin 官方 | Android 官方 | 第三方 |
| 取消机制 | 协程自动管理 | 生命周期自动管理 | 手动管理 Disposable |

## 核心概念：用大白话说清楚

### Flow 是什么？

**一句话定义**：Flow 是一个**可以发射多个值**的异步数据流。

如果说 `suspend` 函数返回**一个值**，那么 `Flow` 就是返回**多个值**。

```kotlin
// suspend 函数：返回一个值
suspend fun getUser(): User

// Flow：返回多个值（数据流）
fun observeUsers(): Flow<User>
```

**生活例子**：
- `suspend` 函数就像去餐厅点餐，点完等着，上一道菜
- `Flow` 就像自助餐的传送带，食物一道一道不断送过来

### 冷流 vs 热流

这是理解 Flow 的关键概念！

**冷流（Cold Flow）**：每次收集时才开始执行，每个收集者独立获得完整数据。

```kotlin
// 冷流：每次 collect 都从头执行
val coldFlow = flow {
    println("开始生产数据")
    emit(1)
    emit(2)
    emit(3)
}

// 第一个收集者
coldFlow.collect { println("收集者 A: $it") }
// 输出：开始生产数据 → 收集者 A: 1 → 收集者 A: 2 → 收集者 A: 3

// 第二个收集者（又从头开始！）
coldFlow.collect { println("收集者 B: $it") }
// 输出：开始生产数据 → 收集者 B: 1 → 收集者 B: 2 → 收集者 B: 3
```

**热流（Hot Flow）**：不管有没有收集者，数据都在流动。收集者只能收到订阅后的数据。

```kotlin
// 热流：StateFlow、SharedFlow
val hotFlow = MutableStateFlow(0)

// 启动一个协程不断更新值
launch {
    repeat(100) {
        delay(100)
        hotFlow.value = it  // 不管有没有人收集，都在更新
    }
}

delay(500)  // 等 500ms 再开始收集

// 这时候收集，只能收到第 5 个及之后的值
hotFlow.collect { println(it) }  // 5, 6, 7, 8...
```

```
┌─────────────────────────────────────────────────────────────────┐
│                     冷流 vs 热流 对比                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  冷流（Flow）                    热流（StateFlow/SharedFlow）     │
│                                                                 │
│  ┌─────────┐                    ┌─────────┐                     │
│  │ 数据源   │                    │ 数据源   │ ← 一直在产生数据     │
│  └────┬────┘                    └────┬────┘                     │
│       │                              │                          │
│       │ collect 时才开始              │ 不管有没有收集者          │
│       ▼                              ▼                          │
│  ┌─────────┐                    ┌─────────┐                     │
│  │ 收集者 A │ ← 完整数据           │ 收集者 A │ ← 只收到订阅后的    │
│  └─────────┘   1,2,3             └─────────┘   数据               │
│                                                                 │
│  特点：                          特点：                          │
│  - 懒加载，按需生产               - 始终活跃                      │
│  - 每个收集者独立                 - 多个收集者共享                 │
│  - 收集完自动结束                 - 需要手动管理生命周期            │
│                                                                 │
│  例子：网络请求、文件读取          例子：UI 状态、位置更新          │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**普通 Flow 是冷流**，StateFlow 和 SharedFlow 是热流。

### Flow 的三个角色

```
┌─────────────────────────────────────────────────────────────────┐
│                     Flow 的三个角色                             │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  生产者（Producer）        中间操作符         消费者（Consumer）   │
│  ┌─────────────┐      ┌─────────────┐      ┌─────────────┐     │
│  │  flow { }   │ ──→  │ map/filter  │ ──→  │  collect    │     │
│  │  emit(x)    │      │ debounce    │      │  { value }  │     │
│  └─────────────┘      └─────────────┘      └─────────────┘     │
│                                                                 │
│  - 产生数据               - 转换/过滤数据        - 消费数据        │
│  - 决定发射什么            - 可以有多个           - 触发执行        │
│  - 运行在哪个线程          - flowOn 指定线程      - 只能有一个      │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

## 基本用法：快速上手

### 1. 创建 Flow

#### 方式一：flow 构建器（最常用）

```kotlin
// 最基础的创建方式：flow { } 构建器
fun countDown(start: Int): Flow<Int> = flow {
    for (i in start downTo 1) {
        delay(1000)     // 每秒
        emit(i)         // 发射值
    }
    emit(0)             // 最后发射 0
}

// 使用
countDown(5).collect { second ->
    println("倒计时: $second")
}
// 输出：倒计时: 5 → 4 → 3 → 2 → 1 → 0
```

#### 方式二：flowOf（创建固定值的 Flow）

```kotlin
// 类似 listOf，创建包含固定元素的 Flow
val numbers = flowOf(1, 2, 3, 4, 5)

numbers.collect { println(it) }  // 1, 2, 3, 4, 5
```

#### 方式三：asFlow（集合转 Flow）

```kotlin
// 把现有集合转成 Flow
val list = listOf("A", "B", "C")
val flow = list.asFlow()

// 范围也可以
(1..10).asFlow().collect { println(it) }
```

#### 方式四：callbackFlow（回调转 Flow）

当需要把传统的回调 API 转成 Flow 时使用：

```kotlin
// 把位置监听回调转成 Flow
fun locationUpdates(
    locationClient: FusedLocationProviderClient
): Flow<Location> = callbackFlow {
    
    // 创建位置回调
    val callback = object : LocationCallback() {
        override fun onLocationResult(result: LocationResult) {
            // 把回调的数据发送到 Flow
            result.lastLocation?.let { location ->
                trySend(location)  // 在回调中用 trySend，不是 emit
            }
        }
    }
    
    // 注册监听
    val request = LocationRequest.Builder(10000).build()
    locationClient.requestLocationUpdates(request, callback, Looper.getMainLooper())
    
    // awaitClose：当 Flow 被取消时执行清理
    awaitClose {
        locationClient.removeLocationUpdates(callback)
    }
}

// 使用
lifecycleScope.launch {
    locationUpdates(locationClient)
        .collect { location ->
            updateLocationUI(location)
        }
}
```

**callbackFlow 要点**：
- 用 `trySend()` 而不是 `emit()` 发送数据（因为可能在非挂起上下文）
- 必须调用 `awaitClose {}` 来清理资源
- 当收集被取消时，awaitClose 会执行

### 2. 收集 Flow

#### collect：最基本的收集

```kotlin
// collect 是一个挂起函数，会暂停直到 Flow 完成
flow.collect { value ->
    println(value)
}
println("Flow 完成了")  // 等 Flow 完全结束才执行
```

#### collectLatest：只处理最新值

当生产速度 > 消费速度时，取消正在处理的旧值，只处理最新值：

```kotlin
// 模拟：生产快，消费慢
flow {
    emit(1)
    delay(50)
    emit(2)
    delay(50)
    emit(3)
}.collectLatest { value ->
    println("开始处理 $value")
    delay(100)  // 处理需要 100ms
    println("处理完成 $value")
}

// 输出：
// 开始处理 1
// 开始处理 2（取消了 1 的处理）
// 开始处理 3（取消了 2 的处理）
// 处理完成 3（只有最后一个完成了）
```

**使用场景**：搜索框输入时，用户连续输入，只需要处理最后一次输入。

#### first / firstOrNull：只取第一个值

```kotlin
val firstUser = userFlow.first()           // 取第一个，Flow 为空会抛异常
val maybeUser = userFlow.firstOrNull()     // 取第一个，Flow 为空返回 null
```

#### toList / toSet：收集到集合

```kotlin
val list: List<Int> = (1..5).asFlow().toList()  // [1, 2, 3, 4, 5]
val set: Set<Int> = flowOf(1, 1, 2, 2, 3).toSet()  // {1, 2, 3}
```

### 3. 基础操作符

#### map：转换每个元素

```kotlin
// 用户 ID 流 → 用户名流
userIdFlow
    .map { id -> userRepository.getUser(id) }  // 根据 ID 获取用户
    .map { user -> user.name }                  // 提取名字
    .collect { name -> println(name) }
```

#### filter：过滤元素

```kotlin
// 只保留活跃用户
usersFlow
    .filter { user -> user.isActive }
    .collect { activeUser -> println(activeUser) }
```

#### take：只取前 N 个

```kotlin
// 只取前 3 个
(1..100).asFlow()
    .take(3)
    .collect { println(it) }  // 1, 2, 3
```

#### drop：跳过前 N 个

```kotlin
// 跳过前 2 个
(1..5).asFlow()
    .drop(2)
    .collect { println(it) }  // 3, 4, 5
```

#### onEach：对每个元素执行副作用

```kotlin
// 打印日志，但不影响数据
dataFlow
    .onEach { data -> Log.d("Flow", "收到数据: $data") }
    .map { it.process() }
    .collect { updateUI(it) }
```

#### onStart / onCompletion：开始和结束回调

```kotlin
dataFlow
    .onStart { 
        Log.d("Flow", "开始收集")
        showLoading()  // 显示加载中
    }
    .onCompletion { cause ->
        Log.d("Flow", "收集结束: $cause")
        hideLoading()  // 隐藏加载中
    }
    .collect { updateUI(it) }
```

### 4. 线程切换

#### flowOn：指定上游的执行线程

```kotlin
flow {
    // 这个块在 IO 线程执行
    val data = fetchFromNetwork()  // 网络请求
    emit(data)
}
.flowOn(Dispatchers.IO)  // 指定上游线程
.map { process(it) }      // 这个还是在 IO 线程
.flowOn(Dispatchers.Default)  // 上面的 map 改到 Default 线程
.collect { 
    // collect 在调用者的线程（通常是 Main）
    updateUI(it)
}
```

**flowOn 的特点**：
- 只影响**上游**（flowOn 之前的操作）
- 可以多次调用，每次只影响到上一个 flowOn
- **不影响下游**（collect 等）

#### withContext vs flowOn 的区别

```kotlin
// ❌ 错误：不能在 flow 内部用 withContext 切换到不同的调度器发射
flow {
    withContext(Dispatchers.IO) {
        emit(fetchData())  // 可能崩溃！
    }
}

// ✅ 正确：用 flowOn
flow {
    emit(fetchData())
}
.flowOn(Dispatchers.IO)
```

**为什么？** Flow 的设计是**上下文保持**（Context Preservation），emit 必须在同一个上下文中调用。flowOn 通过创建新的协程来安全地切换线程。

### 5. 异常处理

#### catch：捕获上游异常

```kotlin
dataFlow
    .map { 
        if (it.isInvalid) throw IllegalArgumentException("无效数据")
        it.process()
    }
    .catch { e ->
        // 捕获上游的异常（map 抛出的）
        Log.e("Flow", "处理出错: ${e.message}")
        emit(Data.default())  // 可以发射默认值继续
    }
    .collect { updateUI(it) }
```

**catch 的特点**：
- 只能捕获**上游**的异常
- 可以在 catch 中 emit 值，让 Flow 继续
- **不能捕获 collect 中的异常**

```kotlin
// catch 不能捕获 collect 中的异常
flow { emit(1) }
    .catch { Log.e("Flow", "捕获不到！") }
    .collect { 
        throw Exception("collect 中的异常")  // catch 捕获不到
    }

// 正确做法：在外层 try-catch
try {
    flow.catch { /* 上游异常 */ }
        .collect { updateUI(it) }
} catch (e: Exception) {
    // collect 中的异常
}
```

#### retry / retryWhen：重试

```kotlin
// 简单重试：最多重试 3 次
apiFlow
    .retry(3)  // 出错自动重试，最多 3 次
    .collect { updateUI(it) }

// 条件重试：只有特定异常才重试
apiFlow
    .retryWhen { cause, attempt ->
        if (cause is IOException && attempt < 3) {
            delay(1000 * (attempt + 1))  // 指数退避
            true  // 返回 true 表示重试
        } else {
            false  // 返回 false 表示不重试，异常继续传播
        }
    }
    .collect { updateUI(it) }
```

## 实际应用场景

### 场景一：搜索防抖

用户在搜索框输入时，不是每输入一个字符就请求接口，而是等用户停止输入 300ms 后再请求。

```kotlin
class SearchViewModel : ViewModel() {
    
    // 用户输入的搜索词
    private val searchQuery = MutableStateFlow("")
    
    // 搜索结果（由 searchQuery 转换而来）
    val searchResults: StateFlow<List<SearchResult>> = searchQuery
        .debounce(300)                    // 防抖：300ms 内没有新输入才继续
        .filter { it.length >= 2 }        // 至少输入 2 个字符
        .distinctUntilChanged()           // 去重：相同的查询不重复搜索
        .flatMapLatest { query ->         // 切换到新的搜索，取消旧的
            if (query.isEmpty()) {
                flowOf(emptyList())
            } else {
                searchRepository.search(query)
                    .catch { emit(emptyList()) }  // 搜索出错返回空列表
            }
        }
        .stateIn(
            scope = viewModelScope,
            started = SharingStarted.WhileSubscribed(5000),
            initialValue = emptyList()
        )
    
    // 用户输入时调用
    fun onQueryChange(query: String) {
        searchQuery.value = query
    }
}
```

### 场景二：Room 数据库监听

Room 原生支持返回 Flow，数据变化时自动通知：

```kotlin
// 1. DAO 返回 Flow
@Dao
interface TaskDao {
    @Query("SELECT * FROM tasks ORDER BY createdAt DESC")
    fun observeAllTasks(): Flow<List<Task>>  // 数据变化时自动发射新列表
    
    @Query("SELECT * FROM tasks WHERE completed = 0")
    fun observePendingTasks(): Flow<List<Task>>
    
    @Insert
    suspend fun insert(task: Task)
    
    @Update
    suspend fun update(task: Task)
}

// 2. Repository
class TaskRepository(private val taskDao: TaskDao) {
    
    fun observeTasks(): Flow<List<Task>> = taskDao.observeAllTasks()
    
    suspend fun addTask(title: String) {
        taskDao.insert(Task(title = title))
        // 不需要手动通知 UI，Flow 会自动发射新数据！
    }
}

// 3. ViewModel
class TaskListViewModel(private val repository: TaskRepository) : ViewModel() {
    
    val tasks: StateFlow<List<Task>> = repository.observeTasks()
        .stateIn(
            scope = viewModelScope,
            started = SharingStarted.WhileSubscribed(5000),
            initialValue = emptyList()
        )
    
    fun addTask(title: String) {
        viewModelScope.launch {
            repository.addTask(title)
            // UI 会自动更新！
        }
    }
}
```

### 场景三：定时刷新数据

每隔一段时间自动刷新数据：

```kotlin
class DashboardViewModel(private val repository: DashboardRepository) : ViewModel() {
    
    // 每 30 秒刷新一次的数据流
    val dashboardData: StateFlow<DashboardData?> = flow {
        while (true) {
            val data = repository.fetchDashboard()
            emit(data)
            delay(30_000)  // 30 秒
        }
    }
    .catch { e ->
        Log.e("Dashboard", "刷新失败: ${e.message}")
        // 不 emit 任何值，保持上一次的数据
    }
    .stateIn(
        scope = viewModelScope,
        started = SharingStarted.WhileSubscribed(5000),
        initialValue = null
    )
}
```

### 场景四：多数据源合并

同时监听多个数据源，合并成一个状态：

```kotlin
class ProfileViewModel(
    private val userRepository: UserRepository,
    private val settingsRepository: SettingsRepository
) : ViewModel() {
    
    // 合并用户信息和设置
    val profileState: StateFlow<ProfileState> = combine(
        userRepository.observeUser(),
        settingsRepository.observeSettings()

            avatar = user?.avatar,
            darkMode = settings.darkMode,
            notificationEnabled = settings.notificationEnabled

    .stateIn(
        scope = viewModelScope,
        started = SharingStarted.WhileSubscribed(5000),

    )
}

data class ProfileState(
    val userName: String,
    val avatar: String?,
    val darkMode: Boolean,
    val notificationEnabled: Boolean
) {
    companion object {
        fun default() = ProfileState(
            userName = "加载中...",
            avatar = null,
            darkMode = false,
            notificationEnabled = true
        )
    }
}
```

## 常见问题与陷阱

### 1. 在 Activity/Fragment 中收集 Flow 要注意生命周期

```kotlin
// ❌ 错误：Activity 进入后台时还在收集，浪费资源
lifecycleScope.launch {
    viewModel.uiState.collect { state ->
        updateUI(state)  // Activity 不可见时也在执行
    }
}

// ✅ 正确：使用 repeatOnLifecycle，只在前台收集
lifecycleScope.launch {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.uiState.collect { state ->
            updateUI(state)  // 只在 STARTED 及以上状态执行
        }
    }
}

// 或者用扩展函数（更简洁）
lifecycleScope.launch {
    viewModel.uiState
        .flowWithLifecycle(lifecycle, Lifecycle.State.STARTED)
        .collect { state ->
            updateUI(state)
        }
}
```

### 2. collect 是挂起函数，会阻塞后续代码

```kotlin
// 问题：collect 后面的代码永远不会执行（假设 Flow 是无限的）
lifecycleScope.launch {
    viewModel.dataFlow.collect { /* ... */ }
    println("这行永远不会执行！")  // 因为 collect 一直在等待新数据
}

// 解决方案 1：使用 launchIn
viewModel.dataFlow
    .onEach { updateUI(it) }
    .launchIn(lifecycleScope)

// 后续代码可以继续执行

// 解决方案 2：在单独的 launch 中收集
lifecycleScope.launch {
    viewModel.dataFlow.collect { /* ... */ }
}
lifecycleScope.launch {
    viewModel.anotherFlow.collect { /* ... */ }
}
```

### 3. StateFlow 不会发射相同的值

```kotlin
val stateFlow = MutableStateFlow(1)

stateFlow.collect { println(it) }

stateFlow.value = 1  // 不会发射！因为值相同
stateFlow.value = 2  // 发射 2
stateFlow.value = 2  // 不会发射！因为值相同
```

如果需要发射相同的值，用 SharedFlow：

```kotlin
val sharedFlow = MutableSharedFlow<Int>()

sharedFlow.collect { println(it) }

sharedFlow.emit(1)  // 发射 1
sharedFlow.emit(1)  // 发射 1（SharedFlow 不去重）
```

### 4. Flow 是冷的，每次 collect 都重新执行

```kotlin
val flow = flow {
    println("开始执行")
    emit(1)
    emit(2)
}

// 第一次收集
flow.collect { println("A: $it") }
// 输出：开始执行 → A: 1 → A: 2

// 第二次收集（又从头执行！）
flow.collect { println("B: $it") }
// 输出：开始执行 → B: 1 → B: 2
```

如果需要共享数据，用 stateIn 或 shareIn 转成热流。

### 5. flowOn 只影响上游

```kotlin
flow {
    println("生产者线程: ${Thread.currentThread().name}")  // IO
    emit(1)
}
.flowOn(Dispatchers.IO)  // 只影响上面的 flow 块
.map {
    println("map 线程: ${Thread.currentThread().name}")  // Main！
    it * 2
}
.collect {
    println("收集线程: ${Thread.currentThread().name}")  // Main
}

// 如果想让 map 也在 IO 线程，要再加一个 flowOn
flow { emit(1) }
    .flowOn(Dispatchers.IO)
    .map { it * 2 }
    .flowOn(Dispatchers.IO)  // 这个 flowOn 让 map 也在 IO 线程
    .collect { }
```

## 面试检验

### 基础概念题

**Q1：Flow 是什么？和 LiveData 有什么区别？**

> **答案**：Flow 是 Kotlin 协程库中的响应式流实现，用于处理异步数据流。
> 
> 与 LiveData 的区别：
> | | Flow | LiveData |
> |--|------|----------|
> | 来源 | Kotlin 标准库 | Android 专属 |
> | 操作符 | 丰富（map、filter、flatMap...） | 很少（map、switchMap） |
> | 线程 | 可指定任意调度器 | 只能在主线程 setValue |
> | 生命周期 | 需要配合 repeatOnLifecycle | 自动感知 |
> | 背压 | 支持 | 不支持 |
> | 跨平台 | 支持 | Android 专属 |
> 
> 推荐：Repository 层用 Flow，ViewModel 到 UI 用 StateFlow。

**Q2：什么是冷流？什么是热流？Flow 是哪种？**

> **答案**：
> - **冷流**：每次收集时才开始执行，每个收集者独立获得完整数据。像点播视频。
> - **热流**：不管有没有收集者，数据都在流动。收集者只能收到订阅后的数据。像直播。
> 
> **普通 Flow 是冷流**，StateFlow 和 SharedFlow 是热流。
> 
> 冷流的好处是懒加载、节省资源；热流的好处是多个订阅者共享数据。

**Q3：collect 和 collectLatest 有什么区别？**

> **答案**：
> - **collect**：处理每一个值，前一个处理完才处理下一个
> - **collectLatest**：如果有新值到来，取消正在处理的旧值，只处理最新的
> 
> 使用场景：
> - `collect`：需要处理每个值的场景（如消息队列）
> - `collectLatest`：只关心最新值的场景（如搜索输入、UI 状态更新）

**Q4：flowOn 和 withContext 有什么区别？**

> **答案**：
> - **flowOn**：切换 Flow **上游**的执行线程，不影响下游
> - **withContext**：切换当前协程的执行线程
> 
> 关键区别：**不能在 flow 块内用 withContext 来 emit**，因为 Flow 要求 emit 在同一个上下文中调用。flowOn 通过创建新协程来安全地切换线程。
> 
> ```kotlin
> // ❌ 错误
> flow { withContext(Dispatchers.IO) { emit(1) } }
> 
> // ✅ 正确
> flow { emit(1) }.flowOn(Dispatchers.IO)
> ```

**Q5：catch 操作符能捕获 collect 中的异常吗？**

> **答案**：**不能**。catch 只能捕获上游的异常。
> 
> ```kotlin
> flow { emit(1) }
>     .catch { /* 只能捕获上游异常 */ }
>     .collect { 
>         throw Exception("catch 捕获不到！") 
>     }
> ```
> 
> 要捕获 collect 中的异常，需要在外层用 try-catch，或者把处理逻辑移到 onEach 中（onEach 的异常可以被 catch 捕获）。
