# Activity 基础篇

## 技术演进：为什么需要 Activity？

### 从桌面应用说起

在 PC 时代，一个应用就是一个窗口，用户打开应用后：
- 所有功能都在一个窗口里
- 应用完全控制自己的生命周期
- 资源（内存、CPU）几乎不受限制

但手机不一样：

```
┌────────────────────────────────────────────────────────────┐
│                      手机 vs 电脑                           │
├────────────────────────────────────────────────────────────┤
│                                                            │
│    电脑：                        手机：                     │
│    • 内存 16GB+                  • 内存 4-8GB               │
│    • 持续供电                     • 电池容量有限             │
│    • 多窗口并行                   • 通常单窗口焦点           │
│    • 用户主动关闭应用             • 系统随时可能杀进程        │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

### Android 的设计哲学

Android 设计之初就考虑到移动设备的特点，提出了几个核心理念：

**1. 组件化设计**

不是把应用当成一个整体，而是拆成多个独立组件（Activity、Service、BroadcastReceiver、ContentProvider）。好处是：
- 组件可以被其他应用调用（如分享功能）
- 系统可以单独管理每个组件的生命周期
- 更细粒度的资源控制

**2. 声明式组件**

所有组件必须在 `AndroidManifest.xml` 中声明，系统才知道你的应用有哪些"入口点"。

**3. 生命周期托管**

组件的生命周期由系统管理，不是由应用自己控制。系统会根据资源情况决定是否要"回收"你的组件。

### Activity 的角色

Activity 就是在这种设计哲学下诞生的**界面组件**：

```
┌────────────────────────────────────────────────────────────┐
│                   Activity 是什么？                         │
├────────────────────────────────────────────────────────────┤
│                                                            │
│   一句话：Activity = 一个屏幕界面 + 用户交互入口            │
│                                                            │
│   类比：                                                    │
│   • 餐厅：Activity 是一个包厢，你在这里点菜、吃饭           │
│   • 剧院：Activity 是一个舞台，演员（View）在上面表演       │
│   • 书籍：Activity 是一页纸，展示内容供你阅读               │
│                                                            │
│   核心职责：                                                │
│   ✓ 创建和管理窗口（Window）                               │
│   ✓ 托管 View 层级树                                       │
│   ✓ 响应生命周期事件                                        │
│   ✓ 处理用户交互                                            │
│   ✓ 与其他组件/应用通信                                     │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

## 生命周期：Activity 的"一生"

### 为什么需要生命周期？

想象你开了一家餐厅（Activity）：

```
开店前：装修、准备食材（onCreate）
开门营业：可以接客了（onStart）
客人进来：开始服务（onResume）
客人暂时离开：去上厕所（onPause）
客人全走了：打烊但不关门（onStop）
关门大吉：彻底关闭（onDestroy）
```

Android 系统通过生命周期回调告诉你："嘿，现在是什么状态，你该做什么了"。

### 生命周期全景图

```
┌─────────────────────────────────────────────────────────────────┐
```

### 每个回调该做什么？

| 回调 | 调用时机 | 你该做什么 | 你不该做什么 |
|-----|---------|-----------|-------------|
| `onCreate` | Activity 首次创建 | setContentView、初始化 View、绑定数据 | 耗时操作、网络请求 |
| `onStart` | 变为可见 | 注册广播、开始动画 | 耗时操作 |
| `onResume` | 获得焦点，可交互 | 恢复暂停的操作、开始相机预览 | - |
| `onPause` | 失去焦点 | 暂停动画、释放相机 | 保存数据到数据库（太慢） |
| `onStop` | 完全不可见 | 保存数据、释放资源 | 耗时操作（可能被快速杀死） |
| `onDestroy` | 即将销毁 | 释放所有资源、取消注册 | 尝试恢复状态（已经晚了） |

### 代码示例：生命周期监控

```kotlin
class LifecycleActivity : AppCompatActivity() {
    
    // 使用 TAG 方便在 Logcat 中过滤
    companion object {
        private const val TAG = "LifecycleDemo"
    }
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_lifecycle)
        
        // onCreate 适合做的事：
        // 1. 设置布局
        // 2. 初始化成员变量
        // 3. 恢复保存的状态
        Log.d(TAG, "onCreate: 是否有保存的状态? ${savedInstanceState != null}")
        
        savedInstanceState?.let {
            val count = it.getInt("counter", 0)
            Log.d(TAG, "恢复计数器: $count")
        }
    }
    
    override fun onStart() {
        super.onStart()
        // Activity 可见但还不能交互
        // 适合注册广播接收器
        Log.d(TAG, "onStart: Activity 可见了")
    }
    
    override fun onResume() {
        super.onResume()
        // Activity 在前台，可以交互
        // 适合开始动画、恢复播放
        Log.d(TAG, "onResume: Activity 可交互了")
    }
    
    override fun onPause() {
        super.onPause()
        // Activity 失去焦点，可能还可见（如对话框覆盖）
        // 适合暂停动画、释放独占资源（如相机）
        // 注意：这个方法要快，否则影响下一个 Activity 显示
        Log.d(TAG, "onPause: Activity 失去焦点")
    }
    
    override fun onStop() {
        super.onStop()
        // Activity 完全不可见
        // 适合保存数据、释放非必要资源
        Log.d(TAG, "onStop: Activity 不可见了")
    }
    
    override fun onDestroy() {
        super.onDestroy()
        // Activity 即将被销毁
        // 必须释放所有资源，避免内存泄漏
        Log.d(TAG, "onDestroy: Activity 即将销毁, isFinishing=${isFinishing}")
    }
    
    override fun onRestart() {
        super.onRestart()
        // 从 stopped 状态重新启动
        Log.d(TAG, "onRestart: 从停止状态恢复")
    }
}
```

### 经典面试题：A 启动 B 的回调顺序

这是面试必问题，理解了这个顺序才算真正理解生命周期。

**场景**：Activity A 启动 Activity B

```
时间线：
────────────────────────────────────────────────────────────►

A.onPause()          ← A 先失去焦点
        ↓
    B.onCreate()     ← B 开始创建
        ↓
    B.onStart()      ← B 可见
        ↓
    B.onResume()     ← B 可交互
        ↓
A.onStop()           ← A 完全不可见后才 stop
```

**为什么是这个顺序？**

设计原则：**保证用户始终能看到一个完整的界面**

1. A 先 pause：告诉 A "你即将失去焦点，做好准备"
2. B 创建并显示：此时 A 还在后面，但已经不处理用户输入
3. B 完全可见后，A 才 stop：因为这时 A 已经被完全遮挡了

**实际验证代码**：

```kotlin
// 在 A 和 B 中都添加日志
override fun onPause() {
    super.onPause()
    Log.d("Lifecycle", "${javaClass.simpleName}.onPause")
}

// 输出顺序：
// ActivityA.onPause
// ActivityB.onCreate
// ActivityB.onStart
// ActivityB.onResume
// ActivityA.onStop
```

## 状态保存与恢复

### 为什么需要保存状态？

你正在填一个表单，突然来了个电话，接完电话发现表单内容全没了——这就是没有正确处理状态保存的后果。

**会触发状态保存的场景**：

| 场景 | 是否调用 onSaveInstanceState | 是否调用 onDestroy |
|-----|---------------------------|-------------------|
| 按 Home 键 | ✓ | ✗ |
| 屏幕旋转 | ✓ | ✓ |
| 打开新 Activity | ✓ | ✗ |
| 锁屏 | ✓ | ✗ |
| 内存不足被杀 | ✓ | ✓ |
| 按返回键 | ✗ | ✓ |
| 调用 finish() | ✗ | ✓ |

> **关键规律**：用户主动退出（返回键、finish）不保存；系统可能杀死（旋转、切后台）要保存。

### onSaveInstanceState vs onRestoreInstanceState

```kotlin
class FormActivity : AppCompatActivity() {
    
    private var counter = 0
    private lateinit var editText: EditText
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_form)
        
        editText = findViewById(R.id.editText)
        
        // 方式1：在 onCreate 中恢复（推荐）
        // savedInstanceState 为 null 表示是首次创建，不是恢复
        savedInstanceState?.let {
            counter = it.getInt("counter", 0)
            // 注意：EditText 自带 id 的话，系统会自动恢复其文本
        }
    }
    
    override fun onSaveInstanceState(outState: Bundle) {
        // 在 onStop 之前调用（Android P 及以上是 onStop 之后）
        // 保存需要恢复的数据
        outState.putInt("counter", counter)
        
        // 别忘了调用 super，它会保存 View 层级的状态
        super.onSaveInstanceState(outState)
    }
    
    override fun onRestoreInstanceState(savedInstanceState: Bundle) {
        // 在 onStart 之后调用
        // 方式2：在这里恢复（如果需要确保 View 已经初始化完成）
        super.onRestoreInstanceState(savedInstanceState)
        
        // 这时 View 的状态已经被 super 恢复了
        counter = savedInstanceState.getInt("counter", 0)
    }
}
```

### View 的自动保存

有些 View 会自动保存恢复状态，但有个前提：**必须设置 android:id**

```xml
<!-- ✅ 会自动恢复文本 -->
<EditText
    android:id="@+id/editName"
    android:layout_width="match_parent"
    android:layout_height="wrap_content"/>

<!-- ❌ 不会自动恢复，因为没有 id -->
<EditText
    android:layout_width="match_parent"
    android:layout_height="wrap_content"/>
```

**原理**：系统在保存状态时，会遍历所有有 id 的 View，调用它们的 `onSaveInstanceState()`。

## Intent：Activity 之间的信使

### Intent 是什么？

Intent 是 Android 组件之间通信的"信封"，包含了：
- **要干什么**（Action）
- **对谁干**（Component/Category）
- **带什么数据**（Extras/Data）

```
┌────────────────────────────────────────────────────────────┐
│                      Intent 结构                           │
├────────────────────────────────────────────────────────────┤
│                                                            │
│   ┌──────────────┐                                         │
│   │   Action     │  做什么？VIEW/SEND/PICK/CALL...         │
│   ├──────────────┤                                         │
│   │   Data       │  操作什么？URI 格式                      │
│   ├──────────────┤                                         │
│   │   Category   │  补充说明：LAUNCHER/DEFAULT/BROWSABLE   │
│   ├──────────────┤                                         │
│   │   Component  │  指定目标：包名+类名                     │
│   ├──────────────┤                                         │
│   │   Extras     │  附加数据：键值对                        │
│   ├──────────────┤                                         │
│   │   Flags      │  启动标志：控制启动行为                   │
│   └──────────────┘                                         │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

### 显式 Intent vs 隐式 Intent

```kotlin
// ================== 显式 Intent ==================
// 明确指定要启动哪个 Activity（用于应用内跳转）
val explicitIntent = Intent(this, DetailActivity::class.java)
startActivity(explicitIntent)

// ================== 隐式 Intent ==================
// 只描述要做什么，让系统找合适的 Activity（用于跨应用）
val implicitIntent = Intent(Intent.ACTION_VIEW).apply {
    data = Uri.parse("https://www.google.com")
}

// 隐式 Intent 可能没有匹配的 Activity，要做保护
if (implicitIntent.resolveActivity(packageManager) != null) {
    startActivity(implicitIntent)
} else {
    Toast.makeText(this, "没有找到合适的应用", Toast.LENGTH_SHORT).show()
}
```

### 数据传递

```kotlin
// ================== 发送方 ==================
class MainActivity : AppCompatActivity() {
    
    private fun openDetail() {
        val intent = Intent(this, DetailActivity::class.java).apply {
            // 基本类型
            putExtra("id", 123)
            putExtra("name", "张三")
            putExtra("isVip", true)
            
            // 传递对象（需要实现 Parcelable）
            putExtra("user", User("李四", 25))  // User 需要是 Parcelable
            
            // 传递列表
            putStringArrayListExtra("tags", arrayListOf("Android", "Kotlin"))
        }
        startActivity(intent)
    }
}

// ================== 接收方 ==================
class DetailActivity : AppCompatActivity() {
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        
        // 获取数据（带默认值，避免空指针）
        val id = intent.getIntExtra("id", -1)
        val name = intent.getStringExtra("name") ?: "默认"
        val isVip = intent.getBooleanExtra("isVip", false)
        
        // 获取 Parcelable 对象
        val user = if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU) {
            intent.getParcelableExtra("user", User::class.java)
        } else {
            @Suppress("DEPRECATION")
            intent.getParcelableExtra("user")
        }
        
        // 获取列表
        val tags = intent.getStringArrayListExtra("tags") ?: emptyList()
    }
}

// ================== Parcelable 对象 ==================
// 使用 @Parcelize 注解简化实现（需要 kotlin-parcelize 插件）
@Parcelize
data class User(
    val name: String,
    val age: Int
) : Parcelable
```

### Activity Result API（推荐）

传统的 `startActivityForResult` 已被废弃，现在推荐使用 Activity Result API：

```kotlin
class MainActivity : AppCompatActivity() {
    
    // 注册结果回调（必须在 onCreate 之前注册，通常作为成员变量）
    private val pickImageLauncher = registerForActivityResult(
        ActivityResultContracts.GetContent()
    ) { uri: Uri? ->
        // 处理选择的图片
        uri?.let { 
            imageView.setImageURI(it)
        }
    }
    
    // 自定义 Activity 结果
    private val customLauncher = registerForActivityResult(
        ActivityResultContracts.StartActivityForResult()
    ) { result ->
        if (result.resultCode == RESULT_OK) {
            val data = result.data?.getStringExtra("result")
            // 处理返回的数据
        }
    }
    
    private fun pickImage() {
        pickImageLauncher.launch("image/*")
    }
    
    private fun openCustomActivity() {
        val intent = Intent(this, CustomActivity::class.java)
        customLauncher.launch(intent)
    }
}

// 返回结果的 Activity
class CustomActivity : AppCompatActivity() {
    
    private fun returnResult() {
        val resultIntent = Intent().apply {
            putExtra("result", "操作成功")
        }
        setResult(RESULT_OK, resultIntent)
        finish()
    }
}
```

## 常见问题与陷阱

### 1. 屏幕旋转重建

**问题**：屏幕旋转后 Activity 重建，数据丢失

**解决方案**：

```kotlin
// 方案1：固定屏幕方向（简单粗暴）
// 在 AndroidManifest.xml 中设置
android:screenOrientation="portrait"

// 方案2：使用 ViewModel（推荐）
class MyViewModel : ViewModel() {
    var data: String = ""
}

class MyActivity : AppCompatActivity() {
    private val viewModel: MyViewModel by viewModels()
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        // viewModel.data 在配置变更后依然存在
    }
}

// 方案3：自己处理配置变更（不推荐，除非有特殊需求）
// AndroidManifest.xml
android:configChanges="orientation|screenSize"

// Activity 中
override fun onConfigurationChanged(newConfig: Configuration) {
    super.onConfigurationChanged(newConfig)
    // 自己处理配置变更，Activity 不会重建
}
```

### 2. 内存泄漏

**问题**：Activity 销毁后，仍被其他对象持有引用

```kotlin
// ❌ 错误：匿名内部类持有 Activity 引用
class LeakyActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        
        // Handler 持有 Activity 引用，消息未处理完 Activity 就泄漏了
        val handler = Handler(Looper.getMainLooper())
        handler.postDelayed({
            // 这个 lambda 持有 Activity 引用
            updateUI()
        }, 60000)  // 1 分钟后执行
    }
}

// ✅ 正确：使用弱引用或在销毁时清理
class SafeActivity : AppCompatActivity() {
    
    private val handler = Handler(Looper.getMainLooper())
    private val updateRunnable = Runnable { updateUI() }
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        handler.postDelayed(updateRunnable, 60000)
    }
    
    override fun onDestroy() {
        super.onDestroy()
        // 移除未执行的消息，避免泄漏
        handler.removeCallbacks(updateRunnable)
    }
    
    private fun updateUI() {
        // 更新 UI
    }
}
```

### 3. Fragment 事务异常

**问题**：在 `onSaveInstanceState` 之后执行 Fragment 事务崩溃

```kotlin
// ❌ 错误：异步回调中直接执行事务
apiService.getData().enqueue(object : Callback<Data> {
    override fun onResponse(call: Call<Data>, response: Response<Data>) {
        // Activity 可能已经 onStop/onDestroy
        // 此时执行 commit() 会崩溃
        supportFragmentManager.beginTransaction()
            .replace(R.id.container, DetailFragment())
            .commit()  // 💥 IllegalStateException
    }
})

// ✅ 正确方案1：使用 commitAllowingStateLoss（可能丢失状态）
supportFragmentManager.beginTransaction()
    .replace(R.id.container, DetailFragment())
    .commitAllowingStateLoss()

// ✅ 正确方案2：检查 Activity 状态
if (!isFinishing && !isDestroyed) {
    supportFragmentManager.beginTransaction()
        .replace(R.id.container, DetailFragment())
        .commit()
}

// ✅ 正确方案3：使用 Lifecycle 感知（推荐）
lifecycleScope.launch {
    val data = apiService.getData()
    // 只有在 STARTED 状态后才执行
    lifecycle.whenStarted {
        supportFragmentManager.beginTransaction()
            .replace(R.id.container, DetailFragment())
            .commit()
    }
}
```

## 面试检验

### 基础题

**Q1: Activity 生命周期有哪些回调？分别在什么时候调用？**

> **答案**：
> - `onCreate`：首次创建时调用，用于初始化
> - `onStart`：变为可见时调用
> - `onResume`：获得焦点、可交互时调用
> - `onPause`：失去焦点时调用（可能还可见）
> - `onStop`：完全不可见时调用
> - `onDestroy`：销毁前调用
> - `onRestart`：从 stopped 状态恢复时调用（在 onStart 之前）

**Q2: Activity A 启动 Activity B，生命周期回调顺序是什么？**

> **答案**：A.onPause → B.onCreate → B.onStart → B.onResume → A.onStop
> 
> **原因**：保证用户始终能看到一个完整界面。A 先让出焦点，B 创建显示完成后，A 才完全停止。

**Q3: onSaveInstanceState 在什么时候调用？什么时候不调用？**

> **答案**：
> - 调用场景：按 Home、屏幕旋转、打开新 Activity、锁屏、内存不足被杀
> - 不调用场景：用户按返回键、调用 finish()
> - 规律：用户主动退出不保存，系统可能杀死时会保存

**Q4: 横竖屏切换时 Activity 的生命周期是怎样的？**

> **答案**：默认情况下，Activity 会销毁重建：onPause → onStop → onSaveInstanceState → onDestroy → onCreate → onStart → onRestoreInstanceState → onResume
> 
> 如果配置了 `android:configChanges="orientation|screenSize"`，则只调用 `onConfigurationChanged`，不会重建。

**Q5: Intent 传递数据有大小限制吗？**

> **答案**：有，大约 1MB（因为 Binder 事务缓冲区限制）。传递大数据应该用：
> - 数据库/文件 + 传递 ID
> - ViewModel 共享
> - EventBus/LiveData
