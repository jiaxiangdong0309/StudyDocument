# Java 数据类型进阶篇（Android 视角）

> 基础篇解决的是“认识数据类型”，进阶篇要解决的是“在真实工程里怎么选、怎么避坑、为什么这个坑总在 Android 项目里反复出现”。

## 一、自动装箱 / 拆箱：方便，但不是免费午餐

很多人第一次接触装箱拆箱，会觉得这只是编译器帮忙做了点语法糖。

**错。它的代价在高频路径里非常真实。**

### 1.1 先看一个最常见的例子

```java
Integer total = 0;
for (int i = 0; i < 100000; i++) {
    total += i;
}
```

看起来很自然，但这里实际上发生了大量装箱和拆箱。

可以粗略理解成：

```java
Integer total = Integer.valueOf(0);
for (int i = 0; i < 100000; i++) {
    total = Integer.valueOf(total.intValue() + i);
}
```

问题就出来了：

- 每次循环都可能有拆箱
- 每次计算后都可能重新装箱
- 容易产生额外对象和方法调用成本

### 1.2 Android 热路径里尤其要小心

比如这些地方：

- `RecyclerView` 大列表数据处理
- `DiffUtil` 比较逻辑
- 图片索引、埋点统计、曝光计算
- 自定义 View 的测量和绘制
- 动画每帧计算

这些场景一旦频繁装箱，问题不是“会不会错”，而是“会不会慢”。

### 1.3 推荐写法

#### 计算过程尽量用基本类型

```kotlin
var total = 0
for (i in 0 until 100_000) {
    total += i
}
```

#### 只有在需要进入集合 / 泛型世界时才接受包装语义

```kotlin
val ids = mutableListOf<Int>()
ids.add(1)
ids.add(2)
```

### 1.4 一个工程化经验

**规则非常简单：内部计算用基本类型，结构承载时再接受包装类型。**

## 二、包装类型的 null 语义：表达能力强，但风险也大

### 2.1 基本类型不能表达“缺失”

比如用户年龄：

- `0` 岁是一种合法值吗？有时不是
- 如果后端没返回年龄，你拿什么表示？

这时候包装类型或可空类型就有意义了。

```kotlin
data class UserProfileDto(
    val age: Int?,
    val score: Long?,
    val vip: Boolean?
)
```

这比强行用：

```kotlin
val age: Int = 0
```

更真实，因为 `0` 不等于“没有值”。

### 2.2 Android 分层设计建议

在 Android 项目里，推荐把类型设计分层看：

| 层级 | 推荐做法 |
|---|---|
| 网络 DTO 层 | 允许可空，贴近后端真实返回 |
| 本地数据库映射层 | 根据表结构决定是否可空 |
| Domain 层 | 尽量收敛成稳定的非空模型 |
| UI 层 | 尽量直接使用“可渲染”的确定值 |

### 2.3 例子：从不稳定到稳定

```kotlin
data class UserDto(
    val id: Long?,
    val nickname: String?,
    val vip: Boolean?
)

data class UserUiModel(
    val id: Long,
    val nickname: String,
    val vip: Boolean
)

fun UserDto.toUiModel(): UserUiModel {
    return UserUiModel(
        id = id ?: 0L,
        nickname = nickname.orEmpty(),
        vip = vip ?: false
    )
}
```

这一步转换非常关键，它把“不确定世界”收敛成了“稳定世界”。

## 三、为什么 Android 推荐 `SparseArray` 而不是 `HashMap<Integer, T>`？

这本质上就是**数据类型 + 集合设计**共同作用的经典案例。

### 3.1 `HashMap<Integer, T>` 的问题

如果 key 是 `Integer`，就意味着：

- `int` 需要装箱成 `Integer`
- `HashMap` 节点本身也有对象开销
- 小数据量场景下，整体内存成本偏高

### 3.2 `SparseArray` 的思路

`SparseArray` 直接用两个数组管理：

- 一个存 key（`int[]`）
- 一个存 value（`Object[]`）

它避开了：

- `Integer` 装箱
- `HashMap.Node` 这种额外节点对象

### 3.3 适用场景

非常适合 Android 里的这些小中型映射：

- `position -> ViewHolder`
- `viewId -> listener`
- `tabId -> Fragment`
- `resourceId -> cache`

### 3.4 经验总结

| 场景 | 推荐 |
|---|---|
| 通用 Map，key 不是整数 | `HashMap` |
| key 是 `int`，数据量不大 | `SparseArray` |
| key 是 `long` | `LongSparseArray` |
| key 是对象，小数据量且重视内存 | `ArrayMap` |

这就是为什么“数据类型”不是孤立知识点，它会直接影响集合和性能选型。

## 四、数值范围与溢出：最容易写出“没报错但错了”的 bug

### 4.1 整数溢出不会自动报错

```java
int max = Integer.MAX_VALUE;
int next = max + 1;
System.out.println(next); // 变成负数
```

很多新手以为会异常，其实不会。

Java 的整数溢出默认就是按二进制截断处理。

### 4.2 Android 里最常见的溢出坑

#### 坑 1：时间戳转 int

```kotlin
val timestamp = System.currentTimeMillis()
val value = timestamp.toInt() // 高位直接丢失
```

这几乎一定有问题。

#### 坑 2：文件大小 / 流量统计

```kotlin
val totalSize: Int = 1024 * 1024 * 1024 * 3 // 可能早就溢出了
```

更稳妥的写法：

```kotlin
val totalSize = 1024L * 1024 * 1024 * 3
```

#### 坑 3：价格计算用浮点数

```kotlin
val total = 0.1 + 0.2
```

结果不是你想象中的“绝对精确”。

### 4.3 结论

- 大整数：优先 `long`
- 金额：优先 `BigDecimal` 或“分”为单位的整数
- 时间戳：永远 `long`
- 文件大小、下载进度总量：优先 `long`

## 五、浮点数为什么不适合做精确比较？

### 5.1 本质原因

`float` 和 `double` 用的是二进制浮点表示法，不是十进制精确表示。

所以很多十进制小数，底层并不能完全精确存储。

```java
double a = 0.1;
double b = 0.2;
System.out.println(a + b == 0.3); // false
```

### 5.2 Android 中的正确理解

#### UI 场景
UI 坐标、动画进度、缩放比例，用 `float` 很正常。

```kotlin
view.alpha = 0.5f
view.translationX = 12.5f
```

因为 UI 本来就允许一点误差。

#### 业务精度场景
金额、结算、积分换算等，不要依赖 `float` / `double` 做精确计算。

## 六、`String` 的高频坑：拼接、截取、常量池

### 6.1 为什么说 `String` 特殊？

它是引用类型，但用得像值类型；它是对象，却又被大量优化。

### 6.2 循环拼接字符串的坑

```java
String result = "";
for (int i = 0; i < 1000; i++) {
    result += i;
}
```

这会不断创建新字符串对象。

因为 `String` 不可变，每次拼接都不是“原地修改”，而是“生成新对象”。

### 6.3 推荐用 `StringBuilder`

```kotlin
val builder = StringBuilder()
for (i in 0 until 1000) {
    builder.append(i)
}
val result = builder.toString()
```

### 6.4 Android 里的典型应用

- 批量日志拼接
- SQL / 路由参数组装
- 富文本内容构建
- 大型埋点字段拼接

### 6.5 `StringBuffer` 和 `StringBuilder` 怎么选？

| 类型 | 线程安全 | 性能 | 场景 |
|---|---|---|---|
| `StringBuilder` | 否 | 更好 | 单线程、大多数 Android 业务代码 |
| `StringBuffer` | 是 | 较慢 | 老代码或确有多线程共享需求 |

**Android 里绝大部分情况下，选 `StringBuilder`。**

## 七、类型转换中的精度丢失问题

### 7.1 从大范围到小范围要特别谨慎

```java
long serverId = 9876543210L;
int localId = (int) serverId;
```

这里不是“变小一点”，而是可能直接变成完全错误的值。

### 7.2 Android 中最常见的几个坑

#### 坑 1：像素值取整

```kotlin
val px = (dp * density).toInt()
```

直接截断会偏小，有些场景应该用四舍五入：

```kotlin
val px = (dp * density + 0.5f).toInt()
```

#### 坑 2：进度百分比计算

```kotlin
val percent = current / total * 100
```

如果 `current` 和 `total` 都是整数，前面的除法可能已经丢精度了。

更合理的写法：

```kotlin
val percent = current * 100f / total
```

## 八、比较陷阱：包装类型、缓存、`==`

### 8.1 一个经典面试题

```java
Integer a = 127;
Integer b = 127;
System.out.println(a == b); // true

Integer c = 128;
Integer d = 128;
System.out.println(c == d); // false
```

为什么？

因为包装类型有缓存机制，`Integer.valueOf()` 会缓存一部分小整数对象。

### 8.2 但工程上更重要的结论是

**不要用 `==` 比较包装类型内容。**

应该用：

```java
Objects.equals(a, b)
```

或者先拆成基本类型再比较。

### Android 里的现实意义

比如：

- 接口返回状态码用 `Integer`
- 数据库存的字段可能是包装类型
- Java 工具层里你不小心写了 `==`

这样的问题很隐蔽，测试不一定能立刻测出来。

## 九、类型系统与 Android API 设计

很多 Android API，本质上就是在“数据类型约束”和“性能现实”之间做取舍。

### 9.1 `Bundle` 为什么有一堆 `putXxx()`？

比如：

- `putInt()`
- `putLong()`
- `putString()`
- `putParcelable()`

看起来有点啰嗦，但它背后是很强的类型意识：

- 不同类型要用不同序列化方式
- 不同类型有不同性能成本
- 取值时也要匹配相同类型

### 9.2 为什么 `Intent` extra 也这么设计？

因为跨组件传递数据时，类型如果不明确，运行时错误成本很高。

### 9.3 为什么 `SparseBooleanArray`、`SparseIntArray` 存在？

因为 Android 工程师非常在意：

- 基本类型数组的空间效率
- 避免无意义装箱
- 移动端内存比服务端更宝贵

## 十、性能优化角度的数据类型选择建议

### 10.1 高频循环

- 用基本类型
- 少装箱
- 少创建临时对象

### 10.2 数据模型

- DTO 层允许可空
- Domain / UI 模型尽量非空、稳定

### 10.3 字符串处理

- 高频拼接用 `StringBuilder`
- key 值尽量稳定统一

### 10.4 大数值

- 时间戳、文件大小、数据库主键：`long`
- 金额：`BigDecimal` 或整型分单位

### 10.5 集合键值

- `int -> object`：优先考虑 `SparseArray`
- `long -> object`：优先考虑 `LongSparseArray`
- 小数据量对象映射：可考虑 `ArrayMap`

## 十一、本篇小结

这篇真正想让你记住的不是语法，而是这几个工程认知：

1. 自动装箱/拆箱方便，但在热路径里有真实代价
2. 包装类型最大的价值，是表达“对象语义”和“空值语义”
3. 时间戳、文件大小、数据库 id 不要轻易用 `int`
4. `float` / `double` 适合 UI，不适合精确金额
5. 字符串高频拼接必须警惕对象创建成本
6. Android 的很多 API 设计，本质上都建立在对数据类型代价的深刻理解上

## 面试题（进阶篇）

### 1. 自动装箱 / 拆箱为什么会影响性能？
**结论**：因为它会引入额外的方法调用、对象语义，某些场景下还会带来 GC 压力。

**原理**：装箱本质上会调用如 `Integer.valueOf()`，拆箱会调用如 `intValue()`；如果发生在高频循环中，成本会被放大。

**Android 例子**：在列表滚动、曝光计算、自定义 View 绘制等热路径中，频繁装箱会加重主线程负担。

### 2. 为什么 Android 推荐 `SparseArray` 替代 `HashMap<Integer, T>`？
**结论**：因为它更省内存，也避免了 `Integer` 装箱成本。

**原理**：`SparseArray` 底层主要基于数组存储 key 和 value，不需要像 `HashMap` 那样维护额外节点对象。

**Android 例子**：`viewId -> listener`、`position -> ViewHolder` 这类小数据量映射，用 `SparseArray` 更合适。

### 3. 为什么金额计算不建议用 `double`？
**结论**：因为浮点数无法精确表示很多十进制小数。

**原理**：`double` 采用二进制浮点表示，像 `0.1` 这样的数在底层往往只能近似存储。

**Android 例子**：电商 App 价格、优惠券结算、积分换算若直接用 `double`，可能导致展示和结算不一致。

### 4. `StringBuilder` 和 `String` 拼接的核心差别是什么？
**结论**：`String` 拼接会不断产生新对象，`StringBuilder` 更适合高频拼接。

**原理**：`String` 不可变，每次拼接都要生成新字符串；`StringBuilder` 基于可变字符数组追加内容。

**Android 例子**：日志批量组装、埋点参数串联、富文本构建时优先用 `StringBuilder`。

### 5. DTO 层为什么更适合可空类型，而 UI 层尽量非空？
**结论**：因为 DTO 面对的是不稳定外部世界，UI 面对的是稳定渲染世界。

**原理**：网络接口字段可能缺失、类型不稳、值为空；但 UI 层如果还保留大量可空，就会到处写判空，增加复杂度。

**Android 例子**：`UserDto` 可空，经过 mapper 转成 `UserUiModel` 后尽量变成非空字段，界面代码会更稳定。
