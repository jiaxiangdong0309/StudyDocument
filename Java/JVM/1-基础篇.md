# JVM 基础篇（Android 视角）

> 作为 Android 开发者，理解 JVM 不是为了背八股，而是为了搞懂 ART 虚拟机、优化 App 内存、排查 OOM 问题。

## 一、为什么 Android 开发者要学 JVM？

### 1.1 JVM 与 Android 的关系

```
┌─────────────────────────────────────────────────────────────────────────┐
│                        JVM 与 Android 虚拟机的演进                        │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  桌面端/服务端：                                                          │
│  ┌─────────┐          ┌─────────┐          ┌─────────────┐             │
│  │  .java  │ ──javac─▶ │  .class │ ──JVM──▶ │ Windows/Mac │             │
│  └─────────┘          └─────────┘          └─────────────┘             │
│                                                                         │
│  Android 端：                                                            │
│  ┌─────────┐          ┌─────────┐          ┌─────────┐                 │
│  │  .java  │ ──javac─▶ │  .class │ ──d8───▶ │  .dex   │                │
│  │ .kt     │          └─────────┘          └────┬────┘                 │
│  └─────────┘                                    │                       │
│                                                 ▼                       │
│                              ┌─────────────────────────────────┐       │
│                              │   Dalvik (Android 4.4 之前)      │       │
│                              │   ART (Android 5.0+，现在用这个)  │       │
│                              └─────────────────────────────────┘       │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**关键认知**：Android 不用标准 JVM，而是用自己的虚拟机（ART），但**内存模型、GC 原理、类加载机制**基本相同。学懂 JVM，就能理解 ART。

### 1.2 学 JVM 对 Android 开发有什么用？

| JVM 知识点 | Android 应用场景 | 能解决什么问题 |
|-----------|-----------------|---------------|
| 内存结构 | App 内存优化 | 理解 Android Profiler 中的 Java Heap |
| GC 原理 | 卡顿优化 | 知道 GC 为什么会导致掉帧，如何避免 |
| 类加载 | 插件化、热修复 | 理解 Tinker、RePlugin 的实现原理 |
| 对象创建 | 对象池优化 | 为什么 RecyclerView 要复用 ViewHolder |
| 引用类型 | 内存泄漏排查 | WeakReference 在图片缓存中的应用 |

### 1.3 JVM vs Dalvik vs ART 对比

| 特性 | JVM (HotSpot) | Dalvik | ART |
|-----|---------------|--------|-----|
| **字节码格式** | .class | .dex | .dex |
| **执行方式** | 解释 + JIT | 解释 + JIT | AOT + JIT |
| **编译时机** | 运行时即时编译 | 运行时即时编译 | 安装时预编译 + 运行时优化 |
| **GC 算法** | 分代收集 | 标记清除 | 并发复制/标记压缩 |
| **内存占用** | 较高 | 较低 | 中等（空间换时间） |
| **启动速度** | 慢（需预热） | 较慢 | 快（AOT 预编译） |
| **Android 版本** | - | 2.2 ~ 4.4 | 5.0+ |

**通俗理解**：
- **JVM**：像边看菜谱边做饭，每次都要翻菜谱（JIT 即时编译）
- **Dalvik**：同上，但菜谱更简洁（dex 格式更紧凑）
- **ART**：安装 App 时就把菜谱背熟了（AOT 预编译），做饭时不用再翻

## 二、JVM 内存结构（重点！）

> 这是 Android 内存优化的理论基础。搞懂这个，Android Profiler 的数据你就能看懂了。

### 2.1 先看一段 Android 代码

```kotlin
class UserRepository(
    private val api: ApiService,  // 成员变量
    private val db: UserDao       // 成员变量
) {
    companion object {
        // 静态变量：整个 App 生命周期只有一份
        private const val CACHE_SIZE = 100
        private val cache = LruCache<String, User>(CACHE_SIZE)
    }
    
    suspend fun getUser(id: String): User {
        // 局部变量：函数执行完就销毁
        val cached = cache.get(id)
        if (cached != null) return cached
        
        return withContext(Dispatchers.IO) {
            val user = api.fetchUser(id)  // user 是局部变量
            cache.put(id, user)
            user
        }
    }
}
```

**问题来了**：
- `api`、`db` 这些成员变量存在哪？
- `CACHE_SIZE`、`cache` 这些静态变量存在哪？
- `cached`、`user` 这些局部变量存在哪？
- `UserRepository` 的实例对象存在哪？

### 2.3 变量到底存在哪？（Android 版）

| 变量类型 | 代码示例 | 存储位置 | Android 关联 |
|---------|---------|---------|-------------|
| **局部变量** | `val user = User()` | 栈（引用在栈，对象在堆） | 方法执行完自动释放，不会泄漏 |
| **成员变量** | `private val adapter: Adapter` | 堆（跟着对象走） | Activity 的成员变量跟 Activity 生命周期 |
| **静态变量** | `companion object { val instance }` | 方法区 | 生命周期=进程，用不好会泄漏 |

```kotlin
class MainActivity : AppCompatActivity() {
    
    // ❌ 危险！静态持有 Activity 引用 = 内存泄漏
    companion object {
        // 这个引用在方法区，生命周期 = 进程
        // 如果存了 Activity 引用，Activity 销毁后依然无法回收
        var leakedActivity: MainActivity? = null
    }
    
    // ✅ 成员变量，跟 Activity 生命周期一致
    private lateinit var binding: ActivityMainBinding
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        
        // ✅ 局部变量，onCreate 执行完就销毁
        val tempData = loadInitialData()
        
        // ❌ 千万别这样！
        // leakedActivity = this
    }
}
```

### 2.4 Android Profiler 中的内存分类

打开 Android Studio → Profiler → Memory，你会看到：

| Profiler 显示 | 对应 JVM 区域 | 说明 |
|--------------|--------------|------|
| **Java** | 堆（Heap） | Java/Kotlin 对象，你写的大部分代码创建的对象 |
| **Native** | 本地内存 | Bitmap 像素、OpenGL 纹理、NDK 分配的内存 |
| **Graphics** | GPU 内存 | 图形缓冲区 |
| **Stack** | 虚拟机栈 | 线程栈空间 |
| **Code** | 方法区 | dex 代码、JIT 编译后的代码 |

**实战经验**：
- Java 内存高 → 检查是否创建了大量对象，或者有内存泄漏
- Native 内存高 → 检查 Bitmap 是否及时回收，NDK 内存管理
- 两者都高 → 可能是 Bitmap 没有正确配置（inBitmap 复用）

### 3.3 Android 中的对象创建优化

**问题**：频繁创建对象 → 频繁 GC → 主线程卡顿（GC 时 STW）

**优化思路**：对象复用

```kotlin
// ❌ 每次滚动都创建新 ViewHolder = 频繁 GC
class BadAdapter : RecyclerView.Adapter<ViewHolder>() {
    override fun onBindViewHolder(holder: ViewHolder, position: Int) {
        // 如果每次都 new，就糟糕了
    }
}

// ✅ RecyclerView 的 ViewHolder 复用机制
// ViewHolder 创建一次，后续只是更新数据
class GoodAdapter : RecyclerView.Adapter<ViewHolder>() {
    override fun onCreateViewHolder(parent: ViewGroup, viewType: Int): ViewHolder {
        // 只在需要时创建，之后会被复用
        return ViewHolder(...)
    }
    
    override fun onBindViewHolder(holder: ViewHolder, position: Int) {
        // 复用已有的 holder，只更新数据
        holder.bind(items[position])
    }
}
```

**常见的对象池模式**：

```kotlin
// Message 对象池：Handler 机制中的核心优化
val msg = Message.obtain()  // 从池中获取，而不是 new Message()
try {
    msg.what = MSG_UPDATE
    msg.obj = data
    handler.sendMessage(msg)
} finally {
    // msg.recycle() 由 Handler 内部调用，归还到池中
}

// Kotlin 协程中的对象复用
// CoroutineContext 的 Element 也是复用的
```

## 四、垃圾回收（GC）

> GC 导致的卡顿是 Android 性能优化的重要课题。

### 4.1 什么是垃圾？

**垃圾 = 没有任何引用链可达的对象**

```kotlin
class LeakDemo {
    fun createGarbage() {
        val user = User("张三")  // user 引用指向对象
        // 方法结束，user 出栈，对象变成垃圾
    }
    
    fun createLeak() {
        val handler = object : Handler(Looper.getMainLooper()) {
            override fun handleMessage(msg: Message) {
                // 匿名内部类持有外部类引用
                updateUI()
            }
        }
        handler.postDelayed({ }, 60_000)  // 1分钟后执行
        // 如果 Activity 在这 1 分钟内销毁，Handler 仍持有 Activity 引用
        // Activity 对象不是垃圾（还有引用），但已经不需要了 = 内存泄漏
    }
}
```

### 4.2 如何判断对象是垃圾？

| 方法 | 原理 | 问题 | 使用者 |
|-----|------|------|-------|
| **引用计数法** | 有引用 +1，失去引用 -1，为 0 即垃圾 | 循环引用无法处理 | Python、Swift（改进版） |
| **可达性分析** | 从 GC Roots 出发，不可达即垃圾 | 需要 STW 扫描 | JVM、ART |

**GC Roots 有哪些？**

```kotlin
// 1. 虚拟机栈中的引用（正在执行的方法的局部变量）
fun processData() {
    val list = mutableListOf<User>()  // list 是 GC Root
    // ...
}

// 2. 静态变量引用的对象
companion object {
    val instance = Singleton()  // instance 是 GC Root
}

// 3. JNI 引用
// Native 代码持有的 Java 对象引用

// 4. 同步锁持有的对象
synchronized(lockObject) {  // lockObject 是 GC Root
    // ...
}
```

### 4.3 GC 算法

| 算法 | 原理 | 优点 | 缺点 | 适用场景 |
|-----|------|------|------|---------|
| **标记-清除** | 标记垃圾，然后清除 | 简单 | 内存碎片 | 老年代 |
| **复制算法** | 存活对象复制到另一半，清空原区域 | 无碎片，速度快 | 浪费一半空间 | 年轻代 |
| **标记-整理** | 标记后，存活对象向一端移动 | 无碎片 | 移动成本高 | 老年代 |
| **分代收集** | 年轻代用复制，老年代用标记-整理 | 综合最优 | 实现复杂 | 现代 GC |

### 4.4 ART 的 GC 演进

```
┌──────────────────────────────────────────────────────────────────────────┐
│                         Android GC 演进史                                 │
├──────────────────────────────────────────────────────────────────────────┤
│                                                                          │
│  Dalvik 时代（Android 4.4 及之前）：                                       │
│  ├─ 采用 Stop-The-World（STW）方式                                        │
│  ├─ GC 时全部线程暂停，导致明显卡顿                                        │
│  └─ GC 耗时通常 50~100ms                                                 │
│                                                                          │
│  ART 初期（Android 5.0~6.0）：                                            │
│  ├─ 引入并发 GC（Concurrent GC）                                          │
│  ├─ 大部分 GC 工作与应用线程并发执行                                       │
│  └─ STW 时间降低到 5~10ms                                                │
│                                                                          │
│  ART 现代（Android 8.0+）：                                               │
│  ├─ 引入 Concurrent Copying GC                                           │
│  ├─ 支持压缩堆（Compacting），减少碎片                                     │
│  ├─ 引入 Generational GC（分代回收）                                      │
│  └─ STW 时间进一步降低到 2~3ms                                            │
│                                                                          │
│  Android 10+ 优化：                                                       │
│  ├─ GC 更加智能，根据设备状态调整策略                                      │
│  └─ 支持后台压缩，空闲时整理内存                                           │
│                                                                          │
└──────────────────────────────────────────────────────────────────────────┘
```

### 4.5 如何避免 GC 导致的卡顿？

**核心原则**：减少对象创建，特别是在 UI 线程和高频调用的地方。

```kotlin
// ❌ 错误：onDraw 中创建对象，每帧都触发
class BadView(context: Context) : View(context) {
    override fun onDraw(canvas: Canvas) {
        val paint = Paint()  // 每次 onDraw 都 new，16ms 画一帧，疯狂 GC
        val rect = RectF(0f, 0f, width.toFloat(), height.toFloat())
        canvas.drawRoundRect(rect, 10f, 10f, paint)
    }
}

// ✅ 正确：对象复用
class GoodView(context: Context) : View(context) {
    // 只创建一次，复用
    private val paint = Paint().apply {
        color = Color.BLUE
        style = Paint.Style.FILL
    }
    private val rect = RectF()
    
    override fun onDraw(canvas: Canvas) {
        rect.set(0f, 0f, width.toFloat(), height.toFloat())
        canvas.drawRoundRect(rect, 10f, 10f, paint)
    }
}
```

**RecyclerView 滚动时的 GC 优化**：

```kotlin
class OptimizedAdapter : RecyclerView.Adapter<ViewHolder>() {
    
    // ❌ 错误：每次 bind 都创建新的点击监听器
    override fun onBindViewHolder(holder: ViewHolder, position: Int) {
        holder.itemView.setOnClickListener {
            // 每次都 new OnClickListener
            onClick(position)
        }
    }
    
    // ✅ 正确：在 ViewHolder 中设置一次
    inner class ViewHolder(view: View) : RecyclerView.ViewHolder(view) {
        init {
            view.setOnClickListener {
                // 使用 adapterPosition 而不是闭包捕获
                onClick(adapterPosition)
            }
        }
    }
}
```

## 五、类加载机制

> 理解类加载，才能理解插件化、热修复的实现原理。

### 5.1 类加载过程

```
加载 → 验证 → 准备 → 解析 → 初始化
 │      │      │      │      │
 │      │      │      │      └─ 执行 <clinit>（静态代码块、静态变量赋值）
 │      │      │      └─ 符号引用 → 直接引用
 │      │      └─ 为静态变量分配内存，设零值
 │      └─ 验证字节码格式合法
 └─ 读取 .class/.dex 文件到内存
```

**Android 中的类加载时机**：

```kotlin
class MyClass {
    companion object {
        // 类加载时执行（准备阶段设零值，初始化阶段赋值）
        val config = loadConfig()  // 初始化阶段才调用
        
        init {
            Log.d("MyClass", "类被加载了")  // 初始化阶段执行
        }
    }
}

// 什么时候触发类加载？
// 1. 创建实例：val obj = MyClass()
// 2. 访问静态成员：MyClass.config
// 3. 反射：Class.forName("MyClass")
```

### 5.3 热修复原理简述

```kotlin
// 热修复的核心思路：利用双亲委派的"漏洞"
// 让修复后的类优先于有 Bug 的类被加载

// 简化版原理示意
class HotFixManager {
    fun loadPatch(patchDexPath: String) {
        // 1. 获取 App 的 PathClassLoader
        val appClassLoader = context.classLoader
        
        // 2. 通过反射获取 DexPathList
        val pathListField = findField(appClassLoader, "pathList")
        val pathList = pathListField.get(appClassLoader)
        
        // 3. 获取 dexElements 数组
        val dexElementsField = findField(pathList, "dexElements")

        val patchClassLoader = DexClassLoader(patchDexPath, ...)
```

## 六、常见内存问题

### 6.1 StackOverflowError（栈溢出）

**原因**：递归太深或方法调用链太长，栈空间耗尽。

```kotlin
// ❌ 典型错误：无限递归
fun badRecursion(): Int {
    return badRecursion()  // 每次调用都创建栈帧，直到栈满
}

// ✅ 正确：有终止条件
fun factorial(n: Int): Int {
    if (n <= 1) return 1  // 终止条件
    return n * factorial(n - 1)
}

// ✅ 更好：用尾递归优化（Kotlin 支持）
tailrec fun factorialTailRec(n: Int, acc: Int = 1): Int {
    if (n <= 1) return acc
    return factorialTailRec(n - 1, n * acc)  // 编译器优化为循环，不会栈溢出
}
```

### 6.2 OutOfMemoryError（堆溢出）

**原因**：堆内存不足，可能是对象太多或内存泄漏。

```kotlin
// Android 中最常见的 OOM 场景：Bitmap

// ❌ 错误：直接加载大图
fun loadBigImage(path: String): Bitmap {
    return BitmapFactory.decodeFile(path)  // 4000x3000 的图 = 48MB 内存
}

// ✅ 正确：采样加载
fun loadBigImageOptimized(path: String, reqWidth: Int, reqHeight: Int): Bitmap {
    // 1. 先获取图片尺寸，不加载到内存
    val options = BitmapFactory.Options().apply {
        inJustDecodeBounds = true
    }
    BitmapFactory.decodeFile(path, options)
    
    // 2. 计算采样率
    options.inSampleSize = calculateInSampleSize(options, reqWidth, reqHeight)
    
    // 3. 真正加载（缩小后的图）
    options.inJustDecodeBounds = false
    return BitmapFactory.decodeFile(path, options)
}

private fun calculateInSampleSize(
    options: BitmapFactory.Options,
    reqWidth: Int,
    reqHeight: Int
): Int {
    val (width, height) = options.outWidth to options.outHeight
    var inSampleSize = 1
    
    if (height > reqHeight || width > reqWidth) {
        val halfHeight = height / 2
        val halfWidth = width / 2
        while (halfHeight / inSampleSize >= reqHeight && 
               halfWidth / inSampleSize >= reqWidth) {
            inSampleSize *= 2
        }
    }
    return inSampleSize
}
```

### 6.3 内存泄漏排查

**常见泄漏场景与解决方案**：

| 泄漏场景 | 原因 | 解决方案 |
|---------|------|---------|
| 静态持有 Activity | 静态变量生命周期 = 进程 | 使用 WeakReference 或 ApplicationContext |
| Handler 内存泄漏 | 匿名内部类持有外部引用 | 静态内部类 + WeakReference，或使用 lifecycleScope |
| 单例持有 Context | 单例长期持有 Activity Context | 使用 ApplicationContext |
| 监听器未注销 | 注册后忘记注销 | 在 onDestroy 中注销，或使用 lifecycle 组件 |
| 集合只增不减 | 添加后从不移除 | 适时清理，或使用 WeakHashMap |

```kotlin
// ❌ Handler 内存泄漏
class LeakyActivity : AppCompatActivity() {
    private val handler = object : Handler(Looper.getMainLooper()) {
        override fun handleMessage(msg: Message) {
            // 匿名内部类隐式持有 LeakyActivity.this
            doSomething()
        }
    }
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        handler.postDelayed({ }, 60_000)  // 延迟 1 分钟，期间 Activity 无法回收
    }
}

// ✅ 使用 lifecycleScope（推荐）
class SafeActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        
        lifecycleScope.launch {
            delay(60_000)  // 如果 Activity 销毁，协程自动取消
            doSomething()
        }
    }
}

// ✅ 或者使用静态内部类 + WeakReference
class SafeActivity2 : AppCompatActivity() {
    private val handler = SafeHandler(this)
    
    private class SafeHandler(activity: SafeActivity2) : Handler(Looper.getMainLooper()) {
        private val activityRef = WeakReference(activity)
        
        override fun handleMessage(msg: Message) {
            activityRef.get()?.doSomething()  // Activity 可能已被回收
        }
    }
}
```
