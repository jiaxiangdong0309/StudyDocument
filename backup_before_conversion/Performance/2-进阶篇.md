## 一、虚拟列表（Virtual List）

### 为什么长列表会卡？

一次渲染成千上万个 DOM 节点会带来：
- **首屏慢**：创建大量 DOM、执行大量组件渲染
- **滚动卡顿**：重排、重绘、事件处理负担大
- **内存占用高**：大量节点常驻内存

### 什么是虚拟列表？

**虚拟列表**只渲染「当前可见区域」的列表项，随着滚动动态替换内容，DOM 数量保持在一屏左右，列表再长也只渲染可见部分。

```mermaid
graph LR
    A[10000 条数据] --> B[只渲染可见的 ~20 条]
    B --> C[滚动时更新可见项]
```

### 如何使用：react-window

常用库：**react-window**（轻量）、**react-virtualized**（功能更多）。

#### 1. 安装

```bash
npm install react-window
```

#### 2. 固定高度列表

```typescript
import { FixedSizeList as List } from 'react-window'

interface User {
  id: string
  name: string
}

function UserList({ users }: { users: User[] }) {
  const Row = ({ index, style }: { index: number; style: React.CSSProperties }) => (
    <div style={style}>
      {users[index].name}
    </div>
  )

  return (
    <List
      height={400}
      itemCount={users.length}
      itemSize={40}
      width="100%"
    >
      {Row}
    </List>
  )
}
```

- **height**：可视区域高度
- **itemCount**：总条数
- **itemSize**：每行高度（固定时）
- **Row**：每行渲染函数，接收 `index` 和 `style`（必须套在根元素上定位）

#### 3. 不定高：VariableSizeList

每行高度不固定时用 `VariableSizeList`，并实现 `itemSize: (index) => number`。

### 适用场景

- 列表**几千、几万条**以上
- 每条结构简单、高度可算（固定或可测量）
- 需要**流畅滚动**、控制 DOM 数量

### 注意事项

- 虚拟列表依赖**可见区域和滚动位置**，需要固定或可计算的 item 高度（或提供 getItemSize）
- 若列表项高度差异很大，可用 `VariableSizeList` 或先估算再测量

## 二、代码分割与 React.lazy

### 为什么需要代码分割？

单页应用默认会把所有路由、组件的代码打成一个 bundle，首屏要下载全部代码才能渲染，导致：
- **首屏慢**：体积大、解析执行时间长
- **浪费流量**：用户可能只访问少数几个页面

**代码分割**把应用拆成多个 chunk，按需加载：访问某路由或某组件时再加载对应 JS。

### React.lazy：懒加载组件

`React.lazy` 接收一个**动态 import**，返回一个「懒加载组件」：只有真正渲染时才去加载对应 chunk。

```typescript
import { lazy, Suspense } from 'react'

// 懒加载：只有渲染到 Dashboard 时才加载这段代码
const Dashboard = lazy(() => import('./Dashboard'))
const Settings = lazy(() => import('./Settings'))
```

### Suspense：加载中的占位

懒加载组件在加载完成前需要占位 UI，用 **Suspense** 包住，并设置 `fallback`：

```typescript
import { lazy, Suspense } from 'react'

const Dashboard = lazy(() => import('./Dashboard'))

function App() {
  return (
    <Suspense fallback={<div>加载中...</div>}>
      <Dashboard />
    </Suspense>
  )
}
```

### 按路由分割（常见用法）

```typescript
import { lazy, Suspense } from 'react'
import { BrowserRouter, Routes, Route } from 'react-router-dom'

const Home = lazy(() => import('./pages/Home'))
const UserList = lazy(() => import('./pages/UserList'))
const UserDetail = lazy(() => import('./pages/UserDetail'))

function App() {
  return (
    <BrowserRouter>
      <Suspense fallback={<PageLoading />}>
        <Routes>
          <Route path="/" element={<Home />} />
          <Route path="/users" element={<UserList />} />
          <Route path="/users/:id" element={<UserDetail />} />
        </Routes>
      </Suspense>
    </BrowserRouter>
  )
}
```

这样每个路由对应一个 chunk，进入该路由时才加载对应 JS。

### 适用场景

- **按路由拆分**：每个页面一个 chunk，首屏只加载当前页
- **大组件/弹窗**：很少用到的弹窗、复杂图表等用 lazy，用到再加载
- **首屏 bundle 过大**：用懒加载把非首屏部分拆出去

### 注意事项

- `React.lazy` 只支持**默认导出**：`import('./X')` 的模块必须是 `export default Component`
- 若用命名导出，可包一层：`lazy(() => import('./X').then(m => ({ default: m.Named })))`
- Suspense 的 `fallback` 要有，否则加载期间可能空白或报错

## 三、useTransition：低优先级更新

### 解决什么问题？

某些更新**计算量大**（如大列表过滤、复杂搜索），会阻塞主线程，导致输入卡顿、点击无响应。
**useTransition** 把这类更新标记为「可中断的低优先级更新」，让输入、点击等**高优先级更新**先执行，保持界面响应。

### 基本用法

```typescript
import { useTransition, useState } from 'react'

function SearchResults() {
  const [query, setQuery] = useState('')
  const [isPending, startTransition] = useTransition()

  const handleChange = (e: React.ChangeEvent<HTMLInputElement>) => {
    const value = e.target.value
    // 输入框立即更新（高优先级）
    setQuery(value)
    // 把「根据 query 过滤大列表」放到低优先级
    startTransition(() => {
      setSearchQuery(value)
    })
  }

  return (
    <>
      <input value={query} onChange={handleChange} />
      {isPending ? <Spinner /> : null}
      <BigList searchQuery={searchQuery} />
    </BigList>
  )
}
```

- **startTransition(callback)**：在 callback 里做的 setState 会被标记为**过渡更新**（低优先级），可被中断、延后。
- **isPending**：是否有未完成的过渡更新，可用来显示「加载中」等 UI。

### 典型场景

- **大列表过滤/搜索**：输入先更新，过滤结果延后计算和渲染
- **标签/筛选项切换**：切换先响应，结果列表再更新
- **复杂表格/图表**：先响应用户操作，再更新重计算部分

### 与防抖/节流的区别

- **防抖/节流**：少执行几次逻辑，仍然可能在某次执行时卡住主线程
- **useTransition**：不减少执行次数，但把重活放到低优先级，不阻塞输入和点击

## 四、性能优化策略小结

| 场景 | 手段 | 说明 |
|------|------|------|
| 父渲染导致子无效渲染 | React.memo + useMemo/useCallback | 稳定 props 引用，浅比较生效 |
| 重计算、大列表过滤 | useMemo | 依赖不变复用结果 |
| 长列表（成千上万条） | 虚拟列表（react-window） | 只渲染可见区域 |
| 首屏 bundle 大、路由多 | React.lazy + Suspense | 按路由/组件懒加载 |
| 大计算阻塞输入/点击 | useTransition | 低优先级更新，保持响应 |

## 五、常见问题

| 问题 | 原因 | 解决 |
|------|------|------|
| 虚拟列表空白或错位 | 高度不对、itemSize 与真实高度不一致 | 固定高度或正确实现 getItemSize |
| lazy 组件报错或白屏 | 模块没有 default 导出、加载失败 | 确保 default 导出，或 .then 包装；Suspense fallback 要有 |
| useTransition 没感觉 | 更新本身很快，或没有重计算 | 用在真正耗时的更新上（如大列表过滤） |
| 过度优化 | 简单列表、小 bundle 也上虚拟列表/lazy | 先保证正确，有卡顿/体积问题再优化 |

## 六、实用检验（自测）

1. **长列表卡顿怎么优化？**
   用虚拟列表（如 react-window），只渲染可见区域，DOM 数量保持在一屏左右。

2. **首屏 JS 体积太大怎么办？**
   用 React.lazy 按路由或大组件拆 chunk，Suspense 包一层并设置 fallback，进入对应路由或组件时再加载。

3. **useTransition 解决什么问题？**
   把耗时更新（如大列表过滤）标记为低优先级，不阻塞输入和点击，保持界面响应；isPending 可用来显示加载状态。

4. **虚拟列表和普通列表的区别？**
   普通列表有多少条就渲染多少 DOM；虚拟列表只渲染可见区域的那几条，滚动时再更新，DOM 数量恒定在一屏左右。

5. **React.lazy 的模块必须怎么导出？**
   必须**默认导出**（export default），否则要用 .then 包装成 { default: Component }。
