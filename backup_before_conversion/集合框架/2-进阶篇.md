# 集合框架进阶篇

> **目标**：深入理解 Android 优化集合，掌握性能优化技巧，在实际开发中做出正确的集合选择。

## 一、为什么 Android 要"重新发明"集合？

### 背景：手机内存的"斤斤计较"

想象一下，你在 PC 上有 16GB 内存，用 HashMap 存 1000 个数据，多占几百 KB 内存，你根本不会在意。

但在手机上：
- 早期 Android 设备只有 **256MB ~ 512MB** 内存
- 每个 App 分到的堆内存只有 **16MB ~ 64MB**
- 系统会杀掉内存大户来回收资源

所以 Google 工程师必须"斤斤计较"每一个字节：

```
HashMap 的问题：
┌─────────────────────────────────────────────────────────┐
│  HashMap.Entry 对象                                      │
│  ├── hash (int, 4 bytes)                                │
│  ├── key (Object reference, 4-8 bytes)                  │
│  ├── value (Object reference, 4-8 bytes)                │
│  ├── next (Object reference, 4-8 bytes)                 │
│  └── Object header (8-12 bytes)                         │
│                                                         │
│  每存一个键值对，光 Entry 对象就要 32-48 bytes！          │
│  还没算 key 和 value 本身的大小                          │
└─────────────────────────────────────────────────────────┘

ArrayMap 的优化：
┌─────────────────────────────────────────────────────────┐
│  不需要 Entry 对象！                                     │
│                                                         │
│  mHashes: [hash0, hash1, hash2, ...]  // int 数组       │
│  mArray:  [key0, val0, key1, val1, ...] // Object 数组  │
│                                                         │
│  省掉了 Entry 对象的开销，内存占用减少约 30%              │
└─────────────────────────────────────────────────────────┘
```

## 二、ArrayMap 深度解析

### 2.1 ArrayMap vs HashMap 结构对比

```
HashMap 内部结构：
┌───────────────────────────────────────────────────────────┐
│  table[] 数组（桶）                                        │
│  ┌─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┐        │
│  │null │Entry│null │Entry│null │null │Entry│null │        │
│  └──┬──┴──┬──┴─────┴──┬──┴─────┴─────┴──┬──┴─────┘        │
│     │     │           │                 │                 │
│     │     ▼           ▼                 ▼                 │
│     │  ┌─────┐     ┌─────┐           ┌─────┐              │
│     │  │Entry│────▶│Entry│           │Entry│              │
│     │  └─────┘     └─────┘           └─────┘              │
│     ▼                                                     │
│  ┌─────┐                                                  │
│  │Entry│  每个 Entry 都是独立对象，有对象头开销             │
│  └─────┘                                                  │
└───────────────────────────────────────────────────────────┘

ArrayMap 内部结构：
┌───────────────────────────────────────────────────────────┐
│  mHashes[] - 存储 hash 值（已排序）                        │
│  ┌─────┬─────┬─────┬─────┬─────┐                          │
│  │ 102 │ 305 │ 518 │ 721 │ 933 │   ← 有序，可二分查找      │
│  └─────┴─────┴─────┴─────┴─────┘                          │
│                                                           │
│  mArray[] - 交替存储 key 和 value                          │
│  ┌─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┬───┬───┐│
│  │key0 │val0 │key1 │val1 │key2 │val2 │key3 │val3 │...│...││
│  └─────┴─────┴─────┴─────┴─────┴─────┴─────┴─────┴───┴───┘│
│                                                           │
│  没有 Entry 对象！两个数组搞定一切                          │
└───────────────────────────────────────────────────────────┘
```

### 2.2 查找性能对比

```kotlin
// ArrayMap 的查找过程
class ArrayMapLookup {
    
    /**
     * ArrayMap 查找流程：
     * 1. 计算 key 的 hash 值
     * 2. 在 mHashes 数组中二分查找 hash 值的位置
     * 3. 根据位置在 mArray 中取出 key 和 value
     * 
     * 时间复杂度：O(log n) 二分查找
     */
    fun <V> simulateArrayMapGet(
        mHashes: IntArray,
        mArray: Array<Any?>,
        key: String
    ): V? {
        val hash = key.hashCode()
        
        // 二分查找 hash 值
        val index = mHashes.binarySearch(hash)
        if (index < 0) return null
        
        // 从 mArray 中取值（key 在 index*2，value 在 index*2+1）
        @Suppress("UNCHECKED_CAST")
        return mArray[index * 2 + 1] as? V
    }
}
```

### 2.3 什么时候用 ArrayMap？

| 数据量 | 推荐集合 | 原因 |
|-------|---------|------|
| < 100 | ArrayMap | 内存省 30%，查找差异可忽略 |
| 100 ~ 1000 | ArrayMap | 综合来看 ArrayMap 更优 |
| > 1000 | HashMap | 二分查找开始变慢，HashMap 更快 |
| 超大数据量 | HashMap | HashMap O(1) 完胜 |

## 三、SparseArray 家族详解

### 3.1 为什么需要 SparseArray？

```kotlin
// 问题：用 HashMap<Integer, User> 存储用户

// Java 的自动装箱：
val userId: Int = 10086
val map = HashMap<Int, User>()  // Kotlin 会自动装箱成 Integer

// 背后发生了什么？
// 1. Int 10086 被装箱成 Integer 对象
// 2. Integer 对象有对象头开销（8-12 bytes）
// 3. 每次 put/get 都要装箱/拆箱

// 如果存 1000 个用户：
// - 1000 个 Integer 对象 × 16 bytes ≈ 16KB
// - 1000 个 Entry 对象 × 32 bytes ≈ 32KB
// - 总计额外开销：约 48KB！
```

**SparseArray 的解决方案**：

```kotlin
// SparseArray：直接用 int 作为 key，无需装箱
val sparseArray = SparseArray<User>()

// 内部结构：
// mKeys: [int, int, int, ...]     ← 原始 int 数组，无装箱
// mValues: [User, User, User, ...] ← Object 数组

sparseArray.put(10086, user)  // key 直接存 int，不创建 Integer 对象
val user = sparseArray.get(10086)  // 返回时也不需要拆箱
```

### 3.2 SparseArray 家族成员

| 类名 | 键类型 | 值类型 | 使用场景 |
|-----|-------|-------|---------|
| SparseArray<T> | int | Object | ID → 数据对象 |
| SparseBooleanArray | int | boolean | ID → 是否选中 |
| SparseIntArray | int | int | ID → 数量/计数 |
| SparseLongArray | int | long | ID → 时间戳 |
| LongSparseArray<T> | long | Object | 长整型 ID → 数据对象 |

```kotlin
class MessageReadStateManager {
    
    // ✅ 用 LongSparseArray 存储消息已读时间
    // key 是 messageId（long），value 是已读时间戳
    private val readTimestamps = LongSparseArray<Long>()

    }
    
    fun isRead(messageId: Long): Boolean {
        return readTimestamps.indexOfKey(messageId) >= 0
    }
    
    fun getReadTime(messageId: Long): Long? {
        val index = readTimestamps.indexOfKey(messageId)
        return if (index >= 0) readTimestamps.valueAt(index) else null
    }
    
    // 清理 7 天前的已读记录
    fun cleanOldRecords() {
        val threshold = System.currentTimeMillis() - 7 * 24 * 60 * 60 * 1000L
        val keysToRemove = mutableListOf<Long>()
        
        for (i in 0 until readTimestamps.size()) {
            if (readTimestamps.valueAt(i) < threshold) {
                keysToRemove.add(readTimestamps.keyAt(i))
            }
        }
        
        keysToRemove.forEach { readTimestamps.remove(it) }
    }
```

## 四、并发集合与线程安全

### 4.1 常见的线程安全问题

```kotlin
// ❌ 错误：多线程操作非线程安全集合
class UserCacheWrong {
    // HashMap 不是线程安全的！
    private val cache = HashMap<String, User>()
    
    // 在 IO 线程更新缓存
    fun updateFromNetwork() {
        CoroutineScope(Dispatchers.IO).launch {
            val users = api.fetchUsers()
            users.forEach { user ->
                cache[user.id] = user  // 💥 多线程写入，可能导致数据丢失或死循环！
            }
        }
    }
    
    // 在主线程读取缓存
    fun getUser(id: String): User? {
        return cache[id]  // 💥 与写入线程并发，可能读到不一致的数据
    }
}
```

**为什么 HashMap 不是线程安全的？**

```
问题1：死循环（JDK 7 及之前）
HashMap 扩容时需要 rehash，如果两个线程同时触发扩容，
链表可能形成环，导致 get() 时无限循环。

问题2：数据丢失
两个线程同时 put 到同一个桶，只有一个会成功。

问题3：读到脏数据
一个线程在写，另一个线程在读，可能读到中间状态。
```

### 4.2 线程安全的解决方案

**方案1：使用 ConcurrentHashMap**

```kotlin
// ✅ 正确：使用 ConcurrentHashMap
class UserCacheCorrect {
    // ConcurrentHashMap 是线程安全的
    private val cache = ConcurrentHashMap<String, User>()
    
    fun updateFromNetwork() {
        CoroutineScope(Dispatchers.IO).launch {
            val users = api.fetchUsers()
            users.forEach { user ->
                cache[user.id] = user  // ✅ 线程安全
            }
        }
    }
    
    fun getUser(id: String): User? {
        return cache[id]  // ✅ 线程安全
    }
    
    // ConcurrentHashMap 的原子操作
    fun getOrFetch(id: String): User {
        return cache.getOrPut(id) {
            // 如果不存在，执行这个 lambda 并存入
            api.fetchUser(id)
        }
    }
}
```

**方案2：使用同步包装器**


**方案3：使用协程 + 单线程限制**

```kotlin
// ✅ Android 推荐方式：用协程限制在单线程操作
class UserRepository {
    
    // 普通 HashMap，但只在 IO 调度器的单线程中操作
    private val cache = HashMap<String, User>()
    
    // 使用 Mutex 保证同一时间只有一个协程访问
    private val mutex = Mutex()
    
    suspend fun getUser(id: String): User? = mutex.withLock {
        cache[id]
    }
    
    suspend fun cacheUser(user: User) = mutex.withLock {
        cache[user.id] = user
    }
    
    // 或者用 newSingleThreadContext 限制在单线程
    private val cacheDispatcher = newSingleThreadContext("cache-thread")
    
    suspend fun getUserSingleThread(id: String): User? = withContext(cacheDispatcher) {
        cache[id]  // 只在单线程中执行，无需同步
    }
}
```

### 4.3 ConcurrentHashMap vs Collections.synchronizedMap

| 特性 | ConcurrentHashMap | synchronizedMap |
|-----|-------------------|-----------------|
| 锁粒度 | 分段锁/CAS（细粒度） | 整个 Map 一把锁（粗粒度） |
| 并发读 | 不阻塞 | 会阻塞 |
| 并发写 | 不同段可并发 | 完全串行 |
| 遍历 | 弱一致性，不抛异常 | 需手动同步，否则抛异常 |
| 性能 | 高并发下优秀 | 高并发下较差 |

```kotlin
// ConcurrentHashMap 的高级用法
class SessionManager {
    
    private val sessions = ConcurrentHashMap<String, Session>()
    
    // ✅ 原子操作：如果不存在就创建
    fun getOrCreateSession(userId: String): Session {
        return sessions.computeIfAbsent(userId) { id ->
            Session(id, System.currentTimeMillis())
        }
    }
    
    // ✅ 原子操作：如果存在就更新
    fun updateLastActiveTime(userId: String) {
        sessions.computeIfPresent(userId) { _, session ->
            session.copy(lastActiveTime = System.currentTimeMillis())
        }
    }
    
    // ✅ 原子操作：替换（CAS）
    fun replaceSession(userId: String, oldSession: Session, newSession: Session): Boolean {
        return sessions.replace(userId, oldSession, newSession)
    }
}

data class Session(val userId: String, val lastActiveTime: Long)
```

### 5.3 不可变集合与 DiffUtil

```kotlin
// ✅ 最佳实践：使用不可变集合 + submitList
class ArticleViewModel(
    private val repository: ArticleRepository
) : ViewModel() {
    
    private val _articles = MutableLiveData<List<Article>>()
    val articles: LiveData<List<Article>> = _articles
    
    fun loadArticles() {
        viewModelScope.launch {
            // repository 返回不可变列表
            val result = repository.getArticles()
            _articles.value = result
        }
    }
    
    fun markAsRead(articleId: Long) {
        val currentList = _articles.value ?: return
        
        // 创建新列表（不可变风格）
        // map 返回新的 List，不修改原列表
        val newList = currentList.map { article ->
            if (article.id == articleId) {
                article.copy(isRead = true)  // 创建新对象
            } else {
                article
            }
        }
        
        // 发送新列表，DiffUtil 会自动计算差异
        _articles.value = newList
    }
    
    fun deleteArticle(articleId: Long) {
        val currentList = _articles.value ?: return
        
        // filter 返回新的 List
        val newList = currentList.filter { it.id != articleId }
        _articles.value = newList
    }
}

class ArticleFragment : Fragment() {
```

## 六、内存优化实战

### 6.1 检测集合内存占用

```kotlin
// 使用 Android Profiler 检测内存
// 或者用代码估算

object CollectionMemoryEstimator {
    
    /**
     * 粗略估算 HashMap<String, Object> 的内存占用
     * 
     * HashMap 内部：
     * - table[] 数组：默认 16 槽位 × 4 bytes = 64 bytes
     * - 每个 Entry：hash(4) + key ref(4) + value ref(4) + next ref(4) + 对象头(12) = 28 bytes
     * - 加上对齐，每个 Entry 约 32 bytes
     */
    fun estimateHashMapMemory(size: Int): Long {
        val tableSize = maxOf(16, size * 2)  // 假设 load factor 0.75
        val tableMemory = tableSize * 4L     // 数组引用
        val entryMemory = size * 32L         // Entry 对象
        return tableMemory + entryMemory
    }
    
    /**
     * 粗略估算 ArrayMap<String, Object> 的内存占用
     * 
     * ArrayMap 内部：
     * - mHashes[] int 数组：size × 4 bytes
     * - mArray[] Object 数组：size × 2 × 4 bytes（key + value）
     * - 无 Entry 对象开销！
     */
    fun estimateArrayMapMemory(size: Int): Long {
        val hashesMemory = size * 4L
        val arrayMemory = size * 2 * 4L
        return hashesMemory + arrayMemory
    }
    
    fun compare(size: Int) {
        val hashMapMem = estimateHashMapMemory(size)
        val arrayMapMem = estimateArrayMapMemory(size)
        val saved = hashMapMem - arrayMapMem
        val percent = saved * 100 / hashMapMem
        
        println("""
            数据量: $size
            HashMap 估算: $hashMapMem bytes
            ArrayMap 估算: $arrayMapMem bytes
            节省: $saved bytes ($percent%)
        """.trimIndent())
    }
}

// 测试
fun main() {
    CollectionMemoryEstimator.compare(100)
    // 数据量: 100
    // HashMap 估算: 4000 bytes
    // ArrayMap 估算: 1200 bytes
    // 节省: 2800 bytes (70%)
}
```

### 6.2 常见内存问题与优化

```kotlin
// 问题1：使用 HashMap<Int, Object> 导致装箱
// ❌ 错误
val badCache = HashMap<Int, Bitmap>()  // Int 会被装箱成 Integer

// ✅ 正确
val goodCache = SparseArray<Bitmap>()  // 直接用 int，无装箱


// 问题2：集合只增不减
class MemoryLeakExample {
    // ❌ 错误：集合无限增长
    private val eventLog = mutableListOf<Event>()
    
    fun logEvent(event: Event) {
        eventLog.add(event)  // 永远不清理，内存会爆！
    }
}

class MemoryOptimizedExample {
    // ✅ 正确：限制大小或定期清理
    private val eventLog = ArrayDeque<Event>(100)  // 固定大小的队列
    
    fun logEvent(event: Event) {
        if (eventLog.size >= 100) {
            eventLog.removeFirst()  // 超出就删除最老的
        }
        eventLog.addLast(event)
    }
}


// 问题3：重复创建集合
class InefficiencyExample {
    // ❌ 错误：每次调用都创建新集合
    fun getFilteredItems(items: List<Item>): List<Item> {
        val result = mutableListOf<Item>()  // 每次都 new
        items.filterTo(result) { it.isValid }
        return result
    }
}

class EfficientExample {
    // ✅ 正确：复用集合或使用 Sequence 延迟计算
    private val tempList = mutableListOf<Item>()
    
    fun getFilteredItems(items: List<Item>): List<Item> {
        tempList.clear()  // 清空复用
        items.filterTo(tempList) { it.isValid }
        return tempList.toList()
    }
    
    // 或者用 Sequence 延迟计算
    fun getFilteredItemsLazy(items: List<Item>): Sequence<Item> {
        return items.asSequence().filter { it.isValid }
    }
}

data class Event(val name: String, val timestamp: Long)
data class Item(val id: Long, val isValid: Boolean)
```

## 七、面试检验

### 进阶题

**Q1：ArrayMap 比 HashMap 省多少内存？原理是什么？**

> **结论**：小数据量（< 1000）时，ArrayMap 约省 30%-50% 内存。
> 
> **原理**：
> - HashMap 每个键值对需要一个 Entry 对象（约 32 bytes）
> - ArrayMap 用两个数组直接存储，无 Entry 对象开销
> - mHashes[] 存哈希值，mArray[] 交替存 key 和 value
> 
> **Android 实例**：Bundle、Intent 内部都用 ArrayMap。因为传递的数据通常很少，用 ArrayMap 既省内存又不影响性能。

**Q2：SparseArray 为什么能避免装箱开销？**

> **结论**：SparseArray 的 key 直接用原始类型 int 存储，不需要装箱成 Integer。
> 
> **原理**：
> - HashMap<Integer, Object> 中，int 必须装箱成 Integer 对象
> - 每个 Integer 对象有 12-16 bytes 的对象头开销
> - SparseArray 内部用 int[] 数组存 key，完全避免装箱
> 
> **Android 实例**：
> ```kotlin
> // ❌ 用户 ID 是 int，用 HashMap 会产生大量 Integer 对象
> val badCache = HashMap<Int, User>()
> 
> // ✅ 用 SparseArray，直接存 int
> val goodCache = SparseArray<User>()
> ```

**Q3：ConcurrentHashMap 和 Collections.synchronizedMap 有什么区别？**

> **结论**：ConcurrentHashMap 是分段锁/CAS 实现，并发性能更好；synchronizedMap 是整体加锁，并发性能差。
> 
> **原理**：
> - ConcurrentHashMap（JDK 8+）用 CAS + synchronized 细粒度锁
> - 读操作无锁，写操作只锁住一个桶
> - synchronizedMap 每次操作都锁整个 Map
> 
> **Android 实例**：多线程缓存场景用 ConcurrentHashMap。但 Android 更推荐用协程 + Mutex，或者把操作限制在单线程。

**Q4：为什么 RecyclerView 的数据源必须支持快速索引访问？**

> **结论**：因为 onBindViewHolder(position) 会频繁调用，必须 O(1) 获取数据。
> 
> **原理**：
> - 用户滑动列表时，RecyclerView 需要快速获取指定位置的数据
> - ArrayList 的 get(position) 是 O(1)
> - LinkedList 的 get(position) 是 O(n)，会导致滑动卡顿
> 
> **Android 实例**：永远用 ArrayList 作为 RecyclerView 的数据源，不要用 LinkedList。

**Q5：如何避免集合导致的内存泄漏？**

> **结论**：1) 及时清理不需要的数据；2) 使用弱引用；3) 限制集合大小；4) 注意生命周期。
> 
> **原理**：集合持有对象引用，如果集合生命周期比对象长，就会内存泄漏。
> 
> **Android 实例**：
> ```kotlin
> // ❌ 静态集合持有 Activity
> object BadManager {
>     val listeners = mutableListOf<OnClickListener>()  // 可能持有 Activity！
> }
> 
> // ✅ 使用弱引用或及时移除
> object GoodManager {
>     val listeners = mutableListOf<WeakReference<OnClickListener>>()
> }
> ```
