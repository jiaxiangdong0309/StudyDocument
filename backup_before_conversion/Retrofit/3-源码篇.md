# Retrofit 源码篇

> 理解框架设计的精妙之处

## 整体架构

### 一句话总结

Retrofit 的核心就是 **动态代理 + 注解解析 + 适配器模式**：通过动态代理拦截接口方法调用，解析方法上的注解构建 HTTP 请求，用 OkHttp 发送请求，再通过 Converter 和 CallAdapter 把响应转成你要的类型。

### 架构图

```

│  apiService.getUser(1)                                      │
└────────────────────────────┬────────────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────────────┐
│                     动态代理 (Proxy)                         │

                             │
```

### 核心组件

| 组件 | 职责 | 设计模式 |
|-----|------|---------|
| **Retrofit** | 门面，管理配置和创建代理 | 建造者模式、门面模式 |
| **ServiceMethod** | 解析方法注解，缓存解析结果 | 工厂模式、享元模式 |
| **RequestFactory** | 构建 OkHttp Request | 建造者模式 |
| **CallAdapter** | 适配不同的返回类型 | 适配器模式 |
| **Converter** | 数据格式转换 | 策略模式 |
| **OkHttpCall** | 真正执行请求 | 适配器模式 |

## 动态代理：核心魔法

### 为什么接口能变成实现类？

当你调用 `retrofit.create(ApiService::class.java)` 时，Retrofit 并没有生成真正的实现类，而是创建了一个**动态代理对象**。

```kotlin
// 简化版源码
public <T> T create(final Class<T> service) {
    // 验证接口的合法性
    validateServiceInterface(service);
    
    // 使用 Java 动态代理创建接口的实现
    return (T) Proxy.newProxyInstance(
        service.getClassLoader(),
        new Class<?>[] { service },
        new InvocationHandler() {
            @Override
            public Object invoke(Object proxy, Method method, Object[] args) {
                // 每次调用接口方法都会进入这里
                
                // 如果是 Object 的方法（如 toString），直接调用
                if (method.getDeclaringClass() == Object.class) {
                    return method.invoke(this, args);
                }
                
                // 核心：加载或解析 ServiceMethod，然后执行
                return loadServiceMethod(method).invoke(args);
            }
        }
    );
}
```

### 动态代理的本质

```
┌─────────────────────────────────────────────────────────┐
│  你以为的调用                                            │
│                                                         │
│  apiService.getUser(1)                                  │
│       │                                                 │
│       └──► ApiServiceImpl.getUser(1) ← 不存在！         │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│  实际的调用                                              │
│                                                         │
│  apiService.getUser(1)                                  │
│       │                                                 │
│       └──► Proxy.invoke(method="getUser", args=[1])    │
│                    │                                    │
│                    └──► ServiceMethod.invoke([1])       │
│                              │                          │
│                              └──► OkHttpCall.execute()  │
└─────────────────────────────────────────────────────────┘
```

### 设计哲学

**为什么用动态代理而不是代码生成？**

| 方案 | 优点 | 缺点 |
|-----|------|------|
| **动态代理（Retrofit 选择）** | 无需编译时处理，API 简洁 | 运行时有性能开销 |
| **代码生成（如 Room）** | 编译时检查，运行时零开销 | 需要注解处理器，构建复杂 |

Retrofit 选择动态代理是因为：
1. 网络请求本身就慢，代理的开销可以忽略
2. API 更简洁，不需要额外的编译配置
3. 接口变化不需要重新编译生成代码

## ServiceMethod：注解解析引擎

### 一句话总结

ServiceMethod 把接口方法的注解**翻译**成构建 HTTP 请求的指令，并缓存解析结果避免重复解析。

### 解析流程

```mermaid
graph TD
    A[调用接口方法] --> B{缓存中有?}
    B -->|是| C[直接使用缓存的 ServiceMethod]
    B -->|否| D[parseAnnotations]
    D --> E[解析方法注解<br/>@GET/@POST等]
    D --> F[解析参数注解<br/>@Path/@Query等]
    D --> G[确定返回类型]
    E --> H[创建 RequestFactory]
    F --> H
    G --> I[选择 CallAdapter]
    G --> J[选择 Converter]
    H --> K[创建 ServiceMethod]
    I --> K
    J --> K
    K --> L[放入缓存]
    L --> C
    
    style B fill:#fff9c4
    style D fill:#c8e6c9
    style K fill:#e1bee7
```

### 核心源码

```kotlin
// 简化版 ServiceMethod
abstract class ServiceMethod<T> {
    
    abstract fun invoke(args: Array<Any?>): T
    
    companion object {
        fun <T> parseAnnotations(retrofit: Retrofit, method: Method): ServiceMethod<T> {
            // 1. 解析方法注解，创建 RequestFactory
            val requestFactory = RequestFactory.parseAnnotations(retrofit, method)
            
            // 2. 获取返回类型
            val returnType = method.genericReturnType
            
            // 3. 选择合适的 CallAdapter
            val callAdapter = retrofit.callAdapter(returnType, method.annotations)
            
            // 4. 选择合适的 ResponseConverter
            val responseConverter = retrofit.responseBodyConverter(
                callAdapter.responseType(),
                method.annotations
            )
            
            // 5. 创建 HttpServiceMethod
            return HttpServiceMethod(requestFactory, callAdapter, responseConverter)
        }
    }
}
```

### 缓存机制

```kotlin
// Retrofit 类中的缓存
private val serviceMethodCache = ConcurrentHashMap<Method, ServiceMethod<*>>()

fun loadServiceMethod(method: Method): ServiceMethod<*> {
    // 先查缓存
    var result = serviceMethodCache[method]
    if (result != null) return result
    
    // 双重检查锁定
    synchronized(serviceMethodCache) {
        result = serviceMethodCache[method]
        if (result == null) {
            result = ServiceMethod.parseAnnotations(this, method)
            serviceMethodCache[method] = result
        }
    }
    return result!!
}
```

**设计亮点**：
- 使用 ConcurrentHashMap 保证线程安全
- 双重检查避免重复解析
- 以 Method 对象为 key，天然唯一

## RequestFactory：请求构建器

### 一句话总结

RequestFactory 把方法注解和参数注解**翻译**成 OkHttp 的 Request，是从"声明式 API"到"命令式请求"的桥梁。

### 解析过程

```kotlin
// 简化版 RequestFactory
class RequestFactory private constructor(
    val method: String,           // HTTP 方法：GET/POST
    val baseUrl: HttpUrl,
    val relativeUrl: String?,     // 相对路径
    val headers: Headers?,
    val contentType: MediaType?,
    val hasBody: Boolean,
    val isFormEncoded: Boolean,
    val isMultipart: Boolean,
    val parameterHandlers: Array<ParameterHandler<*>>  // 参数处理器
) {
    
    // 创建 OkHttp Request
    fun create(args: Array<Any?>): Request {
        val requestBuilder = RequestBuilder(
            method, baseUrl, relativeUrl, headers, contentType,
            hasBody, isFormEncoded, isMultipart
        )
        
        // 每个参数用对应的 ParameterHandler 处理
        parameterHandlers.forEachIndexed { index, handler ->
            handler.apply(requestBuilder, args[index])
        }
        
        return requestBuilder.build()
    }
    
    companion object {
        fun parseAnnotations(retrofit: Retrofit, method: Method): RequestFactory {
            // 解析方法注解
            for (annotation in method.annotations) {
                parseMethodAnnotation(annotation)
            }
            
            // 解析每个参数的注解
            val parameterTypes = method.genericParameterTypes
            val parameterAnnotations = method.parameterAnnotations
            val handlers = Array(parameterTypes.size) { index ->
                parseParameterAnnotation(
                    parameterTypes[index],
                    parameterAnnotations[index]
                )
            }
            
            return RequestFactory(...)
        }
    }
}
```

### ParameterHandler：参数处理器

每种参数注解对应一个 ParameterHandler：

```kotlin
// 参数处理器接口
abstract class ParameterHandler<T> {
    abstract fun apply(builder: RequestBuilder, value: T)
}

// @Path 的处理器
class Path(private val name: String, private val encoded: Boolean) : ParameterHandler<String>() {
    override fun apply(builder: RequestBuilder, value: String) {
        builder.addPathParam(name, value, encoded)
    }
}

// @Query 的处理器
class Query(private val name: String, private val encoded: Boolean) : ParameterHandler<String?>() {
    override fun apply(builder: RequestBuilder, value: String?) {
        if (value != null) {
            builder.addQueryParam(name, value, encoded)
        }
    }
}

// @Body 的处理器
class Body<T>(private val converter: Converter<T, RequestBody>) : ParameterHandler<T>() {
    override fun apply(builder: RequestBuilder, value: T) {
        val body = converter.convert(value)
        builder.setBody(body)
    }
}
```

**设计亮点**：
- **策略模式**：不同注解用不同的 Handler 处理
- **单一职责**：每个 Handler 只处理一种注解
- **解耦**：新增注解只需新增 Handler，不影响现有代码

## Converter：数据转换的艺术

### 一句话总结

Converter 是数据格式的翻译官，负责 RequestBody ↔ 对象 和 ResponseBody ↔ 对象 的双向转换。

### 工厂模式

```kotlin
// Converter 工厂接口
abstract class Converter<F, T> {
    abstract fun convert(value: F): T
    
    // 工厂：负责创建 Converter
    abstract class Factory {
        // 响应体转换器：ResponseBody → T
        open fun responseBodyConverter(
            type: Type,
            annotations: Array<Annotation>,
            retrofit: Retrofit
        ): Converter<ResponseBody, *>? = null
        
        // 请求体转换器：T → RequestBody
        open fun requestBodyConverter(
            type: Type,
            parameterAnnotations: Array<Annotation>,
            methodAnnotations: Array<Annotation>,
            retrofit: Retrofit
        ): Converter<*, RequestBody>? = null
        
        // 字符串转换器：T → String（用于 @Query, @Path 等）
        open fun stringConverter(
            type: Type,
            annotations: Array<Annotation>,
            retrofit: Retrofit
        ): Converter<*, String>? = null
    }
}
```

### Converter 选择流程

```kotlin
// Retrofit 类中
fun <T> responseBodyConverter(type: Type, annotations: Array<Annotation>): Converter<ResponseBody, T> {
    // 遍历所有 ConverterFactory
    for (factory in converterFactories) {
        val converter = factory.responseBodyConverter(type, annotations, this)
        if (converter != null) {
            return converter as Converter<ResponseBody, T>
        }
    }
    throw IllegalArgumentException("找不到合适的 Converter")
}
```

**关键点**：
- 按添加顺序遍历
- 第一个返回非 null 的胜出
- 所以顺序很重要！

### Gson Converter 实现

```kotlin
class GsonConverterFactory private constructor(private val gson: Gson) : Converter.Factory() {
    
    override fun responseBodyConverter(
        type: Type,
        annotations: Array<Annotation>,
        retrofit: Retrofit
    ): Converter<ResponseBody, *> {
        val adapter = gson.getAdapter(TypeToken.get(type))
        return GsonResponseBodyConverter(gson, adapter)
    }
    
    override fun requestBodyConverter(
        type: Type,
        parameterAnnotations: Array<Annotation>,
        methodAnnotations: Array<Annotation>,
        retrofit: Retrofit
    ): Converter<*, RequestBody> {
        val adapter = gson.getAdapter(TypeToken.get(type))
        return GsonRequestBodyConverter(gson, adapter)
    }
}

// 响应转换器
class GsonResponseBodyConverter<T>(
    private val gson: Gson,
    private val adapter: TypeAdapter<T>
) : Converter<ResponseBody, T> {
    
    override fun convert(value: ResponseBody): T {
        val reader = gson.newJsonReader(value.charStream())
        return value.use {
            adapter.read(reader)
        }
    }
}
```

## CallAdapter：返回类型的魔法

### 一句话总结

CallAdapter 决定了接口方法返回什么类型：`Call<T>`、`Observable<T>`、还是直接返回 `T`（suspend 函数）。

### 适配器模式

```kotlin
// CallAdapter 接口
interface CallAdapter<R, T> {
    // 返回响应类型（Converter 需要知道转成什么类型）
    fun responseType(): Type
    
    // 把 Call<R> 适配成 T
    fun adapt(call: Call<R>): T
}

// 工厂接口
abstract class Factory {
    abstract fun get(
        returnType: Type,
        annotations: Array<Annotation>,
        retrofit: Retrofit
    ): CallAdapter<*, *>?
}
```

### 默认 CallAdapter

```kotlin
// 返回 Call<T> 的适配器（最简单）
class DefaultCallAdapterFactory : CallAdapter.Factory() {
    
    override fun get(returnType: Type, annotations: Array<Annotation>, retrofit: Retrofit): CallAdapter<*, *>? {
        if (getRawType(returnType) != Call::class.java) {
            return null  // 不是 Call 类型，交给下一个工厂
        }
        
        val responseType = getParameterUpperBound(0, returnType as ParameterizedType)
        return object : CallAdapter<Any, Call<Any>> {
            override fun responseType() = responseType
            override fun adapt(call: Call<Any>) = call  // 直接返回，不做任何转换
        }
    }
}
```

### 协程 suspend 的实现

Retrofit 2.6.0+ 内置了对 suspend 函数的支持：

```kotlin
// 简化版 SuspendForBody
class SuspendForBody<ResponseT>(
    private val responseType: Type,
    private val isNullable: Boolean
) : CallAdapter<ResponseT, Any> {
    
    override fun responseType() = responseType
    
    override fun adapt(call: Call<ResponseT>): Any {
        // 返回一个 suspend lambda
        return suspend {
            // 使用协程的 suspendCancellableCoroutine
            suspendCancellableCoroutine<ResponseT> { continuation ->
                // 协程取消时，取消请求
                continuation.invokeOnCancellation {
                    call.cancel()
                }
                
                // 异步执行请求
                call.enqueue(object : Callback<ResponseT> {
                    override fun onResponse(call: Call<ResponseT>, response: Response<ResponseT>) {
                        if (response.isSuccessful) {
                            continuation.resume(response.body()!!)
                        } else {
                            continuation.resumeWithException(HttpException(response))
                        }
                    }
                    
                    override fun onFailure(call: Call<ResponseT>, t: Throwable) {
                        continuation.resumeWithException(t)
                    }
                })
            }
        }
    }
}
```

**核心技巧**：把回调式 API 转成挂起函数，用 `suspendCancellableCoroutine` 桥接。

## 设计亮点与借鉴

### 1. 注解驱动设计

**理念**：用声明式的方式描述意图，让框架负责实现。

```kotlin
// 声明式：说"做什么"
@GET("users/{id}")
suspend fun getUser(@Path("id") id: Int): User

// 命令式：说"怎么做"
val request = Request.Builder()
    .url("$baseUrl/users/$id")
    .get()
    .build()
```

**可借鉴**：设计 API 时，考虑能否用注解简化使用方。

### 2. 工厂 + 责任链

**理念**：用工厂创建处理者，用责任链选择处理者。

```kotlin
// 多个工厂按顺序尝试
for (factory in factories) {
    val result = factory.create(input)
    if (result != null) return result
}
```

**可借鉴**：当有多种处理策略时，用这种模式实现可扩展性。

### 3. 延迟解析 + 缓存

**理念**：第一次用到才解析，解析结果缓存复用。

```kotlin
// 不是在 create() 时就解析所有方法
// 而是在调用方法时才解析，并缓存结果
```

**可借鉴**：对于计算密集的初始化，考虑延迟执行。

### 4. 类型安全的参数处理

**理念**：用泛型确保类型安全，在编译期发现问题。

```kotlin
// 每个 ParameterHandler 都是泛型的
abstract class ParameterHandler<T> {
    abstract fun apply(builder: RequestBuilder, value: T)
}
```

**可借鉴**：善用泛型提供编译期类型检查。

## 延伸思考

### 如果让你设计 Retrofit，你会怎么做？

1. **接口到实现**：
   - 方案 A：动态代理（Retrofit 的选择）
   - 方案 B：APT 代码生成（类似 Room）
   - 方案 C：KSP 代码生成（Kotlin 专用）
   
2. **注解解析**：
   - 何时解析？启动时 vs 首次调用时
   - 缓存什么？Method 对象 vs 方法签名字符串
   
3. **线程模型**：
   - 同步还是异步？
   - 协程支持怎么设计？

### Retrofit 的局限性

1. **运行时开销**：动态代理有性能成本（虽然很小）
2. **调试困难**：代理对象不好 debug
3. **编译期检查不足**：注解错误只有运行时才发现
4. **不支持增量构建**：接口改了全部重新解析（相比 APT）

### 未来可能的改进

1. **KSP 代码生成**：像 Room 一样，编译期生成实现类
2. **更强的类型推断**：自动识别返回类型，减少配置
3. **更好的错误提示**：编译期检查注解使用是否正确

## 面试检验

### Q1：Retrofit 是如何将接口变成实现类的？

**答案**：使用 **Java 动态代理**。调用 `retrofit.create(ApiService::class.java)` 时，Retrofit 用 `Proxy.newProxyInstance()` 创建代理对象。当调用接口方法时，实际调用的是代理的 `invoke()` 方法，在这里 Retrofit 会解析方法注解、构建请求、发送请求并返回结果。

**追问**：为什么用动态代理而不是代码生成？
- 网络请求本身耗时，代理开销可忽略
- API 更简洁，不需要 APT/KSP 配置
- 灵活性更高，运行时可以动态调整

### Q2：ServiceMethod 的作用和缓存机制？

**答案**：ServiceMethod 负责解析方法注解，是"声明式接口"到"命令式请求"的翻译器。它解析 @GET、@POST、@Path、@Query 等注解，生成构建 Request 的指令。

缓存机制：使用 `ConcurrentHashMap<Method, ServiceMethod>` 存储已解析的 ServiceMethod。首次调用时解析并缓存，后续调用直接从缓存取，避免重复解析的开销。

### Q3：Converter 和 CallAdapter 的区别？工作时机？

**答案**：

**Converter**：
- 职责：数据格式转换（JSON ↔ 对象）
- 工作时机：请求发送前（对象 → RequestBody）和响应返回后（ResponseBody → 对象）
- 举例：GsonConverterFactory

**CallAdapter**：
- 职责：调用方式转换（决定返回什么类型）
- 工作时机：构建 ServiceMethod 时选择，调用接口方法时执行适配
- 举例：RxJavaCallAdapterFactory 把 Call 变成 Observable

**本质区别**：Converter 管"数据长什么样"，CallAdapter 管"怎么拿数据"。

### Q4：多个 Converter/CallAdapter 的选择规则？

**答案**：**按添加顺序依次尝试**，第一个返回非 null 的被使用。这是责任链模式的应用。

所以添加顺序很重要：
```kotlin
Retrofit.Builder()
    .addConverterFactory(ScalarsConverterFactory.create())  // 先加特殊的
    .addConverterFactory(GsonConverterFactory.create())      // 后加通用的
```

如果顺序反了，Gson 会"吃掉"所有类型，ScalarsConverter 永远不会被用到。

### Q5：Retrofit 如何支持 Kotlin 协程？

**答案**：Retrofit 2.6.0+ 内置支持 suspend 函数。检测到方法是 suspend 时，使用特殊的 SuspendForBody/SuspendForResponse 作为 CallAdapter。

实现原理：使用 `suspendCancellableCoroutine` 桥接回调式 API：
1. 把 OkHttp 的 Callback 转成协程的 Continuation
2. 协程取消时自动 `call.cancel()`
3. 回调成功时 `continuation.resume()`
4. 回调失败时 `continuation.resumeWithException()`
