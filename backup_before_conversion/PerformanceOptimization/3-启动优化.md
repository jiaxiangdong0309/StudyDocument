# 启动优化 (Launch Optimization)

## 为什么要做启动优化？

App 启动就像餐厅开门迎客——开门太慢，顾客就走了。用户对启动速度非常敏感，超过 3 秒就会有明显的流失。

**启动优化的价值**：
- 用户体验：启动快 = 体验好
- 留存率：每快 100ms，转化率提升 1%
- 面试必问：大厂面试高频题

## 一、启动类型

### 1.1 三种启动类型

```
┌────────────────────────────────────────────────────────────────┐
│                        App 启动类型                             │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│   冷启动 (Cold Start)                                          │
│   ├── 进程不存在，需要创建进程                                   │
│   ├── 加载 Application、Activity                               │
│   └── 耗时最长，是优化重点                                       │
│                                                                │
│   温启动 (Warm Start)                                          │
│   ├── 进程存在，但 Activity 被销毁                               │
│   ├── 需要重新创建 Activity                                     │
│   └── 比冷启动快，跳过进程创建                                   │
│                                                                │
│   热启动 (Hot Start)                                           │
│   ├── 进程存在，Activity 在后台                                 │
│   ├── 只需要把 Activity 带到前台                                │
│   └── 最快，几乎无需优化                                        │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

### 1.2 冷启动流程

```
┌─────────────────────────────────────────────────────────────────┐
│                        冷启动完整流程                             │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  系统阶段（不可控）              App 阶段（可优化）                  │
│  ┌─────────────────┐          ┌─────────────────────────┐       │
│  │ 1. fork 进程     │    →    │ 4. Application.onCreate │       │
│  │ 2. 创建虚拟机    │          │ 5. Activity.onCreate    │       │
│  │ 3. 创建Application│         │ 6. 测量、布局、绘制       │       │
│  └─────────────────┘          │ 7. 首帧渲染完成          │       │
│                               └─────────────────────────┘       │
│                                                                 │
│  启动时间 = 系统耗时 + Application耗时 + Activity耗时 + 首帧渲染    │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**启动时间计算**：
- **起点**：用户点击图标
- **终点**：首帧渲染完成（用户看到有内容的界面）

## 二、启动时间测量

### 2.1 查看系统日志

```bash
# 过滤 ActivityTaskManager 日志
adb logcat -s ActivityTaskManager

# 输出示例
# ActivityTaskManager: Displayed com.example.app/.MainActivity: +1s234ms
```

这个时间是系统测量的「首帧显示时间」。

### 2.2 使用 adb 命令

```bash
# 冷启动测量（先强制停止 App）
adb shell am force-stop com.example.app
adb shell am start-activity -W com.example.app/.MainActivity

# 输出示例
# TotalTime: 1234    # 从 startActivity 到首帧显示
# WaitTime: 1456     # 包含等待前一个 Activity pause 的时间
```

### 2.3 代码埋点

```kotlin
class MyApplication : Application() {
    
    companion object {
        // 记录启动时间
        var startTime = SystemClock.elapsedRealtime()
    }
    
    override fun attachBaseContext(base: Context) {
        super.attachBaseContext(base)
        startTime = SystemClock.elapsedRealtime()
    }
}

class MainActivity : AppCompatActivity() {
    
    override fun onWindowFocusChanged(hasFocus: Boolean) {
        super.onWindowFocusChanged(hasFocus)
        if (hasFocus) {
            val launchTime = SystemClock.elapsedRealtime() - MyApplication.startTime
            Log.d("Launch", "启动耗时: ${launchTime}ms")
        }
    }
}
```

### 2.4 使用 Systrace

```bash
# 抓取启动 trace
python systrace.py -o launch_trace.html -a com.example.app sched freq idle am wm gfx view

# 在 trace.html 中分析：
# - bindApplication：Application 创建
# - activityStart：Activity 启动
# - inflate：布局加载
# - draw：绘制
```

## 三、Application 优化

### 3.1 延迟初始化

很多 SDK 不需要在 Application 中立即初始化：

```kotlin
class MyApplication : Application() {
    
    override fun onCreate() {
        super.onCreate()
        
        // ❌ 所有 SDK 都在 onCreate 初始化
        initCrashSDK()
        initAnalyticsSDK()
        initPushSDK()
        initAdSDK()
        initShareSDK()
        // ... 更多 SDK
    }
}
```

```kotlin
class MyApplication : Application() {
    
    override fun onCreate() {
        super.onCreate()
        
        // ✅ 分级初始化
        
        // 1. 必须立即初始化（崩溃收集、基础配置）
        initCrashSDK()
        
        // 2. 可以延迟到首帧后
        // 3. 可以延迟到使用时
    }
}

// 首帧后初始化
class MainActivity : AppCompatActivity() {
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)
        
        // 首帧绘制后再初始化
        window.decorView.post {
            initAnalyticsSDK()
            initPushSDK()
        }
    }
}

// 使用时初始化（懒加载）
object ShareManager {
    private var initialized = false
    
    fun share(context: Context, content: String) {
        if (!initialized) {
            initShareSDK(context)
            initialized = true
        }
        // 执行分享
    }
}
```

### 3.2 异步初始化

把耗时初始化放到子线程：

```kotlin
class MyApplication : Application() {
    
    override fun onCreate() {
        super.onCreate()
        
        // 必须在主线程初始化的 SDK
        initCrashSDK()
        
        // 可以异步初始化的 SDK
        thread {
            initAnalyticsSDK()  // 不依赖主线程
            initImageLoader()    // 图片库
        }
    }
}
```

#### 使用启动框架

对于复杂的依赖关系，可以使用启动框架：

```kotlin
// 定义任务
class AnalyticsTask : Task() {
    override fun run() {
        initAnalyticsSDK()
    }
    
    override fun needRunOnMainThread() = false  // 可以异步
    override fun dependencies() = emptyList<Class<out Task>>()  // 无依赖
}

class PushTask : Task() {
    override fun run() {
        initPushSDK()
    }
    
    override fun needRunOnMainThread() = true  // 必须主线程
    override fun dependencies() = listOf(AnalyticsTask::class.java)  // 依赖分析 SDK
}

// 启动时执行
TaskDispatcher.init(this)
TaskDispatcher.createInstance()
    .addTask(AnalyticsTask())
    .addTask(PushTask())
    .addTask(AdTask())
    .start()
    .await()  // 等待必须的任务完成
```

### 3.3 减少 Application 中的操作

- 不要在 Application 中进行大量计算
- 不要在 Application 中进行 IO 操作
- 不要在 Application 中创建大量对象

## 四、Activity 优化

### 4.1 减少 onCreate 耗时

```kotlin
class MainActivity : AppCompatActivity() {
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        
        // ✅ 先设置布局
        setContentView(R.layout.activity_main)
        
        // ✅ 轻量级初始化
        initViews()
        
        // ❌ 不要在这里：
        // - 请求网络数据
        // - 读取大文件
        // - 进行复杂计算
        
        // ✅ 异步加载数据
        viewModel.loadData()
    }
}
```

### 4.2 布局优化

参考布局优化章节，减少布局层级、使用 ViewStub 延迟加载：

```xml
<!-- 首屏只显示必要内容 -->
<ConstraintLayout>
    <!-- 必要的 UI 元素 -->
    <TextView android:id="@+id/title" ... />
    
    <!-- 非首屏内容延迟加载 -->
    <ViewStub
        android:id="@+id/stub_content"
        android:layout="@layout/content_layout"/>
</ConstraintLayout>
```

### 4.3 减少首帧内容

首屏只显示骨架屏或占位符，数据加载完成后再显示实际内容：

```kotlin
class MainActivity : AppCompatActivity() {
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)
        
        // 显示骨架屏
        showSkeleton()
        
        // 异步加载数据
        viewModel.data.observe(this) { data ->
            // 数据加载完成后显示实际内容
            hideSkeleton()
            showContent(data)
        }
    }
}
```

## 五、视觉优化

### 5.1 启动页白屏问题

冷启动时，系统会先显示一个预览窗口（通常是白色或黑色），然后才显示 Activity 内容。

**解决方案一：设置启动主题背景**

```xml
<!-- 定义启动主题 -->
<style name="SplashTheme" parent="Theme.MaterialComponents.DayNight.NoActionBar">
    <!-- 设置启动时显示的背景 -->
    <item name="android:windowBackground">@drawable/splash_background</item>
</style>

<!-- splash_background.xml -->
<layer-list xmlns:android="http://schemas.android.com/apk/res/android">
    <item android:drawable="@color/white"/>
    <item>
        <bitmap
            android:gravity="center"
            android:src="@mipmap/ic_launcher"/>
    </item>
</layer-list>
```

```xml
<!-- AndroidManifest.xml -->
<activity
    android:name=".SplashActivity"
    android:theme="@style/SplashTheme">
    <intent-filter>
        <action android:name="android.intent.action.MAIN"/>
        <category android:name="android.intent.category.LAUNCHER"/>
    </intent-filter>
</activity>
```

```kotlin
class SplashActivity : AppCompatActivity() {
    
    override fun onCreate(savedInstanceState: Bundle?) {
        // 在 setContentView 之前切换主题
        setTheme(R.style.AppTheme)
        super.onCreate(savedInstanceState)
        
        // 跳转到主页
        startActivity(Intent(this, MainActivity::class.java))
        finish()
    }
}
```

**解决方案二：使用 SplashScreen API（Android 12+）**

```kotlin
// build.gradle
implementation 'androidx.core:core-splashscreen:1.0.1'
```

```xml
<!-- 定义 SplashScreen 主题 -->
<style name="Theme.App.Starting" parent="Theme.SplashScreen">
    <item name="windowSplashScreenBackground">@color/white</item>
    <item name="windowSplashScreenAnimatedIcon">@drawable/ic_launcher</item>
    <item name="windowSplashScreenAnimationDuration">1000</item>
    <item name="postSplashScreenTheme">@style/AppTheme</item>
</style>
```

```kotlin
class MainActivity : AppCompatActivity() {
    
    override fun onCreate(savedInstanceState: Bundle?) {
        // 安装 SplashScreen
        val splashScreen = installSplashScreen()
        super.onCreate(savedInstanceState)
        
        // 保持启动页直到数据加载完成
        splashScreen.setKeepOnScreenCondition {
            viewModel.isLoading.value
        }
    }
}
```

## 六、进阶优化

### 6.1 MultiDex 优化

64K 方法数限制导致需要 MultiDex，但 MultiDex 会增加启动时间。

**优化方案**：
1. 减少方法数，避免 MultiDex
2. 使用 R8 优化，减少无用代码
3. Android 5.0+ 使用 ART，MultiDex 影响较小

### 6.2 类加载优化

类加载也是启动耗时的一部分：

```kotlin
// 预加载常用类
class MyApplication : Application() {
    
    override fun onCreate() {
        super.onCreate()
        
        thread {
            // 异步预加载类
            Class.forName("androidx.recyclerview.widget.RecyclerView")
            Class.forName("com.google.gson.Gson")
            // ... 其他常用类
        }
    }
}
```

### 6.3 资源优化

- 使用 WebP 代替 PNG
- 压缩图片资源
- 删除无用资源

### 6.4 线程优化

启动时线程过多会竞争 CPU：

```kotlin
// 使用统一的线程池，避免创建过多线程
val startupExecutor = Executors.newFixedThreadPool(
    (Runtime.getRuntime().availableProcessors() - 1).coerceAtLeast(1)
)
```

## 七、监控与持续优化

### 7.1 线上监控

```kotlin
// 上报启动时间
class MainActivity : AppCompatActivity() {
    
    override fun onWindowFocusChanged(hasFocus: Boolean) {
        super.onWindowFocusChanged(hasFocus)
        if (hasFocus && !reported) {
            reported = true
            val launchTime = SystemClock.elapsedRealtime() - MyApplication.startTime
            
            // 上报到监控平台
            Analytics.report("launch_time", launchTime)
        }
    }
}
```

### 7.2 CI 集成

在 CI 中集成启动时间检测，防止劣化：

```bash
# CI 脚本示例
launch_time=$(adb shell am start-activity -W com.example.app/.MainActivity | grep TotalTime | awk '{print $2}')

if [ $launch_time -gt 2000 ]; then
    echo "启动时间超过 2s，请优化！"
    exit 1
fi
```

## 八、面试题精选

### Q1：启动优化做过哪些工作？

**答**：
1. **测量**：使用 adb、Systrace、代码埋点测量启动时间
2. **Application 优化**：延迟初始化、异步初始化、使用启动框架
3. **Activity 优化**：减少 onCreate 耗时、布局优化、异步加载数据
4. **视觉优化**：使用启动主题、SplashScreen API
5. **监控**：线上监控启动时间、CI 防劣化

### Q2：冷启动、温启动、热启动的区别？

**答**：

| 类型 | 进程状态 | Activity 状态 | 耗时 |
|-----|---------|--------------|------|
| 冷启动 | 不存在 | 不存在 | 最长 |
| 温启动 | 存在 | 被销毁 | 中等 |
| 热启动 | 存在 | 在后台 | 最短 |

### Q3：如何测量启动时间？

**答**：
1. **系统日志**：`adb logcat -s ActivityTaskManager`，查看 Displayed 日志
2. **adb 命令**：`adb shell am start-activity -W`，查看 TotalTime
3. **代码埋点**：`attachBaseContext` 到 `onWindowFocusChanged` 的时间差
4. **Systrace**：分析详细的各阶段耗时

### Q4：有哪些启动优化的方法？

**答**：

**Application 阶段**：
- 延迟初始化：非必要 SDK 延后
- 异步初始化：耗时操作放子线程
- 启动框架：管理依赖关系

**Activity 阶段**：
- 布局优化：减少层级、ViewStub 延迟加载
- 异步加载：数据请求异步化
- 首帧优化：显示骨架屏，减少首帧内容

**视觉优化**：
- 启动主题：避免白屏
- SplashScreen API：统一启动体验

### Q5：延迟初始化和异步初始化有什么区别？

**答**：
- **延迟初始化**：把初始化推迟到首帧后或使用时
- **异步初始化**：在子线程执行初始化，不阻塞主线程

两者可以结合使用：对于不紧急且耗时的初始化，先延迟到首帧后，再异步执行。
