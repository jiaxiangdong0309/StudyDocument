# Android 四大引用（Strong、Soft、Weak、Phantom Reference）

## 为什么要了解四大引用？

想象一下这个场景：你开了一家奶茶店，店里有 VIP 客户、普通客户、临时客户和已经走了但还没结账的客户。当店里座位不够时，你会怎么处理？

- **VIP 客户**（强引用）：绝对不能赶走，就算店倒闭也得伺候着
- **普通客户**（软引用）：座位实在不够了才请他们离开
- **临时客户**（弱引用）：随时可能走，下次 GC 来就没了
- **已走未结账的**（虚引用）：人已经走了，只是留个记录方便后续处理

这就是 Java/Android 中四大引用的核心思想：**让 GC 知道对象的"重要程度"，从而决定回收策略**。

## 一、四大引用全景图

### 1.1 快速对比

| 引用类型 | 回收时机 | 是否进入引用队列 | 典型应用场景 | 生活类比 |
|---------|---------|----------------|-------------|---------|
| **强引用** | 永不回收（除非置 null） | 不适用 | 普通对象引用 | VIP 客户 |
| **软引用** | 内存不足时回收 | 可选 | 内存敏感缓存（图片） | 普通客户 |
| **弱引用** | 下次 GC 时回收 | 可选 | 防内存泄漏、WeakHashMap | 临时客户 |
| **虚引用** | 随时可能被回收 | **必须** | 追踪对象回收、堆外内存管理 | 已走未结账 |

### 1.2 引用强度排序

```
强引用 > 软引用 > 弱引用 > 虚引用
  ↓        ↓        ↓        ↓
绝不回收  内存不足  下次GC   随时回收
```

## 二、强引用（Strong Reference）

### 2.1 是什么？

强引用是最常见的引用类型，就是我们平时写的普通对象引用：

```kotlin
val user = User("张三")  // 这就是强引用
```

**核心特点**：只要强引用存在，GC 绝对不会回收这个对象，哪怕 OOM 也不会。

### 2.2 为什么会导致内存泄漏？

```kotlin
// ❌ 经典内存泄漏：Activity 被静态变量强引用
object AppManager {
    var currentActivity: Activity? = null  // 强引用！
}

class MainActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        AppManager.currentActivity = this  // 泄漏！Activity 无法被回收
    }
}
```

**问题分析**：
- `AppManager` 是单例，生命周期 = 应用生命周期
- `currentActivity` 强引用 Activity
- Activity 销毁后，因为被强引用，GC 无法回收 → **内存泄漏**

### 2.3 如何断开强引用？

```kotlin
// ✅ 正确做法：在合适的时机置空
override fun onDestroy() {
    super.onDestroy()
    AppManager.currentActivity = null  // 断开强引用
}
```

## 三、软引用（Soft Reference）

### 3.1 是什么？

软引用描述的是"有用但非必需"的对象。**只有当内存不足时，GC 才会回收软引用对象**。

```kotlin
import java.lang.ref.SoftReference

// 创建软引用
val bitmap = BitmapFactory.decodeResource(resources, R.drawable.large_image)
val softRef = SoftReference(bitmap)

// 使用时需要检查是否被回收
val cachedBitmap = softRef.get()
if (cachedBitmap != null) {
    imageView.setImageBitmap(cachedBitmap)
} else {
    // 已被回收，需要重新加载
    loadImageAgain()
}
```

### 3.2 典型应用：图片缓存

```kotlin
/**
 * 基于软引用的简易图片缓存
 * 
 * 设计思路：
 * - 内存充足时：图片保留在缓存中，快速访问
 * - 内存紧张时：GC 自动回收，避免 OOM
 */
class SoftImageCache {
    // 用 HashMap 存储软引用，key 是图片 URL
    private val cache = HashMap<String, SoftReference<Bitmap>>()
    
    fun put(url: String, bitmap: Bitmap) {
        cache[url] = SoftReference(bitmap)
    }
    
    fun get(url: String): Bitmap? {
        val softRef = cache[url] ?: return null
        val bitmap = softRef.get()
        
        // 如果已被回收，清理无效条目
        if (bitmap == null) {
            cache.remove(url)
        }
        return bitmap
    }
    
    // 清理所有已被回收的条目
    fun cleanUp() {
        val iterator = cache.entries.iterator()
        while (iterator.hasNext()) {
            if (iterator.next().value.get() == null) {
                iterator.remove()
            }
        }
    }
}
```

### 3.3 软引用 vs LruCache

| 对比项 | 软引用缓存 | LruCache |
|-------|----------|----------|
| 回收策略 | 由 GC 决定，不可控 | 由 LRU 算法决定，可控 |
| 内存控制 | 被动，等 GC 回收 | 主动，设置最大容量 |
| 命中率 | 不稳定，可能刚存入就被回收 | 稳定，按访问频率淘汰 |
| 适用场景 | 对缓存命中率要求不高 | 需要稳定缓存效果 |

> **实战建议**：现代 Android 开发中，**LruCache + DiskLruCache 组合** 比纯软引用缓存更可控。Glide、Coil 等图片库内部就是这么做的。软引用更适合作为"二级缓存"或"兜底策略"。

### 3.4 软引用的回收时机

```
内存充足时：软引用对象不会被回收
     ↓
内存开始紧张（接近 -Xmx 限制）
     ↓
GC 触发，开始回收软引用对象
     ↓
回收顺序：最近最少使用的软引用优先被回收（LRU 策略）
     ↓
如果回收后内存仍不足 → OOM
```

## 四、弱引用（Weak Reference）

### 4.1 是什么？

弱引用比软引用更"弱"，**只要 GC 运行，不管内存够不够，都会回收弱引用对象**。

```kotlin
import java.lang.ref.WeakReference

val user = User("张三")
val weakRef = WeakReference(user)

// 此时 weakRef.get() 返回 User 对象
println(weakRef.get())  // User(name=张三)

// 如果没有其他强引用指向 user，下次 GC 后
System.gc()  // 建议 GC（不保证立即执行）
Thread.sleep(100)

// weakRef.get() 可能返回 null
println(weakRef.get())  // 可能是 null
```

### 4.2 核心应用：防止内存泄漏

**场景一：Handler 内存泄漏**

```kotlin
// ❌ 经典错误：匿名内部类持有外部类引用
class MainActivity : AppCompatActivity() {
    
    private val handler = object : Handler(Looper.getMainLooper()) {
        override fun handleMessage(msg: Message) {
            // 这里隐式持有 MainActivity 的强引用！
            updateUI()
        }
    }
    
    fun updateUI() { /* ... */ }
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        // 发送延迟消息，10秒后执行
        handler.sendEmptyMessageDelayed(0, 10_000)
    }
    // 如果用户在 10 秒内退出 Activity，Activity 无法被回收 → 内存泄漏
}
```

```kotlin
// ✅ 正确做法：使用弱引用
class MainActivity : AppCompatActivity() {
    
    // 静态内部类 + 弱引用
    private class SafeHandler(activity: MainActivity) : Handler(Looper.getMainLooper()) {
        private val activityRef = WeakReference(activity)
        
        override fun handleMessage(msg: Message) {
            // 通过弱引用获取 Activity，可能为 null
            val activity = activityRef.get() ?: return
            activity.updateUI()
        }
    }
    
    private val handler = SafeHandler(this)
    
    fun updateUI() { /* ... */ }
    
    override fun onDestroy() {
        super.onDestroy()
        handler.removeCallbacksAndMessages(null)  // 清理消息队列
    }
}
```

**场景二：监听器/回调泄漏**

```kotlin
// ❌ 错误：强引用回调
class DataManager {
    private val listeners = mutableListOf<OnDataChangeListener>()
    
    fun addListener(listener: OnDataChangeListener) {
        listeners.add(listener)  // 强引用，如果忘记 remove 就泄漏
    }
}

// ✅ 正确：弱引用回调
class DataManager {
    private val listeners = mutableListOf<WeakReference<OnDataChangeListener>>()
    
    fun addListener(listener: OnDataChangeListener) {
        listeners.add(WeakReference(listener))
    }
    
    fun notifyListeners(data: String) {
        // 遍历时清理已被回收的引用
        val iterator = listeners.iterator()
        while (iterator.hasNext()) {
            val listener = iterator.next().get()
            if (listener != null) {
                listener.onDataChanged(data)
            } else {
                iterator.remove()  // 清理无效引用
            }
        }
    }
}
```

### 4.3 WeakHashMap：自动清理的 Map

`WeakHashMap` 的 **Key 是弱引用**，当 Key 对象没有其他强引用时，整个键值对会被自动移除。

```kotlin
import java.util.WeakHashMap

// 场景：缓存 Activity 相关的数据
val activityDataCache = WeakHashMap<Activity, ActivityData>()

fun cacheData(activity: Activity, data: ActivityData) {
    activityDataCache[activity] = data
}

// 当 Activity 被销毁且没有其他强引用时，
// WeakHashMap 会自动移除这个条目，不会造成内存泄漏
```

**注意**：WeakHashMap 的 Value 仍然是强引用！如果 Value 反过来引用 Key，仍然会泄漏。

### 4.4 软引用 vs 弱引用

| 对比项 | 软引用 | 弱引用 |
|-------|-------|-------|
| 回收时机 | 内存不足时 | 下次 GC 时 |
| 生存能力 | 较强，能撑到内存紧张 | 较弱，随时可能被回收 |
| 适用场景 | 缓存（希望尽量保留） | 防泄漏（不影响对象生命周期） |
| 典型应用 | 图片缓存、对象池 | Handler、监听器、WeakHashMap |

> **记忆口诀**：软引用"软"在内存上（内存不足才回收），弱引用"弱"在 GC 面前（GC 一来就回收）。

## 五、虚引用（Phantom Reference）

### 5.1 是什么？

虚引用是最弱的引用，**形同虚设**——你永远无法通过虚引用获取到对象（`get()` 永远返回 null）。

那它有什么用？**追踪对象被回收的时机**。

```kotlin
import java.lang.ref.PhantomReference
import java.lang.ref.ReferenceQueue

// 虚引用必须配合引用队列使用
val referenceQueue = ReferenceQueue<User>()
val user = User("张三")
val phantomRef = PhantomReference(user, referenceQueue)

// 永远返回 null！
println(phantomRef.get())  // null

// 虚引用的价值在于：当 user 被回收后，phantomRef 会被加入 referenceQueue
```

### 5.2 为什么需要虚引用？

**核心价值**：在对象被回收**之后**执行清理操作。

与 `finalize()` 的区别：

| 对比项 | finalize() | 虚引用 + 引用队列 |
|-------|-----------|-----------------|
| 执行时机 | 对象回收前 | 对象回收后 |
| 可靠性 | 不保证执行 | 可靠 |
| 性能影响 | 延长对象生命周期 | 无影响 |
| 复活对象 | 可以（不推荐） | 不可能 |

### 5.3 典型应用：堆外内存管理

Android/Java 中最经典的应用是 `DirectByteBuffer` 的内存回收：

```kotlin
/**
 * 虚引用实战：追踪对象回收，释放关联资源
 * 
 * 场景：管理 Native 层分配的内存
 */
class NativeResourceTracker {
    
    // 引用队列：被回收的虚引用会进入这里
    private val referenceQueue = ReferenceQueue<Any>()
    
    // 记录虚引用和对应的 Native 指针
    private val pointerMap = ConcurrentHashMap<PhantomReference<*>, Long>()
    
    // 清理线程
    private val cleanerThread = Thread {
        while (true) {
            try {
                // 阻塞等待，直到有虚引用进入队列
                val ref = referenceQueue.remove()  // 阻塞方法
                
                // 对象已被回收，现在可以安全释放 Native 资源
                val nativePointer = pointerMap.remove(ref)
                if (nativePointer != null) {
                    freeNativeMemory(nativePointer)
                    Log.d("Cleaner", "Native memory freed: $nativePointer")
                }
            } catch (e: InterruptedException) {
                break
            }
        }
    }.apply { 
        isDaemon = true  // 守护线程，不阻止 JVM 退出
        start() 
    }
    
    /**
     * 注册需要追踪的对象
     */
    fun <T : Any> track(obj: T, nativePointer: Long): T {
        val phantomRef = PhantomReference(obj, referenceQueue)
        pointerMap[phantomRef] = nativePointer
        return obj
    }
    
    // 模拟释放 Native 内存
    private fun freeNativeMemory(pointer: Long) {
        // 实际项目中调用 JNI 方法释放
        // nativeFree(pointer)
    }
}

// 使用示例
val tracker = NativeResourceTracker()
val buffer = tracker.track(
    obj = ByteBuffer.allocateDirect(1024),
    nativePointer = 0x12345678L
)
// 当 buffer 被 GC 回收后，tracker 会自动释放 Native 内存
```

### 5.4 Java 9+ 的 Cleaner API

Java 9 引入了 `Cleaner` 类，封装了虚引用的使用，更加方便：

```kotlin
// Java 9+ 推荐方式（Android API 33+）
import java.lang.ref.Cleaner

class NativeResource : AutoCloseable {
    
    companion object {
        private val cleaner = Cleaner.create()
    }
    
    private val nativePointer: Long = allocateNative()
    
    // 清理动作（注意：不能引用外部类实例！）
    private class CleanupAction(private val pointer: Long) : Runnable {
        override fun run() {
            freeNative(pointer)
            Log.d("Cleaner", "Native resource cleaned: $pointer")
        }
    }
    
    private val cleanable = cleaner.register(this, CleanupAction(nativePointer))
    
    override fun close() {
        cleanable.clean()  // 手动清理
    }
    
    private external fun allocateNative(): Long
    
    companion object {
        @JvmStatic
        private external fun freeNative(pointer: Long)
    }
}
```

## 六、引用队列（ReferenceQueue）

### 6.1 是什么？

引用队列是软引用、弱引用、虚引用的"回收通知机制"。当引用对象被 GC 回收后，对应的 Reference 对象会被加入到关联的引用队列中。

```kotlin
import java.lang.ref.ReferenceQueue
import java.lang.ref.WeakReference

val queue = ReferenceQueue<User>()
var user: User? = User("张三")
val weakRef = WeakReference(user, queue)  // 关联引用队列

user = null  // 断开强引用
System.gc()  // 建议 GC

// 检查引用队列
val ref = queue.poll()  // 非阻塞，立即返回
if (ref != null) {
    println("User 对象已被回收")
}
```

### 6.2 引用队列的工作流程

```
┌─────────────────────────────────────────────────────────────┐
│                        GC 运行                               │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  检查 Reference 对象指向的实际对象是否可达                      │
│  - 软引用：内存不足时回收                                      │
│  - 弱引用：直接回收                                           │
│  - 虚引用：直接回收                                           │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  如果对象被回收，且 Reference 关联了 ReferenceQueue            │
│  → 将 Reference 对象加入队列                                  │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  应用程序可以从队列中取出 Reference，执行清理逻辑               │
│  - queue.poll()：非阻塞，立即返回                             │
│  - queue.remove()：阻塞，等待有元素                           │
│  - queue.remove(timeout)：超时等待                           │
└─────────────────────────────────────────────────────────────┘
```

### 6.3 实战：检测内存泄漏（LeakCanary 原理）

LeakCanary 检测内存泄漏的核心原理就是**弱引用 + 引用队列**：

```kotlin
/**
 * 简化版内存泄漏检测器
 * 
 * 原理：
 * 1. 用弱引用包装 Activity，关联引用队列
 * 2. Activity 销毁后，触发 GC
 * 3. 如果 Activity 被正常回收，弱引用会进入队列
 * 4. 如果队列中没有这个弱引用，说明 Activity 泄漏了
 */
class SimpleLeakDetector {
    
    private val referenceQueue = ReferenceQueue<Activity>()
    
    // 存储所有待检测的弱引用，Key 是唯一标识
    private val watchedRefs = ConcurrentHashMap<String, KeyedWeakReference>()
    
    // 带标识的弱引用
    class KeyedWeakReference(
        activity: Activity,
        val key: String,
        queue: ReferenceQueue<Activity>
    ) : WeakReference<Activity>(activity, queue)
    
    /**
     * 监控 Activity
     */
    fun watch(activity: Activity) {
        val key = UUID.randomUUID().toString()
        val ref = KeyedWeakReference(activity, key, referenceQueue)
        watchedRefs[key] = ref
        
        // 延迟 5 秒后检查
        Handler(Looper.getMainLooper()).postDelayed({
            checkForLeak(key)
        }, 5000)
    }
    
    private fun checkForLeak(key: String) {
        // 先清理已回收的引用
        removeWeaklyReachableRefs()
        
        val ref = watchedRefs[key]
        if (ref != null) {
            // 引用还在 watchedRefs 中，说明没有进入队列，可能泄漏
            // 再触发一次 GC 确认
            Runtime.getRuntime().gc()
            Thread.sleep(100)
            removeWeaklyReachableRefs()
            
            if (watchedRefs.containsKey(key)) {
                // 确认泄漏！
                Log.e("LeakDetector", "内存泄漏检测到: ${ref.get()?.javaClass?.name}")
                // 实际的 LeakCanary 会在这里 dump heap 并分析引用链
            }
        }
    }
    
    /**
     * 从队列中取出已回收的引用，从 watchedRefs 中移除
     */
    private fun removeWeaklyReachableRefs() {
        var ref: KeyedWeakReference?
        do {
            ref = referenceQueue.poll() as? KeyedWeakReference
            if (ref != null) {
                watchedRefs.remove(ref.key)
            }
        } while (ref != null)
    }
}
```

## 七、总结与最佳实践

### 7.1 选择指南

```
需要缓存数据，希望内存不足时自动释放？
    → 软引用（但更推荐 LruCache）

需要引用对象，但不想影响其生命周期？
    → 弱引用

需要在对象被回收后执行清理操作？
    → 虚引用 + 引用队列（或 Cleaner API）

普通场景？
    → 强引用，注意及时置空
```

### 7.2 常见误区

| 误区 | 正确理解 |
|-----|---------|
| 软引用可以完全避免 OOM | ❌ 软引用只是延缓，如果创建速度 > 回收速度，仍会 OOM |
| 弱引用对象立即被回收 | ❌ 是"下次 GC 时"回收，不是"立即" |
| 虚引用可以获取对象 | ❌ `get()` 永远返回 null |
| WeakHashMap 的 Value 也是弱引用 | ❌ 只有 Key 是弱引用 |

### 7.3 Android 开发中的实践建议

1. **Handler 泄漏**：静态内部类 + 弱引用 + onDestroy 清理消息
2. **图片缓存**：优先用 Glide/Coil，它们内部已经处理好了
3. **监听器管理**：用弱引用或确保 remove，推荐用 Lifecycle 感知组件
4. **Native 资源**：用虚引用或 Cleaner 确保释放

### 7.4 面试高频问题

**Q1：四大引用的区别是什么？**

> 按强度排序：强 > 软 > 弱 > 虚。强引用永不回收；软引用内存不足时回收，适合缓存；弱引用下次 GC 就回收，适合防泄漏；虚引用 get() 永远返回 null，配合引用队列追踪对象回收。

**Q2：为什么 Handler 会导致内存泄漏？怎么解决？**

> 匿名内部类持有外部类（Activity）的强引用，如果 Handler 有延迟消息，Activity 销毁后仍被引用无法回收。解决：静态内部类 + 弱引用持有 Activity，onDestroy 时清理消息队列。

**Q3：LeakCanary 是怎么检测内存泄漏的？**

> 核心原理是弱引用 + 引用队列。监控 Activity 时创建弱引用并关联队列，Activity 销毁后触发 GC，如果弱引用没有进入队列，说明 Activity 仍被强引用，即发生泄漏。然后 dump heap 分析引用链找到泄漏源。

**Q4：软引用和 LruCache 哪个更适合做图片缓存？**

> LruCache 更适合。软引用的回收时机不可控，可能刚存入就被回收，缓存命中率不稳定。LruCache 可以设置最大容量，按 LRU 算法淘汰，行为可预测。现代图片库（Glide、Coil）都是用 LruCache + DiskLruCache 的组合。
