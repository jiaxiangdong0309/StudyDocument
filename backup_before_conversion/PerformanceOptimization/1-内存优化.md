# 内存优化 (Memory Optimization)

## 为什么要做内存优化？

内存就像你家的储物空间——东西放太多会堆不下（OOM），东西乱放会找不到（内存抖动），放了不用还占地方（内存泄漏）。

**内存问题的三大表现**：

| 问题 | 用户感知 | 后果 |
|-----|---------|------|
| 内存泄漏 | App 越用越慢，最终闪退 | 可用内存逐渐减少 |
| 内存溢出 (OOM) | App 直接闪退 | 申请内存超过系统限制 |
| 内存抖动 | 界面卡顿、掉帧 | 频繁 GC 导致卡顿 |

## 一、内存基础知识

### 1.2 内存限制

每个 App 都有内存上限，超过就会 OOM：

```kotlin
// 获取当前 App 的内存限制
val activityManager = getSystemService(Context.ACTIVITY_SERVICE) as ActivityManager

// 普通堆内存限制（通常 192MB ~ 512MB）
val heapSize = activityManager.memoryClass  // 单位 MB

// 大堆内存限制（manifest 中设置 largeHeap=true）
val largeHeapSize = activityManager.largeMemoryClass  // 单位 MB
```

> **注意**：largeHeap 不是银弹，滥用会导致 GC 时间更长，应该是最后手段。

### 1.3 GC 机制

GC（垃圾回收）就像保洁阿姨打扫房间——会暂停你的工作（Stop The World）。

**GC 触发条件**：
- 内存不足时
- 主动调用 `System.gc()`（不推荐）
- 后台进程被回收时

**ART 的 GC 改进**：
- 并发 GC，减少停顿时间
- 压缩 GC，减少内存碎片
- 分代回收，提高效率

## 二、内存泄漏

### 2.1 什么是内存泄漏？

内存泄漏就像借了东西不还——对象已经没用了，但还被引用着，GC 回收不了。

```
正常情况：Activity 销毁 → GC 回收 → 内存释放 ✓
内存泄漏：Activity 销毁 → 还被引用 → GC 无法回收 ✗
```

### 2.2 常见内存泄漏场景

#### 场景一：非静态内部类持有外部类引用

```kotlin
// ❌ 错误示例：Handler 导致内存泄漏
class LeakyActivity : AppCompatActivity() {
    
    // 非静态内部类隐式持有外部类引用
    private val handler = object : Handler(Looper.getMainLooper()) {
        override fun handleMessage(msg: Message) {
            // 如果消息队列中还有消息，Activity 就无法被回收
            updateUI()
        }
    }
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        // 发送一个延迟消息
        handler.sendEmptyMessageDelayed(0, 60_000)  // 60秒后执行
        // 如果用户在 60 秒内退出 Activity，就会泄漏
    }
}
```

```kotlin
// ✅ 正确示例：使用静态内部类 + 弱引用
class SafeActivity : AppCompatActivity() {
    
    // 静态内部类不持有外部类引用
    private class SafeHandler(activity: SafeActivity) : Handler(Looper.getMainLooper()) {
        // 弱引用，不影响 GC 回收
        private val activityRef = WeakReference(activity)
        
        override fun handleMessage(msg: Message) {
            // 获取 Activity，如果已被回收则为 null
            activityRef.get()?.updateUI()
        }
    }
    
    private val handler = SafeHandler(this)
    
    override fun onDestroy() {
        super.onDestroy()
        // 移除所有消息，避免泄漏
        handler.removeCallbacksAndMessages(null)
    }
}
```

#### 场景二：单例持有 Context

```kotlin
// ❌ 错误示例：单例持有 Activity Context
object LeakySingleton {
    private var context: Context? = null
    
    fun init(context: Context) {
        // Activity Context 被单例持有，永远无法回收
        this.context = context
    }
}

// ✅ 正确示例：使用 Application Context
object SafeSingleton {
    private var context: Context? = null
    
    fun init(context: Context) {
        // Application Context 生命周期与 App 一致，不会泄漏
        this.context = context.applicationContext
    }
}
```

#### 场景三：监听器/回调未注销

```kotlin
// ❌ 错误示例：注册了监听器但没有注销
class LeakyActivity : AppCompatActivity() {
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        // 注册广播接收器
        registerReceiver(receiver, IntentFilter("action"))
        // 如果 onDestroy 中没有 unregister，就会泄漏
    }
}

// ✅ 正确示例：配对注册和注销
class SafeActivity : AppCompatActivity() {
    
    private val receiver = MyBroadcastReceiver()
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        registerReceiver(receiver, IntentFilter("action"))
    }
    
    override fun onDestroy() {
        super.onDestroy()
        // 一定要注销！
        unregisterReceiver(receiver)
    }
}
```

#### 场景四：资源未关闭

```kotlin
// ❌ 错误示例：资源未关闭
fun readFile() {
    val inputStream = FileInputStream("file.txt")
    val content = inputStream.read()
    // 忘记关闭流，导致资源泄漏
}

// ✅ 正确示例：使用 use 扩展函数自动关闭
fun readFile() {
    FileInputStream("file.txt").use { inputStream ->
        val content = inputStream.read()
    }  // 自动关闭，即使发生异常
}
```

#### 场景五：集合持有对象引用

```kotlin
// ❌ 错误示例：静态集合持有对象引用
object Cache {
    private val list = mutableListOf<Activity>()
    
    fun add(activity: Activity) {
        list.add(activity)  // Activity 无法被回收
    }
}

// ✅ 正确示例：使用弱引用集合
object Cache {
    // WeakHashMap 的 key 是弱引用
    private val map = WeakHashMap<Activity, Any>()
    
    fun add(activity: Activity) {
        map[activity] = Any()  // Activity 可以正常被回收
    }
}
```

### 2.3 内存泄漏检测工具

#### LeakCanary（推荐）

最流行的内存泄漏检测工具，自动检测并生成报告。

```kotlin
// build.gradle
dependencies {
    // 只在 debug 版本引入
    debugImplementation 'com.squareup.leakcanary:leakcanary-android:2.12'
}
```

使用方式：**什么都不用做**，LeakCanary 会自动：
1. 监控 Activity、Fragment 的销毁
2. 检测是否存在泄漏
3. 生成泄漏堆栈报告
4. 以通知形式提醒开发者

#### Android Profiler

Android Studio 内置工具，可以：
- 实时查看内存使用情况
- 手动触发 GC
- 捕获堆转储（Heap Dump）
- 分析对象分配

#### MAT (Memory Analyzer Tool)

Eclipse 出品的专业内存分析工具：
1. 从 Android Profiler 导出 `.hprof` 文件
2. 使用 `hprof-conv` 转换格式
3. 用 MAT 打开分析

**MAT 常用功能**：
- **Histogram**：查看对象数量和大小
- **Dominator Tree**：查看对象支配关系
- **Path to GC Roots**：查看对象被谁引用

## 三、内存溢出 (OOM)

### 3.1 OOM 的原因

| 原因 | 说明 | 解决方案 |
|-----|------|---------|
| 内存泄漏积累 | 小泄漏积少成多 | 使用 LeakCanary 检测 |
| 大图片加载 | 图片占用内存过大 | 压缩、采样、分块加载 |
| 大量创建对象 | 频繁创建大对象 | 对象池、复用 |
| Native 内存 | Native 层内存泄漏 | 检查 JNI 代码 |

### 3.2 图片内存优化

图片是内存大户，一张 1920x1080 的图片：
- ARGB_8888：1920 × 1080 × 4 = **8MB**
- RGB_565：1920 × 1080 × 2 = **4MB**

#### 采样压缩

```kotlin
// 只加载需要的尺寸，而不是原图
fun decodeSampledBitmap(
    res: Resources,
    resId: Int,
    reqWidth: Int,
    reqHeight: Int
): Bitmap {
    // 第一步：只读取图片尺寸，不加载到内存
    val options = BitmapFactory.Options().apply {
        inJustDecodeBounds = true
    }
    BitmapFactory.decodeResource(res, resId, options)
    
    // 第二步：计算采样率
    options.inSampleSize = calculateInSampleSize(options, reqWidth, reqHeight)
    
    // 第三步：按采样率加载图片
    options.inJustDecodeBounds = false
    return BitmapFactory.decodeResource(res, resId, options)
}

// 计算采样率（向下取 2 的幂次）
fun calculateInSampleSize(
    options: BitmapFactory.Options,
    reqWidth: Int,
    reqHeight: Int
): Int {
    val (height, width) = options.outHeight to options.outWidth
    var inSampleSize = 1
    
    if (height > reqHeight || width > reqWidth) {
        val halfHeight = height / 2
        val halfWidth = width / 2
        
        while (halfHeight / inSampleSize >= reqHeight 
            && halfWidth / inSampleSize >= reqWidth) {
            inSampleSize *= 2
        }
    }
    return inSampleSize
}
```

#### 使用图片加载库

推荐使用 Glide、Coil 等库，它们已经帮你处理了：


### 3.3 对象池复用

频繁创建销毁对象会导致内存抖动，可以使用对象池复用：

```kotlin
// Message 对象池示例（系统实现）
// 获取时从池中取
val message = Message.obtain()

// 用完后回收到池中
message.recycle()

// 自定义对象池
class ObjectPool<T>(
    private val maxSize: Int,
    private val factory: () -> T,
    private val reset: (T) -> Unit
) {
    private val pool = ArrayDeque<T>()
    
    fun obtain(): T {
        return pool.pollFirst() ?: factory()
    }
    
    fun recycle(obj: T) {
        if (pool.size < maxSize) {
            reset(obj)  // 重置对象状态
            pool.addLast(obj)
        }
    }
}
```

## 四、内存抖动

### 4.1 什么是内存抖动？

内存抖动就像你一直在收拾房间——东西不断进进出出，累死了但房间还是乱。

**表现**：短时间内频繁创建和销毁对象，导致频繁 GC。

**危害**：
- GC 时会 Stop The World，造成卡顿
- 内存碎片化，加重后续分配压力

### 4.2 常见场景

```kotlin
// ❌ 错误示例：在 onDraw 中创建对象
class BadView(context: Context) : View(context) {
    override fun onDraw(canvas: Canvas) {
        // onDraw 可能每秒调用 60 次
        // 每次都创建新对象，导致内存抖动
        val paint = Paint()  // ❌ 不要在这里创建
        val rect = Rect(0, 0, width, height)  // ❌ 不要在这里创建
        
        canvas.drawRect(rect, paint)
    }
}

// ✅ 正确示例：对象复用
class GoodView(context: Context) : View(context) {
    // 提前创建，复用
    private val paint = Paint()
    private val rect = Rect()
    
    override fun onDraw(canvas: Canvas) {
        rect.set(0, 0, width, height)
        canvas.drawRect(rect, paint)
    }
}
```

```kotlin
// ❌ 错误示例：循环中创建字符串
fun badStringConcat(list: List<String>): String {
    var result = ""
    for (item in list) {
        result += item  // 每次 += 都创建新的 String 对象
    }
    return result
}

// ✅ 正确示例：使用 StringBuilder
fun goodStringConcat(list: List<String>): String {
    return buildString {
        for (item in list) {
            append(item)
        }
    }
}
```

## 六、面试题精选

### Q1：什么是内存泄漏？如何检测？

**答**：内存泄漏是指对象已经不再使用，但由于被其他对象引用而无法被 GC 回收。检测方法：
1. **LeakCanary**：自动检测 Activity、Fragment 泄漏
2. **Android Profiler**：手动分析堆转储
3. **MAT**：深度分析复杂泄漏场景

### Q2：Handler 为什么会导致内存泄漏？

**答**：非静态内部类的 Handler 隐式持有外部 Activity 的引用。当 Activity 销毁时，如果消息队列中还有该 Handler 发送的消息，消息持有 Handler，Handler 持有 Activity，导致 Activity 无法被回收。

**解决方案**：
1. 使用静态内部类 + WeakReference
2. 在 onDestroy 中调用 `handler.removeCallbacksAndMessages(null)`

### Q3：如何优化 Bitmap 内存？

**答**：
1. **采样压缩**：设置 inSampleSize，只加载需要的尺寸
2. **格式优化**：使用 RGB_565 代替 ARGB_8888（省一半内存）
3. **缓存策略**：使用 LruCache 内存缓存
4. **及时回收**：不用时调用 recycle()
5. **使用图片库**：Glide、Coil 已经做了大量优化

### Q4：什么是内存抖动？如何避免？

**答**：内存抖动是短时间内频繁创建和销毁对象，导致频繁 GC 和卡顿。

**避免方法**：
1. 避免在循环、onDraw、onMeasure 中创建对象
2. 使用对象池复用对象
3. 使用 StringBuilder 代替字符串拼接
4. 使用 Android Profiler 检测分配热点

### Q5：Activity 内存泄漏的常见原因有哪些？

**答**：
1. **Handler 泄漏**：非静态内部类持有外部引用
2. **单例持有 Context**：应使用 ApplicationContext
3. **静态变量**：静态变量持有 Activity 引用
4. **监听器未注销**：EventBus、广播接收器等
5. **异步任务**：AsyncTask、Thread 未取消
6. **动画未停止**：属性动画在 Activity 销毁后继续运行
