# 首屏渲染优化实战

## 前言

首屏渲染速度直接决定用户对 App 的第一印象。目标是让用户感知「秒开」，即首屏完全渲染时间控制在 **400ms 以内**。

本文档从**问题排查**到**优化方案**，完整覆盖首屏渲染优化的方方面面。

---

### 1.2 setContentView 为什么慢？

```kotlin
// setContentView 内部做了什么？
public void setContentView(@LayoutRes int layoutResID) {
    // 1. 获取 Window 的 DecorView
    getWindow().setContentView(layoutResID);
    // 内部调用 LayoutInflater.inflate()
}

// LayoutInflater.inflate() 做了什么？
public View inflate(@LayoutRes int resource, ViewGroup root, boolean attachToRoot) {
    // 1. 获取 XML 解析器（IO 操作）
    XmlResourceParser parser = res.getLayout(resource);
    
    // 2. 解析 XML，创建 View 树
    return inflate(parser, root, attachToRoot);
}

// inflate 解析过程
View inflate(XmlPullParser parser, ViewGroup root, boolean attachToRoot) {
    while ((type = parser.next()) != XmlPullParser.END_DOCUMENT) {
        String name = parser.getName();  // 如 "TextView"
        
        // 3. 反射创建 View（最耗时的地方！）
        View view = createViewFromTag(root, name, context, attrs);
        
        // createViewFromTag 内部：
        // Class clazz = Class.forName("android.widget.TextView");
        // Constructor constructor = clazz.getConstructor(Context.class, AttributeSet.class);
        // View view = constructor.newInstance(context, attrs);
        
        // 4. 递归处理子 View
        rInflateChildren(parser, view, attrs, true);
    }
}
```

**耗时分布**：

| 步骤 | 耗时占比 | 说明 |
|-----|---------|------|
| XML 解析 | ~20% | 读取文件、解析 XML 结构 |
| 反射创建 View | ~50% | Class.forName + newInstance |
| 设置属性 | ~20% | 解析 attrs，设置 padding/background 等 |
| 构建 View 树 | ~10% | addView、建立父子关系 |

### 2.4 代码中添加自定义 Trace 标记

系统的 Trace 标记粒度可能不够，可以在代码中添加自定义标记：

```kotlin
import android.os.Trace

class MainActivity : AppCompatActivity() {
    
    override fun onCreate(savedInstanceState: Bundle?) {
        // 开始标记
        Trace.beginSection("MainActivity_onCreate")
        super.onCreate(savedInstanceState)
        
        // 标记 setContentView
        Trace.beginSection("MainActivity_setContentView")
        setContentView(R.layout.activity_main)
        Trace.endSection()  // 结束 setContentView 标记
        
        // 标记初始化 View
        Trace.beginSection("MainActivity_initViews")
        initViews()
        Trace.endSection()
        
        // 标记加载数据
        Trace.beginSection("MainActivity_loadData")
        loadData()
        Trace.endSection()
        
        Trace.endSection()  // 结束 onCreate 标记
    }
    
    private fun initViews() {
        Trace.beginSection("initViews_findViews")
        val recyclerView = findViewById<RecyclerView>(R.id.recycler_view)
        val toolbar = findViewById<Toolbar>(R.id.toolbar)
        Trace.endSection()
        
        Trace.beginSection("initViews_setupRecyclerView")
        recyclerView.layoutManager = LinearLayoutManager(this)
        recyclerView.adapter = MyAdapter()
        Trace.endSection()
    }
}
```

### 2.5 实际排查案例

```
问题：首页打开需要 800ms，用户感知明显卡顿

排查过程：
1. 用 Perfetto 抓取启动 trace
2. 发现 setContentView 耗时 280ms（正常应该 < 50ms）
3. 展开 inflate 详情，发现：
   - ConstraintLayout: 20ms（正常）
   - RecyclerView: 15ms（正常）
   - WebView: 180ms ← 罪魁祸首！
   - CustomBannerView: 65ms ← 也很慢

分析：
- WebView 首次创建需要初始化 WebKit 内核，非常耗时
- CustomBannerView 内部有复杂的自定义绘制

解决方案：
- WebView 使用 ViewStub 延迟加载，首屏不需要立即显示
- CustomBannerView 改为 ViewStub，首屏先显示占位图
- 预热：在 Application 中提前创建一个 WebView 放入缓存池
```

## 三、优化方案一：AsyncLayoutInflater 异步加载

### 3.1 原理

把 inflate 操作放到后台线程执行，完成后回调到主线程。

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    AsyncLayoutInflater 原理                                  │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   主线程                                后台线程                              │
│   ┌─────────────────────────┐          ┌─────────────────────────┐         │
│   │ 1. 调用 inflate()        │          │                         │         │
│   │    传入 layoutRes        │ ──────→  │ 2. 执行 XML 解析         │         │
│   │                         │          │    反射创建 View        │         │
│   │                         │          │    构建 View 树         │         │
│   │ 4. 收到回调              │ ←──────  │ 3. inflate 完成         │         │
│   │    设置 ContentView     │          │    通过 Handler 回调    │         │
│   │    初始化 View          │          │                         │         │
│   └─────────────────────────┘          └─────────────────────────┘         │
│                                                                             │
│   优点：inflate 过程不阻塞主线程，用户可以看到 loading 状态                   │
│   缺点：增加了首屏显示的延迟（因为要等后台线程完成）                           │
│         适合布局复杂但不需要立即显示的场景                                    │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 3.2 基本使用

```kotlin
class MainActivity : AppCompatActivity() {
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        
        // ❌ 同步加载，阻塞主线程 15-30ms
        // setContentView(R.layout.activity_main)
        
        // ✅ 异步加载，不阻塞主线程
        // 先设置一个简单的加载中布局（可选）
        setContentView(R.layout.activity_loading)
        
        // 异步 inflate 真正的布局
        AsyncLayoutInflater(this).inflate(
            R.layout.activity_main,
            null
        ) { view, resid, parent ->
            // 这个回调在主线程执行
            // 替换为真正的布局
            setContentView(view)
            
            // 初始化 View（此时 View 已经创建好了）
            initViews()
        }
    }
}
```

### 3.3 局限性和解决方案

```kotlin
/**
 * AsyncLayoutInflater 的局限性
 */

// 局限1：不能使用 <fragment> 标签
// 原因：Fragment 的创建必须在主线程
// 解决：改用 FragmentContainerView + 代码动态添加 Fragment
// ❌ 不能这样写
<fragment
    android:name="com.example.MyFragment"
    ... />
// ✅ 应该这样写
<androidx.fragment.app.FragmentContainerView
    android:id="@+id/fragment_container"
    ... />
// 然后在代码中添加 Fragment

// 局限2：不能使用 <merge> 作为根标签
// 原因：merge 需要知道 parent，但异步时 parent 可能还没准备好
// 解决：在 merge 外面包一层 FrameLayout

// 局限3：如果 inflate 过程中有异常，会静默失败并回退到主线程同步加载
// 需要注意日志监控

// 局限4：自定义 View 的构造函数中不能有主线程检查
class BadCustomView(context: Context, attrs: AttributeSet?) : View(context, attrs) {
    init {
        // ❌ 这会导致 AsyncLayoutInflater 失败
        if (Looper.myLooper() != Looper.getMainLooper()) {
            throw IllegalStateException("Must be called on main thread")
        }
    }
}
```

## 四、优化方案二：X2C（XML to Code）

### 4.1 原理

在编译期把 XML 转换成 Java/Kotlin 代码，跳过运行时的 XML 解析和反射。

```xml
<!-- 原始 XML：activity_main.xml -->
<LinearLayout
    android:layout_width="match_parent"
    android:layout_height="match_parent"
    android:orientation="vertical">
    
    <TextView
        android:id="@+id/tv_title"
        android:layout_width="wrap_content"
        android:layout_height="wrap_content"
        android:text="Hello"
        android:textSize="16sp"/>
        
    <ImageView
        android:id="@+id/iv_icon"
        android:layout_width="100dp"
        android:layout_height="100dp"
        android:src="@drawable/icon"/>
        
</LinearLayout>
```

```kotlin
// X2C 编译后生成的代码（示意）
class X2C_activity_main : IViewCreator {
    
    override fun createView(context: Context): View {
        // 直接 new，不需要反射！
        val root = LinearLayout(context).apply {
            layoutParams = ViewGroup.LayoutParams(
                ViewGroup.LayoutParams.MATCH_PARENT,
                ViewGroup.LayoutParams.MATCH_PARENT
            )
            orientation = LinearLayout.VERTICAL
        }
        
        val tvTitle = TextView(context).apply {
            id = R.id.tv_title
            layoutParams = LinearLayout.LayoutParams(
                ViewGroup.LayoutParams.WRAP_CONTENT,
                ViewGroup.LayoutParams.WRAP_CONTENT
            )
            text = "Hello"
            textSize = 16f
        }
        root.addView(tvTitle)
        
        val ivIcon = ImageView(context).apply {
            id = R.id.iv_icon
            layoutParams = LinearLayout.LayoutParams(
                100.dp, 100.dp
            )
            setImageResource(R.drawable.icon)
        }
        root.addView(ivIcon)
        
        return root
    }
}
```

### 4.2 性能对比

| 对比项 | XML inflate | X2C |
|-------|------------|-----|
| XML 解析 | 需要（~2ms） | 不需要 |
| 反射创建 View | 需要（~5ms） | 不需要（直接 new） |
| 编译期检查 | 无 | 有（类型安全） |
| 性能提升 | 基准 | 提升 30-50% |

## 五、优化方案三：ViewStub 延迟加载

### 5.1 适用场景

首页有些模块不需要立即显示：
- 错误页面
- 引导页/弹窗
- WebView（首次创建很慢）
- 非首屏可见的模块

### 5.2 实现方式

```xml
<!-- activity_main.xml -->
<FrameLayout
    android:layout_width="match_parent"
    android:layout_height="match_parent">
    
    <!-- 首屏必须显示的内容 -->
    <LinearLayout
        android:id="@+id/main_content"
        android:layout_width="match_parent"
        android:layout_height="match_parent">
        <!-- 核心 UI -->
    </LinearLayout>
    
    <!-- 错误页：不是首屏必须的，使用 ViewStub -->
    <ViewStub
        android:id="@+id/stub_error"
        android:layout_width="match_parent"
        android:layout_height="match_parent"
        android:layout="@layout/layout_error"/>
    
    <!-- WebView：首次创建很慢，延迟加载 -->
    <ViewStub
        android:id="@+id/stub_webview"
        android:layout_width="match_parent"
        android:layout_height="match_parent"
        android:layout="@layout/layout_webview"/>
        
</FrameLayout>
```

```kotlin
class MainActivity : AppCompatActivity() {
    
    // ViewStub 只能 inflate 一次，用变量记录
    private var errorView: View? = null
    private var webViewContainer: View? = null
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)
        
        // 首屏加载完成，用户已经看到内容了
        // 然后在空闲时预加载 WebView（如果需要）
        preloadWebViewWhenIdle()
    }
    
    /**
     * 显示错误页（按需加载）
     */
    fun showError() {
        if (errorView == null) {
            // 首次调用时才 inflate
            errorView = findViewById<ViewStub>(R.id.stub_error).inflate()
        }
        errorView?.visibility = View.VISIBLE
    }
    
    /**
     * 在主线程空闲时预加载 WebView
     * 
     * 为什么用 IdleHandler？
     * 因为 WebView 首次创建需要 100-200ms，不能在首屏加载时做
     * 但如果等用户点击才加载，又会感觉卡
     * 所以在首屏显示完、主线程空闲时预加载
     */
    private fun preloadWebViewWhenIdle() {
        Looper.myQueue().addIdleHandler {
            // 主线程空闲了，开始预加载 WebView
            if (webViewContainer == null) {
                webViewContainer = findViewById<ViewStub>(R.id.stub_webview).inflate()
                // WebView 预热：加载一个空白页
                webViewContainer?.findViewById<WebView>(R.id.webview)?.loadUrl("about:blank")
            }
            false  // 返回 false，只执行一次
        }
    }
}
```

## 六、优化方案四：布局预加载

### 6.1 原理

在 Splash 页面显示时，提前加载首页布局。等到首页 Activity 创建时，直接使用预加载好的 View。

### 6.2 实现

```kotlin
/**
 * 布局预加载管理器
 * 
 * 原理：在 Splash 显示期间，利用后台线程预先 inflate 首页布局
 * 等到首页 Activity 创建时，直接使用预加载好的 View
 */
object LayoutPreloader {
    
    // 缓存预加载的 View
    private val viewCache = ConcurrentHashMap<Int, View>()
    
    // 标记是否正在预加载
    private val loadingLayouts = ConcurrentHashMap<Int, Boolean>()
    
    /**
     * 异步预加载布局
     * 
     * @param context Application Context（避免内存泄漏）
     * @param layoutRes 布局资源 ID
     */
    fun preload(context: Context, @LayoutRes layoutRes: Int) {
        // 避免重复预加载
        if (viewCache.containsKey(layoutRes) || loadingLayouts[layoutRes] == true) {
            return
        }
        
        loadingLayouts[layoutRes] = true
        
        AsyncLayoutInflater(context).inflate(layoutRes, null) { view, resid, _ ->
            viewCache[resid] = view
            loadingLayouts.remove(resid)
        }
    }
    
    /**
     * 获取预加载的布局
     * 
     * @return 预加载的 View，如果没有则返回 null
     */
    fun getPreloadedView(@LayoutRes layoutRes: Int): View? {
        return viewCache.remove(layoutRes)
    }
    
    /**
     * 清理缓存（Activity 销毁时调用）
     */
    fun clear() {
        viewCache.clear()
        loadingLayouts.clear()
    }
}

/**
 * Splash 页面：在这里预加载首页布局
 */
class SplashActivity : AppCompatActivity() {
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_splash)
        
        // Splash 显示的同时，预加载首页布局
        LayoutPreloader.preload(applicationContext, R.layout.activity_main)
        
        // 模拟 Splash 显示 2 秒
        lifecycleScope.launch {
            delay(2000)
            startActivity(Intent(this@SplashActivity, MainActivity::class.java))
            finish()
        }
    }
}

/**
 * 首页：优先使用预加载的布局
 */
class MainActivity : AppCompatActivity() {
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        
        // 尝试获取预加载的布局
        val preloadedView = LayoutPreloader.getPreloadedView(R.layout.activity_main)
        
        if (preloadedView != null) {
            // 命中预加载！直接使用，省去 inflate 时间
            setContentView(preloadedView)
        } else {
            // 未命中，回退到正常加载
            setContentView(R.layout.activity_main)
        }
        
        initViews()
    }
}
```

## 七、优化方案五：WebView 预热池

### 7.1 为什么 WebView 需要预热？

WebView 首次创建非常耗时（100-200ms），因为需要初始化 WebKit 内核。后续创建会快很多（~20ms）。

如果首页有 WebView，必须做预热。

### 7.2 实现

```kotlin
/**
 * WebView 缓存池
 * 
 * 为什么需要？
 * 1. WebView 首次创建需要初始化 WebKit 内核，耗时 100-200ms
 * 2. 后续创建会快很多（~20ms），因为内核已经初始化了
 * 3. 但如果 WebView 被销毁，下次又要重新初始化
 * 
 * 解决方案：
 * 1. Application 启动时预创建一个 WebView（初始化内核）
 * 2. 需要使用时从池中取，用完放回池中
 * 3. 这样用户永远不会感受到首次创建的延迟
 */
object WebViewPool {
    
    private val pool = LinkedList<WebView>()
    private const val MAX_SIZE = 2
    private var isInitialized = false
    
    /**
     * 预热 WebView 池
     * 
     * 在 Application.onCreate() 中调用
     * 使用 IdleHandler 避免影响启动速度
     */
    fun init(context: Context) {
        if (isInitialized) return
        isInitialized = true
        
        // 在主线程空闲时预创建 WebView
        Looper.myQueue().addIdleHandler {
            preCreateWebView(context.applicationContext)
            false  // 只执行一次
        }
    }
    
    private fun preCreateWebView(context: Context) {
        val startTime = System.currentTimeMillis()
        
        // 创建 WebView（这里会初始化 WebKit 内核）
        val webView = WebView(MutableContextWrapper(context))
        
        // 基本配置
        webView.settings.apply {
            javaScriptEnabled = true
            domStorageEnabled = true
        }
        
        // 预加载空白页，进一步预热
        webView.loadUrl("about:blank")
        
        pool.offer(webView)
        
        Log.d("WebViewPool", "预创建 WebView 耗时: ${System.currentTimeMillis() - startTime}ms")
    }
    
    /**
     * 获取 WebView
     */
    fun obtain(context: Context): WebView {
        val webView = pool.poll() ?: WebView(MutableContextWrapper(context))
        
        // 重要：更换 Context（避免内存泄漏）
        val contextWrapper = webView.context as? MutableContextWrapper
        contextWrapper?.baseContext = context
        
        return webView
    }
    
    /**
     * 回收 WebView
     */
    fun recycle(webView: WebView) {
        if (pool.size >= MAX_SIZE) {
            // 池满了，直接销毁
            webView.destroy()
            return
        }
        
        // 清理状态
        webView.stopLoading()
        webView.loadUrl("about:blank")
        webView.clearHistory()
        
        pool.offer(webView)
    }
    
    /**
     * 可变的 ContextWrapper
     * 
     * 为什么需要？
     * WebView 持有 Context 引用，如果使用 Activity Context，会导致内存泄漏
     * 使用 MutableContextWrapper 可以在需要时切换到正确的 Context
     */
    class MutableContextWrapper(base: Context) : ContextWrapper(base) {
        var baseContext: Context
            get() = super.getBaseContext()
            set(value) {
                // 通过反射设置 mBase 字段
                try {
                    val field = ContextWrapper::class.java.getDeclaredField("mBase")
                    field.isAccessible = true
                    field.set(this, value)
                } catch (e: Exception) {
                    e.printStackTrace()
                }
            }
    }
}
```

### 7.3 使用方式

```kotlin
// Application 中预热
class MyApplication : Application() {
    override fun onCreate() {
        super.onCreate()
        WebViewPool.init(this)
    }
}

// Activity 中使用
class WebViewActivity : AppCompatActivity() {
    private lateinit var webView: WebView
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_webview)
        
        // 从池中获取 WebView（瞬间完成！）
        webView = WebViewPool.obtain(this)
        
        // 添加到布局
        findViewById<FrameLayout>(R.id.webview_container).addView(webView)
        
        // 加载页面
        webView.loadUrl("https://www.example.com")
    }
    
    override fun onDestroy() {
        super.onDestroy()
        // 从布局移除
        (webView.parent as? ViewGroup)?.removeView(webView)
        // 回收到池中
        WebViewPool.recycle(webView)
    }
}
```

## 九、面试回答模板

> **面试官**：你们项目首页加载慢是怎么优化的？
>
> **回答**：
>
> 我们首页 Activity 的 `setContentView` 耗时 180ms，用户感知明显白屏。
>
> **排查过程**：
> 1. 用 Perfetto 抓取启动 trace，添加自定义 Trace 标记
> 2. 发现 inflate 耗时 180ms，其中 WebView 占了 150ms
> 3. 另外首页有 12 个模块，全部一次性渲染也很慢
>
> **优化方案**：
> 1. **WebView 预热池**：在 Application 启动后通过 IdleHandler 预创建 WebView，初始化 WebKit 内核，用户打开首页时直接从池中取
> 2. **ViewStub 延迟加载**：首屏非必须的模块（广告位、推荐位）用 ViewStub，等首屏渲染完再加载
> 3. **布局预加载**：Splash 显示期间用 AsyncLayoutInflater 预加载首页布局
> 4. **分帧加载**：剩余模块通过 IdleHandler 分批加载，每帧只加载 1-2 个模块
>
> **效果**：
> - setContentView 从 180ms 降到 30ms
> - 首屏完全渲染时间从 800ms 降到 350ms
> - 用户感知秒开
