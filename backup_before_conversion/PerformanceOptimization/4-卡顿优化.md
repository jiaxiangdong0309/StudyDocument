# 卡顿优化 (Jank Optimization)

## 为什么要做卡顿优化？

卡顿就像看电影时画面卡住——用户体验极差。Android 界面刷新率是 60 帧/秒，每帧只有 16.6ms，超时就会掉帧卡顿。

**卡顿问题的表现**：

| 表现 | 用户感知 | 严重程度 |
|-----|---------|---------|
| 掉帧 | 动画不流畅、滑动卡顿 | 中等 |
| 卡死 | 界面无响应 | 严重 |
| ANR | 弹出「应用无响应」对话框 | 严重 |

## 一、卡顿原理

### 1.1 帧渲染机制

```
┌─────────────────────────────────────────────────────────────────┐
│                    VSync 和帧渲染                                │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   VSync 信号（每 16.6ms 触发一次）                                │
│   ↓           ↓           ↓           ↓                         │
│   ┌───┐       ┌───┐       ┌───┐       ┌───┐                     │
│   │ 1 │       │ 2 │       │ 3 │       │ 4 │   ← 帧编号           │
│   └───┘       └───┘       └───┘       └───┘                     │
│   16.6ms      16.6ms      16.6ms      16.6ms                    │
│                                                                 │
│   理想情况：每帧都在 16.6ms 内完成渲染                             │
│                                                                 │
│   ↓           ↓           ↓           ↓                         │
│   ┌───┐       ┌───────────┐ ┌───┐     ┌───┐                     │
│   │ 1 │       │     2     │ │ 3 │     │ 4 │                     │
│   └───┘       └───────────┘ └───┘     └───┘                     │
│               ← 超过16.6ms，掉帧！                                │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 1.2 主线程模型

Android 的主线程负责：
- 处理用户输入事件
- 更新 UI
- 执行生命周期回调
- 执行 Handler 消息

```
┌─────────────────────────────────────────────────────────────────┐
│                      主线程消息队列                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   Looper.loop() 不断从消息队列取消息执行                          │
│                                                                 │
│   ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐                       │
│   │Input│→│Draw │→│耗时 │→│点击 │→│刷新 │→ ...                  │
│   │事件 │ │渲染 │ │任务 │ │处理 │ │UI  │                        │
│   └─────┘ └─────┘ └─────┘ └─────┘ └─────┘                       │
│                      ↑                                          │
│                   如果某个消息执行超时，                           │
│                   后续消息就会被阻塞                              │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 1.3 卡顿的本质

**掉帧**：主线程在一个 VSync 周期内没有完成 UI 渲染

**ANR**：主线程被长时间阻塞
- Input 事件超过 5s 未响应
- BroadcastReceiver 超过 10s 未完成
- Service 超过 20s 未完成

## 二、常见卡顿原因

### 2.1 主线程耗时操作

```kotlin
// ❌ 错误示例：主线程进行网络请求
button.setOnClickListener {
    val response = OkHttpClient().newCall(request).execute()  // 阻塞主线程！
    textView.text = response.body?.string()
}

// ✅ 正确示例：异步请求
button.setOnClickListener {
    lifecycleScope.launch {
        val response = withContext(Dispatchers.IO) {
            OkHttpClient().newCall(request).execute()
        }
        textView.text = response.body?.string()
    }
}
```

### 2.2 复杂布局

```kotlin
// ❌ 错误示例：在列表 item 中使用复杂布局
class BadAdapter : RecyclerView.Adapter<BadViewHolder>() {
    
    override fun onBindViewHolder(holder: BadViewHolder, position: Int) {
        // 每次绑定都进行复杂计算
        holder.textView.text = calculateComplexText(data[position])
        
        // 动态添加 View
        holder.container.removeAllViews()
        data[position].items.forEach { item ->
            holder.container.addView(createItemView(item))
        }
    }
}

// ✅ 正确示例：优化布局和数据绑定
class GoodAdapter : RecyclerView.Adapter<GoodViewHolder>() {
    
    override fun onBindViewHolder(holder: GoodViewHolder, position: Int) {
        // 使用已经计算好的数据
        holder.textView.text = data[position].displayText
        
        // 使用 RecyclerView 复用 View
        holder.recyclerView.adapter = itemAdapter
        itemAdapter.submitList(data[position].items)
    }
}
```

### 2.3 频繁 GC

参考内存优化章节，内存抖动会导致频繁 GC，造成卡顿。

### 2.4 锁竞争

```kotlin
// ❌ 错误示例：主线程等待锁
class BadExample {
    private val lock = Object()
    private var data: String? = null
    
    // 子线程持有锁进行耗时操作
    fun loadData() {
        thread {
            synchronized(lock) {
                // 耗时操作
                data = fetchFromNetwork()
            }
        }
    }
    
    // 主线程需要等待锁
    fun showData() {
        synchronized(lock) {  // 可能等待很久！
            textView.text = data
        }
    }
}

// ✅ 正确示例：使用非阻塞方式
class GoodExample {
    private val _data = MutableLiveData<String>()
    val data: LiveData<String> = _data
    
    fun loadData() {
        thread {
            val result = fetchFromNetwork()
            _data.postValue(result)
        }
    }
}
```

### 2.5 Binder 调用阻塞

```kotlin
// ❌ 错误示例：主线程进行 Binder 调用
button.setOnClickListener {
    // getInstalledPackages 是 Binder 调用，可能耗时
    val packages = packageManager.getInstalledPackages(0)
    adapter.submitList(packages)
}

// ✅ 正确示例：异步调用
button.setOnClickListener {
    lifecycleScope.launch {
        val packages = withContext(Dispatchers.IO) {
            packageManager.getInstalledPackages(0)
        }
        adapter.submitList(packages)
    }
}
```

## 三、卡顿检测

### 3.1 使用 BlockCanary

类似 LeakCanary，自动检测卡顿：

```kotlin
// build.gradle
dependencies {
    debugImplementation 'com.github.markzhai:blockcanary-android:1.5.0'
}
```

```kotlin
// Application 中初始化
class MyApplication : Application() {
    
    override fun onCreate() {
        super.onCreate()
        BlockCanary.install(this, BlockCanaryContext()).start()
    }
}

// 自定义配置
class BlockCanaryContext : BlockCanaryContext() {
    
    override fun provideBlockThreshold(): Int {
        // 超过 500ms 就上报
        return 500
    }
    
    override fun providePath(): String {
        return "/blockcanary/"
    }
}
```

### 3.2 使用 Choreographer

```kotlin
// 监控每帧耗时
class FrameMonitor {
    
    private var lastFrameTime = 0L
    
    fun start() {
        Choreographer.getInstance().postFrameCallback(object : Choreographer.FrameCallback {
            override fun doFrame(frameTimeNanos: Long) {
                if (lastFrameTime != 0L) {
                    val frameTime = (frameTimeNanos - lastFrameTime) / 1_000_000
                    if (frameTime > 16) {
                        Log.w("FrameMonitor", "掉帧！帧耗时: ${frameTime}ms")
                    }
                }
                lastFrameTime = frameTimeNanos
                
                // 继续监控下一帧
                Choreographer.getInstance().postFrameCallback(this)
            }
        })
    }
}
```

### 3.3 使用 Looper Printer

```kotlin
// 监控消息处理耗时
class MessageMonitor {
    
    fun start() {
        Looper.getMainLooper().setMessageLogging { msg ->
            if (msg.startsWith(">>>>> Dispatching")) {
                // 消息开始处理
                startTime = SystemClock.elapsedRealtime()
            } else if (msg.startsWith("<<<<< Finished")) {
                // 消息处理完成
                val cost = SystemClock.elapsedRealtime() - startTime
                if (cost > 100) {
                    Log.w("MessageMonitor", "消息处理耗时: ${cost}ms")
                }
            }
        }
    }
}
```

## 四、ANR 分析

### 4.1 ANR 日志

ANR 发生时，系统会生成日志：

```bash
# 查看 ANR 日志
adb shell cat /data/anr/traces.txt

# 或者使用 bugreport
adb bugreport
```

### 4.2 常见 ANR 原因

| 原因 | 典型场景 | 解决方案 |
|-----|---------|---------|
| 主线程 IO | 读写大文件、数据库操作 | 放到子线程 |
| 死锁 | 多线程锁竞争 | 检查锁顺序、使用 tryLock |
| 主线程等待 | wait/sleep/join | 避免在主线程等待 |
| Binder 调用超时 | 系统服务调用慢 | 异步调用 |
| CPU 占用过高 | 后台线程抢占 CPU | 控制线程优先级 |

### 4.3 ANR 分析示例

```
// traces.txt 示例
```

## 五、优化实践

### 5.1 异步化

```kotlin
// 使用协程处理耗时操作
class ViewModel : ViewModel() {
    
    fun loadData() {
        viewModelScope.launch {
            // IO 线程执行耗时操作
            val data = withContext(Dispatchers.IO) {
                repository.fetchData()
            }
            // 主线程更新 UI
            _uiState.value = data
        }
    }
}
```

### 5.2 分帧处理

```kotlin
// 大量数据分帧处理，避免一次性处理导致卡顿
class ChunkedProcessor {
    
    fun processLargeList(list: List<Item>) {
        val handler = Handler(Looper.getMainLooper())
        val chunkSize = 20
        var index = 0
        
        fun processChunk() {
            val end = minOf(index + chunkSize, list.size)
            
            // 处理当前批次
            for (i in index until end) {
                processItem(list[i])
            }
            
            index = end
            
            // 还有数据，下一帧继续处理
            if (index < list.size) {
                handler.post { processChunk() }
            }
        }
        
        processChunk()
    }
}
```

### 5.3 避免频繁刷新

```kotlin
// 使用 DiffUtil 优化 RecyclerView 刷新
class MyAdapter : ListAdapter<Item, ViewHolder>(DiffCallback()) {
    
    class DiffCallback : DiffUtil.ItemCallback<Item>() {
        override fun areItemsTheSame(old: Item, new: Item) = old.id == new.id
        override fun areContentsTheSame(old: Item, new: Item) = old == new
    }
}

// 使用节流/防抖避免频繁触发
class SearchViewModel : ViewModel() {
    
    private val _searchQuery = MutableStateFlow("")
    
    val searchResults = _searchQuery
        .debounce(300)  // 300ms 内不触发
        .distinctUntilChanged()
        .flatMapLatest { query ->
            repository.search(query)
        }
}
```

### 5.4 预加载和缓存

```kotlin
// RecyclerView 预加载
recyclerView.layoutManager = LinearLayoutManager(context).apply {
    // 预加载额外的 item
    initialPrefetchItemCount = 4
}

// 数据预加载
class PrefetchManager {
    
    fun prefetchNextPage(currentPage: Int) {
        // 提前加载下一页数据到缓存
        thread {
            val nextPageData = api.loadPage(currentPage + 1)
            cache.put(currentPage + 1, nextPageData)
        }
    }
}
```

### 5.5 线程优先级

```kotlin
// 降低后台线程优先级，避免抢占主线程 CPU
thread {
    // 设置为后台优先级
    Process.setThreadPriority(Process.THREAD_PRIORITY_BACKGROUND)
    
    // 执行后台任务
    doBackgroundWork()
}
```

## 七、面试题精选

### Q1：什么是卡顿？如何检测？

**答**：卡顿是由于主线程在一个 VSync 周期（16.6ms）内没有完成 UI 渲染，导致掉帧。

**检测方法**：
1. **BlockCanary**：自动检测主线程耗时
2. **Choreographer**：监控每帧耗时
3. **Looper Printer**：监控消息处理耗时
4. **Systrace**：系统级性能分析

### Q2：ANR 的原因和解决方案？

**答**：ANR 是主线程被长时间阻塞。

**常见原因**：
1. 主线程 IO 操作
2. 死锁
3. 主线程等待（wait/sleep）
4. Binder 调用超时

**解决方案**：
1. 耗时操作放子线程
2. 避免死锁，检查锁顺序
3. 使用协程/异步框架
4. Binder 调用异步化

### Q3：如何优化 RecyclerView 卡顿？

**答**：
1. **布局优化**：减少 item 布局层级
2. **复用优化**：设置 setHasFixedSize(true)
3. **预加载**：设置 initialPrefetchItemCount
4. **DiffUtil**：使用 DiffUtil 替代 notifyDataSetChanged
5. **缓存优化**：设置 setItemViewCacheSize
6. **滑动时暂停**：滑动时暂停图片加载

### Q4：主线程为什么不能做耗时操作？

**答**：
1. **掉帧**：每帧只有 16.6ms，耗时操作会导致掉帧
2. **ANR**：超过 5s 会触发 ANR
3. **用户体验**：用户无法与界面交互

**主线程应该做的**：
- 更新 UI
- 处理用户输入
- 轻量级的数据处理

### Q5：如何分析 ANR 日志？

**答**：
1. 查看主线程状态（Running/Blocked/Waiting）
2. 找到阻塞位置（方法栈）
3. 如果是等待锁，找到锁持有者
4. 分析 CPU 使用情况
5. 检查是否有 IO wait
