# App 保活 - 基础篇

## 一、为什么需要 App 保活？

### 1.1 问题背景

打开微信聊天，锁屏玩了会游戏，回来发现消息没收到——这就是 App 被系统杀死了。

Android 系统的内存管理策略是：**当内存不足时，杀掉不重要的进程来释放内存**。这就像餐厅座位有限，不消费的客人会被请走，给新客人腾位置。

### 1.2 哪些 App 需要保活？

| App 类型 | 是否需要保活 | 原因 |
|---------|-------------|------|
| 即时通讯（微信、钉钉） | ✅ 必须 | 需要实时接收消息 |
| 音乐播放器 | ✅ 必须 | 需要后台播放 |
| 导航软件 | ✅ 必须 | 需要持续定位和语音播报 |
| 运动健康 | ✅ 需要 | 需要持续记录运动数据 |
| 新闻资讯 | ❌ 不需要 | 打开时获取最新内容即可 |
| 电商购物 | ❌ 不需要 | 不需要后台运行 |

> **核心观点**：不是所有 App 都需要保活，滥用保活是对用户的不尊重。

## 二、Android 进程管理机制

### 2.1 进程优先级（重要！）

Android 把进程分成 5 个等级，**优先级越高越不容易被杀**：

```
┌─────────────────────────────────────────────────────┐
│   前台进程（Foreground Process）     最高优先级      │
│   ↓ 正在与用户交互的进程                            │
├─────────────────────────────────────────────────────┤
│   可见进程（Visible Process）                        │
│   ↓ 用户可见但不在前台（如弹窗后面的 Activity）       │
├─────────────────────────────────────────────────────┤
│   服务进程（Service Process）                        │
│   ↓ 运行着 Service 但用户不可见                      │
├─────────────────────────────────────────────────────┤
│   缓存进程（Cached Process）                         │
│   ↓ 已经退到后台，系统随时可能杀掉                    │
├─────────────────────────────────────────────────────┤
│   空进程（Empty Process）           最低优先级       │
│   没有任何活动组件，仅为了缓存加速下次启动            │
└─────────────────────────────────────────────────────┘
```

### 2.2 什么是 oom_adj？

`oom_adj` 是系统给每个进程打的"分数"，**数值越小，优先级越高，越不容易被杀**。

| oom_adj 值 | 含义 | 示例 |
|-----------|------|------|
| -1000 | 系统进程，不能杀 | system_server |
| -900 | 持久进程 | 电话进程 |
| 0 | 前台进程 | 正在使用的 App |
| 100 | 可见进程 | 有可见 Activity |
| 200 | 可感知进程 | 前台服务 |
| 300 | 备份进程 | 正在备份 |
| 700 | 服务进程 | 普通后台服务 |
| 900 | 缓存进程（之前使用过） | 刚退到后台 |
| 999 | 缓存进程（空进程） | 长时间不用 |

> **大白话**：oom_adj 就像信用分，分数越低信用越好，银行（系统）越不会找你麻烦（杀掉）。

### 2.3 LMK（Low Memory Killer）

LMK 是 Android 的"内存清道夫"，当内存不足时，它会按照 oom_adj 从高到低杀进程。

```
内存告急 → LMK 介入 → 找 oom_adj 最高的进程 → 杀掉释放内存 → 还不够就继续杀
```

**形象比喻**：LMK 就像公司裁员，先裁临时工（空进程），再裁外包（缓存进程），实在不行才动正式员工（服务进程）。

## 三、基础保活方案

### 3.1 前台服务（最正规的方案）

**原理**：前台服务会在通知栏显示一个常驻通知，告诉系统"我正在干活"，系统就不会轻易杀掉它。

**oom_adj 变化**：普通后台服务是 700，前台服务是 200，优先级大大提升。

```kotlin
// 1. 创建前台服务
class MusicService : Service() {
    
    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        // 创建通知渠道（Android 8.0+ 必须）
        createNotificationChannel()
        
        // 创建通知
        val notification = NotificationCompat.Builder(this, CHANNEL_ID)
            .setContentTitle("音乐播放中")
            .setContentText("正在播放：周杰伦 - 晴天")
            .setSmallIcon(R.drawable.ic_music)
            .build()
        
        // 关键：调用 startForeground 提升为前台服务
        // 第一个参数是通知 ID，必须大于 0
        startForeground(1, notification)
        
        return START_STICKY  // 被杀后尝试重启
    }
    
    private fun createNotificationChannel() {
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.O) {
            val channel = NotificationChannel(
                CHANNEL_ID,
                "音乐播放",
                NotificationManager.IMPORTANCE_LOW  // 低重要性，不会发出声音
            )
            val manager = getSystemService(NotificationManager::class.java)
            manager.createNotificationChannel(channel)
        }
    }
    
    override fun onBind(intent: Intent?): IBinder? = null
    
    companion object {
        private const val CHANNEL_ID = "music_channel"
    }
}
```

**AndroidManifest.xml 配置**：

```xml
<!-- Android 9+ 需要声明前台服务权限 -->
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<!-- Android 14+ 需要声明前台服务类型权限 -->
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_MEDIA_PLAYBACK" />

<service
    android:name=".MusicService"
    android:foregroundServiceType="mediaPlayback"  <!-- Android 10+ 必须声明类型 -->
    android:exported="false" />
```

**Android 版本适配要点**：

| Android 版本 | 要求 |
|-------------|------|
| 8.0 (API 26) | 必须使用通知渠道，后台启动服务有限制 |
| 9.0 (API 28) | 需要 `FOREGROUND_SERVICE` 权限 |
| 10 (API 29) | 前台服务需要声明 `foregroundServiceType` |
| 12 (API 31) | 不能从后台启动前台服务（有例外） |
| 14 (API 34) | 前台服务类型细化，需要对应权限 |

### 3.2 Service 的 START_STICKY

```kotlin
override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
    return START_STICKY  // 被杀后，系统会尝试重启服务
}
```

**返回值对比**：

| 返回值 | 行为 | 适用场景 |
|-------|------|---------|
| `START_STICKY` | 被杀后重启，intent 为 null | 音乐播放器（重启后可恢复状态） |
| `START_NOT_STICKY` | 被杀后不重启 | 一次性任务 |
| `START_REDELIVER_INTENT` | 被杀后重启，重传最后的 intent | 需要完整参数的任务 |

> **注意**：START_STICKY 只是"尝试"重启，在内存极度紧张时不一定能重启成功。

### 3.3 JobScheduler（系统级任务调度）

**原理**：把任务交给系统统一调度，系统会在合适的时机执行，而且多个 App 的任务会被合并执行，省电。

```kotlin
// 1. 定义 JobService
class SyncJobService : JobService() {
    
    override fun onStartJob(params: JobParameters?): Boolean {
        // 在后台线程执行任务
        Thread {
            // 执行同步操作
            syncData()
            // 任务完成，通知系统
            jobFinished(params, false)  // false 表示不需要重新调度
        }.start()
        
        return true  // true 表示任务还在执行中（异步）
    }
    
    override fun onStopJob(params: JobParameters?): Boolean {
        // 任务被系统中断时调用
        return true  // true 表示需要重新调度
    }
    
    private fun syncData() {
        // 实际的同步逻辑
    }
}

// 2. 调度任务
fun scheduleJob(context: Context) {
    val jobScheduler = context.getSystemService(JobScheduler::class.java)
    
    val jobInfo = JobInfo.Builder(
        JOB_ID,
        ComponentName(context, SyncJobService::class.java)
    )
        .setRequiredNetworkType(JobInfo.NETWORK_TYPE_ANY)  // 需要网络
        .setPersisted(true)  // 设备重启后保留任务
        .setPeriodic(15 * 60 * 1000)  // 最小周期 15 分钟
        .build()
    
    jobScheduler.schedule(jobInfo)
}
```

**AndroidManifest.xml**：

```xml
<uses-permission android:name="android.permission.RECEIVE_BOOT_COMPLETED" />

<service
    android:name=".SyncJobService"
    android:permission="android.permission.BIND_JOB_SERVICE"
    android:exported="false" />
```

### 3.4 WorkManager（推荐方案）

**为什么推荐 WorkManager？**

WorkManager 是 Jetpack 组件，它会根据 Android 版本**自动选择最佳实现**：

- Android 6.0+：使用 JobScheduler
- Android 5.x：使用 GcmNetworkManager（如果有）
- 更低版本：使用 AlarmManager + BroadcastReceiver

```kotlin
// 1. 添加依赖
// implementation "androidx.work:work-runtime-ktx:2.9.0"

// 2. 定义 Worker
class SyncWorker(context: Context, params: WorkerParameters) : Worker(context, params) {
    
    override fun doWork(): Result {
        return try {
            // 执行同步操作
            syncData()
            Result.success()
        } catch (e: Exception) {
            Result.retry()  // 失败后重试
        }
    }
    
    private fun syncData() {
        // 实际的同步逻辑
    }
}

// 3. 调度任务
fun scheduleSync(context: Context) {
    // 约束条件
    val constraints = Constraints.Builder()
        .setRequiredNetworkType(NetworkType.CONNECTED)  // 需要网络
        .setRequiresBatteryNotLow(true)  // 电量不能太低
        .build()
    
    // 创建周期性任务（最小 15 分钟）
    val syncRequest = PeriodicWorkRequestBuilder<SyncWorker>(
        15, TimeUnit.MINUTES  // 周期
    )
        .setConstraints(constraints)
        .setBackoffCriteria(  // 重试策略
            BackoffPolicy.LINEAR,
            10, TimeUnit.SECONDS
        )
        .build()
    
    // 提交任务
    WorkManager.getInstance(context).enqueueUniquePeriodicWork(
        "sync_work",
        ExistingPeriodicWorkPolicy.KEEP,  // 如果已存在，保留原任务
        syncRequest
    )
}
```

**WorkManager vs JobScheduler 对比**：

| 特性 | WorkManager | JobScheduler |
|-----|-------------|--------------|
| API 兼容性 | API 14+ | API 21+ |
| 链式任务 | ✅ 支持 | ❌ 不支持 |
| 约束条件 | ✅ 丰富 | ✅ 支持 |
| 任务持久化 | ✅ 自动 | 需要 setPersisted |
| Google 推荐 | ✅ 官方推荐 | 逐渐被 WorkManager 替代 |

## 四、保活的"副作用"

### 4.1 对用户的影响

| 影响 | 说明 |
|-----|------|
| 耗电 | 后台进程需要 CPU 时间 |
| 耗流量 | 如果有网络请求 |
| 占内存 | 进程常驻会占用内存 |
| 影响其他 App | 你不死，别人就可能被杀 |

### 4.2 对开发者的影响

- 需要处理各种边界情况
- 需要适配各厂商的"特殊处理"
- 需要跟进 Android 版本更新
- 可能被应用商店下架（如果被认定为"流氓软件"）

## 五、面试题检验

### Q1：Android 进程优先级有哪些？前台服务属于哪一级？

**答案**：

Android 进程分为 5 级（从高到低）：前台进程 → 可见进程 → 服务进程 → 缓存进程 → 空进程。

前台服务属于**可感知进程**，oom_adj 值为 200，介于可见进程（100）和服务进程（700）之间。

这个设计的原因是：前台服务虽然用户看不到界面，但通知栏的常驻通知让用户"感知"到它的存在，所以优先级比普通后台服务高很多。

---

### Q2：START_STICKY 和 START_REDELIVER_INTENT 有什么区别？

**答案**：

两者都是服务被杀后会重启，区别在于**重启时的 Intent**：

- `START_STICKY`：重启时 intent 为 null，适合不依赖启动参数的场景（如音乐播放器）
- `START_REDELIVER_INTENT`：重启时会重传最后一次的 intent，适合需要完整参数的场景（如下载服务）

选择依据：如果你的服务启动时需要用到 intent 里的数据，用 REDELIVER；如果不需要，用 STICKY 更简单。

---

### Q3：为什么推荐用 WorkManager 而不是直接用 JobScheduler？

**答案**：

三个原因：

1. **兼容性**：WorkManager 支持 API 14+，JobScheduler 只支持 API 21+
2. **功能更强**：WorkManager 支持链式任务、唯一任务替换、灵活的重试策略
3. **自动适配**：WorkManager 会根据系统版本自动选择最佳实现（JobScheduler、GcmNetworkManager 或 AlarmManager）

本质上，WorkManager 是对 JobScheduler 等方案的封装和增强，Google 官方推荐使用 WorkManager。
