## 1. const 构造函数

### 底层原理

Flutter 在 build 阶段通过 `Widget.canUpdate()` 判断是否需要更新 Element。`canUpdate` 的条件是 `runtimeType` 和 `key` 相同。但即使满足条件，框架仍会调用 `build()` 重建子树。

`const` 的优化点在于：**相同参数的 const Widget 在编译期就是同一个对象实例**（存储在常量池），框架通过 `identical()` 引用相等性判断，直接跳过整个子树的重建。

```dart
// 这两个是同一个对象
const Text('Hello') == const Text('Hello'); // identical: true
```

### 有效场景

- 静态文本、图标、间距等不依赖运行时数据的 Widget
- 列表中重复出现的固定 Widget
- 主题配置、样式对象

```dart
// ✅ 有效
const SizedBox(height: 16)
const Icon(Icons.star)
const EdgeInsets.all(16)
const Text('固定标题')
```

### 无效 / 反效果场景

- 参数包含运行时变量，编译器直接报错，无法使用 const
- Widget 本身不提供 const 构造函数（如 `Scaffold`）
- 单次使用的 Widget，const 带来的收益几乎为零

```dart
// ❌ 无法使用 const（dynamicValue 是运行时变量）
Text(dynamicValue)

// ❌ 即使写了 const，子树中有非 const 也无法传递优化
const Column(
  children: [nonConstWidget], // 编译错误
)
```

### 边界情况

- `const` 只能用于拥有 `const` 构造函数的类，且所有参数也必须是编译期常量
- 父 Widget 是 const，不代表子 Widget 自动是 const，需要逐层标注
- 在热重载频繁的开发阶段，const 的收益不如生产环境明显

## 2. RepaintBoundary

### 底层原理

Flutter 渲染管线分为三棵树：Widget 树 → Element 树 → RenderObject 树。绘制阶段，RenderObject 会将绘制指令写入 `Layer`。

`RepaintBoundary` 会创建一个独立的 `OffsetLayer`（离屏缓冲区），将子树的绘制结果缓存到 GPU 纹理中。当子树内部发生重绘时，只重新绘制该层，父层直接复用缓存纹理，不参与重绘。

```
父层 [缓存纹理] ← 不重绘
  └── RepaintBoundary [独立 Layer]
        └── 动画 Widget ← 只重绘这里
```

### 有效场景

- 频繁变化的动画区域（如旋转、位移动画）
- 复杂列表项中独立变化的子组件
- 视频播放器、地图等高频更新区域

```dart
// ✅ 动画组件独立成层，不影响父层
RepaintBoundary(
  child: AnimatedBuilder(
    animation: _controller,
    builder: (context, child) => RotationTransition(...),
  ),
)
```

### 无效 / 反效果场景

- 包裹静态 Widget：没有重绘，缓存层白白占用 GPU 内存
- 嵌套过多 RepaintBoundary：每层都需要离屏缓冲区，GPU 内存压力大
- 包裹整个页面：适得其反，增加内存开销

```dart
// ❌ 静态内容，无收益
RepaintBoundary(child: const Text('Hello'))

// ❌ 过度使用，每个列表项都包裹
ListView.builder(
  itemBuilder: (context, index) => RepaintBoundary(
    child: SimpleListTile(), // 简单 UI 不需要
  ),
)
```

### 边界情况

- 每个 RepaintBoundary 消耗额外 GPU 内存（离屏缓冲区大小 = 组件尺寸 × 像素密度）
- 与 `Transform` 结合时，Transform 本身已经会创建独立层，RepaintBoundary 可能冗余
- 可以用 Flutter DevTools 的 "Highlight Repaints" 功能可视化重绘区域，再决定是否添加

## 3. ValueNotifier / ValueListenableBuilder

### 底层原理

`setState()` 会触发当前 State 的整个 `build()` 方法重新执行，重建整棵子树。

`ValueNotifier<T>` 是一个轻量级的 `ChangeNotifier`，只持有单个值。`ValueListenableBuilder` 只监听该值，当值变化时，**只重建 builder 返回的子树**，不触发父 Widget 的 build。

`child` 参数是关键优化点：传入 `child` 的 Widget 不会随值变化而重建。

```dart
ValueListenableBuilder<int>(
  valueListenable: _counter,
  builder: (context, value, child) {
    return Row(children: [Text('$value'), child!]); // child 不重建
  },
  child: const ExpensiveStaticWidget(), // 只构建一次
)
```

### 有效场景

- 计数器、进度条、开关等单一状态的局部更新
- 表单验证错误提示（只更新提示文字）
- 购物车数量角标

```dart
// ✅ 只有数字部分重建，其他 UI 不受影响
final _count = ValueNotifier<int>(0);

ValueListenableBuilder<int>(
  valueListenable: _count,
  builder: (_, value, __) => Text('$value'),
)
```

### 无效 / 反效果场景

- 状态之间有依赖关系（A 变化导致 B 也要变化），ValueNotifier 难以处理
- 需要跨组件共享复杂状态，应使用 Provider / Riverpod
- 频繁创建和销毁 ValueNotifier 而不 dispose，导致内存泄漏

```dart
// ❌ 忘记 dispose
@override
void dispose() {
  _counter.dispose(); // 必须调用！
  super.dispose();
}
```

### 边界情况

- `child` 参数传入的 Widget 不能依赖 `value`，否则传入无意义
- 多个 ValueListenableBuilder 嵌套会导致代码可读性下降，考虑用 Provider
- ValueNotifier 的 `==` 比较：相同值赋值不会触发通知（`value = value` 无效）

## 4. ListView.builder vs ListView

### 底层原理

`ListView(children: [...])` 会在初始化时创建所有子 Widget，全部挂载到 Element 树，即使不在视口内也占用内存。

`ListView.builder` 使用 `SliverList` + `RenderSliverList`，只创建当前视口内（加上少量预加载缓冲区）的 Widget。滚动时动态创建新 item，销毁移出视口的 item。

### 有效场景

- 列表项数量 > 50，或数量不确定（动态加载）
- 无限滚动、分页加载
- 每个 item 构建成本较高

```dart
// ✅ 大列表
ListView.builder(
  itemCount: items.length,
  itemBuilder: (context, index) => ItemWidget(item: items[index]),
)
```

### 无效 / 反效果场景

- 列表项 < 20 个：`ListView` 更简洁，性能差异可忽略
- 需要在列表中使用 `shrinkWrap: true`：会强制计算所有子项高度，失去懒加载优势

```dart
// ❌ shrinkWrap 破坏懒加载
ListView.builder(
  shrinkWrap: true, // 强制计算全部高度，等同于 ListView
  itemBuilder: ...,
)
```

### 边界情况

- 不提供 `itemCount` 时，列表无限延伸，需要在 `itemBuilder` 中返回 `null` 终止
- 列表项有状态时，必须提供稳定的 `key`，否则滚动时状态会错乱
- `cacheExtent` 参数控制预加载范围，默认 250px，可根据场景调整

## 5. AutomaticKeepAliveClientMixin

### 底层原理

`ListView.builder` 默认会销毁移出视口的 item 的 State。`AutomaticKeepAliveClientMixin` 通过向上发送 `KeepAliveNotification`，告知 `SliverList` 保留该 item 的 Element 和 State，不销毁。

### 有效场景

- `TabBarView` 中的 Tab 页面，保持滚动位置和表单输入
- `PageView` 中的页面状态保持
- 列表中有用户交互状态的 item（如展开/收起）

```dart
class _MyTabState extends State<MyTab> with AutomaticKeepAliveClientMixin {
  @override
  bool get wantKeepAlive => true;

  @override
  Widget build(BuildContext context) {
    super.build(context); // 必须调用，否则 KeepAlive 失效
    return ListView(...);
  }
}
```

### 无效 / 反效果场景

- 所有列表项都设置 `wantKeepAlive = true`：等同于 `ListView`，内存线性增长
- 与普通 `ListView`（非 builder）配合：ListView 本身不销毁 item，mixin 无意义

### 边界情况

- `wantKeepAlive` 可以动态返回，根据条件决定是否保活
- 保活的 item 数量应有上限，避免内存溢出
- 与 `IndexedStack` 相比：IndexedStack 始终保留所有子 Widget，KeepAlive 按需保留

## 6. Opacity vs AnimatedOpacity vs ColorFiltered

### 底层原理

| Widget | 实现方式 | 性能 |
|--------|---------|------|
| `Opacity` | 创建独立合成层，GPU 混合 | 中（有离屏缓冲） |
| `AnimatedOpacity` | 同上，但通过动画驱动 | 中 |
| `ColorFiltered` | 颜色矩阵变换，GPU 计算 | 较低 |
| `Visibility` | 直接从树中移除/保留 | 最高（完全不渲染） |

`Opacity` 不是简单地修改 alpha 值，它会创建一个独立的合成层（类似 RepaintBoundary），这意味着额外的 GPU 内存开销。

### 有效场景

```dart
// ✅ 需要透明度动画时
AnimatedOpacity(
  opacity: _isVisible ? 1.0 : 0.0,
  duration: const Duration(milliseconds: 300),
  child: MyWidget(),
)

// ✅ 需要完全隐藏且不占位时
Visibility(
  visible: _isVisible,
  child: MyWidget(),
)

// ✅ 需要占位但不显示时
Visibility(
  visible: _isVisible,
  maintainSize: true,
  maintainAnimation: true,
  maintainState: true,
  child: MyWidget(),
)
```

### 无效 / 反效果场景

- 用 `Opacity(opacity: 0)` 隐藏 Widget：Widget 仍然参与布局和绘制，只是不可见
- 频繁在 0 和 1 之间切换 `Opacity`：应使用 `AnimatedOpacity` 或条件渲染
- 大量嵌套 `ColorFiltered`：GPU 内存压力大

### 边界情况

- `opacity: 0` 的 Widget 仍然响应点击事件，需要配合 `IgnorePointer`
- `AnimatedOpacity` 在动画期间会创建合成层，动画结束后释放
- 如果只需要灰度效果，`ColorFiltered` 比 `Opacity` 更合适

## 7. ImageCache / precacheImage

### 底层原理

Flutter 的 `ImageCache` 是全局单例，存储已解码的图片数据（`ImageInfo`）。图片解码是 CPU 密集型操作，缓存后可直接复用解码结果。

`precacheImage` 提前触发图片加载和解码，将结果存入缓存，避免首次显示时的解码延迟（卡顿）。

### 有效场景

```dart
// ✅ 页面初始化时预加载关键图片
@override
void didChangeDependencies() {
  super.didChangeDependencies();
  precacheImage(const AssetImage('assets/hero.png'), context);
}

// ✅ 调整缓存大小（根据设备内存）
PaintingBinding.instance.imageCache.maximumSize = 100;
PaintingBinding.instance.imageCache.maximumSizeBytes = 50 << 20; // 50MB
```

### 无效 / 反效果场景

- 预加载所有图片：内存溢出，得不偿失
- 对网络图片使用 precacheImage 但网络不稳定：可能阻塞页面初始化
- 缓存大小设置过大：低内存设备触发 OOM

### 边界情况

- `ImageCache` 使用 LRU 策略，超出限制时自动淘汰最久未使用的图片
- 网络图片的 HTTP 缓存和 Flutter 的 ImageCache 是两层独立缓存
- 清理缓存：`PaintingBinding.instance.imageCache.clear()`

## 8. isolate / compute

### 底层原理

Dart 是单线程模型，所有 UI 操作在主 isolate 执行。耗时操作（> 16ms）会阻塞主线程，导致掉帧。

`Isolate` 是独立的 Dart 执行环境，有独立的内存堆，通过消息传递（`SendPort` / `ReceivePort`）通信，不共享内存，天然线程安全。

`compute(fn, message)` 是便捷封装：创建临时 isolate → 执行函数 → 返回结果 → 销毁 isolate。

### 有效场景

```dart
// ✅ 大 JSON 解析
final users = await compute(parseUsers, jsonString);

List<User> parseUsers(String json) {
  return (jsonDecode(json) as List).map((e) => User.fromJson(e)).toList();
}

// ✅ 图片处理
final thumbnail = await compute(generateThumbnail, imageBytes);

// ✅ 复杂算法
final result = await compute(runAlgorithm, inputData);
```

### 无效 / 反效果场景

- 轻量级任务（< 1ms）：创建 isolate 本身有 ~1ms 开销，得不偿失
- 频繁调用 `compute`：每次都创建销毁 isolate，开销累积
- 需要访问 Flutter UI 或 Platform Channel：isolate 中无法访问

```dart
// ❌ 轻量任务不值得用 compute
final result = await compute((x) => x * 2, 5); // 开销 >> 收益
```

### 边界情况

- `compute` 的参数和返回值必须可以通过 `SendPort` 传递（基本类型、List、Map，不能是 Widget）
- 长期运行的任务应使用持久 isolate（`Isolate.spawn`），而非反复 `compute`
- Flutter 3.7+ 支持 `Isolate.run`，比 `compute` 更简洁

```dart
// Flutter 3.7+
final result = await Isolate.run(() => expensiveTask(data));
```

## 9. shouldRepaint / shouldRebuildSemantics

### 底层原理

`CustomPainter` 的 `paint()` 方法在每次需要重绘时调用。`shouldRepaint(oldDelegate)` 返回 `false` 时，Flutter 直接复用上一帧的绘制结果，跳过 `paint()` 调用。

### 有效场景

```dart
class ChartPainter extends CustomPainter {
  final List<double> data;
  final Color color;

  ChartPainter({required this.data, required this.color});

  @override
  void paint(Canvas canvas, Size size) {
    // 复杂绘制逻辑
  }

  @override
  bool shouldRepaint(ChartPainter oldDelegate) {
    // ✅ 只在数据或颜色变化时重绘
    return oldDelegate.data != data || oldDelegate.color != color;
  }
}
```

### 无效 / 反效果场景

```dart
// ❌ 总是返回 true，无优化效果
@override
bool shouldRepaint(covariant CustomPainter oldDelegate) => true;

// ❌ 深层比较开销可能超过重绘开销
@override
bool shouldRepaint(MyPainter old) => !listEquals(old.complexData, complexData);
```

### 边界情况

- 如果 `CustomPainter` 监听了 `Listenable`（通过构造函数传入），每次通知都会触发重绘，`shouldRepaint` 不会被调用
- `shouldRebuildSemantics` 同理，控制语义树的重建，影响无障碍功能性能

## 10. GlobalKey 滥用问题

### 底层原理

`GlobalKey` 在全局 Widget 树中唯一标识一个 Element，允许从任意位置访问对应的 State 或 RenderObject。

问题在于：
1. 每次 Widget 树重建，Flutter 都需要在全局 Map 中查找 GlobalKey 对应的 Element
2. 在 `build()` 中创建 GlobalKey 会导致每次重建都创建新 key，触发 Element 重建
3. GlobalKey 持有 State 引用，如果 Widget 被移除但 key 未释放，导致内存泄漏

### 问题场景

```dart
// ❌ 在 build() 中创建 GlobalKey
@override
Widget build(BuildContext context) {
  return Form(
    key: GlobalKey(), // 每次 build 都是新 key，Form 每次都重建
    child: ...,
  );
}

// ❌ 列表中使用 GlobalKey
ListView.builder(
  itemBuilder: (context, index) => MyWidget(
    key: GlobalKey(), // 严重性能问题
  ),
)
```

### 正确用法

```dart
// ✅ 在 State 中声明，生命周期与 State 一致
class _MyFormState extends State<MyForm> {
  final _formKey = GlobalKey<FormState>();

  void _submit() {
    if (_formKey.currentState!.validate()) {
      _formKey.currentState!.save();
    }
  }
}
```

### 替代方案

- 需要唯一标识列表项：使用 `ValueKey(item.id)` 或 `ObjectKey(item)`
- 需要访问子 Widget 状态：通过回调或 Controller 模式
- 需要测量子 Widget 尺寸：使用 `LayoutBuilder` 或 `MeasureSize`

## 11. InheritedWidget vs Provider

### 底层原理

`InheritedWidget` 是 Flutter 框架原生的依赖注入机制。当 InheritedWidget 更新时，所有调用了 `context.dependOnInheritedWidgetOfExactType<T>()` 的 Widget 都会重建。

`Provider` 是对 InheritedWidget 的封装，增加了依赖注入、生命周期管理等功能，有轻微额外开销。

### 精准控制重建

```dart
// ✅ updateShouldNotify 控制哪些情况触发重建
class MyData extends InheritedWidget {
  final int value;

  const MyData({required this.value, required super.child});

  @override
  bool updateShouldNotify(MyData oldWidget) {
    return oldWidget.value != value; // 值未变化时不触发重建
  }
}

// ✅ Provider 的 select 精准订阅
context.select<UserModel, String>((user) => user.name); // 只在 name 变化时重建
```

### 有效场景

- `InheritedWidget`：性能关键路径，或不想引入第三方依赖
- `Provider`：大型应用，需要灵活的依赖注入和状态管理

### 无效 / 反效果场景

- 高频更新的状态（如动画值）通过 InheritedWidget 传递：导致大量 Widget 重建
- 不使用 `select` 而直接 `watch` 整个大对象：任何字段变化都触发重建

```dart
// ❌ 监听整个大对象
final user = context.watch<UserModel>(); // UserModel 任何字段变化都重建

// ✅ 精准订阅
final name = context.select<UserModel, String>((u) => u.name); // 只关心 name
```

## 12. build() 方法中避免的操作

`build()` 方法可能在每帧都被调用，其中的操作会被反复执行。

### 禁止：创建有状态对象

```dart
// ❌ 每次 build 都创建新 Controller，旧的泄漏
Widget build(BuildContext context) {
  final controller = TextEditingController();
  return TextField(controller: controller);
}

// ✅ 在 initState 中创建，dispose 中释放
@override
void initState() {
  super.initState();
  _controller = TextEditingController();
}

@override
void dispose() {
  _controller.dispose();
  super.dispose();
}
```

### 禁止：发起网络请求

```dart
// ❌ 每次 build 都发起请求（可能无限循环）
Widget build(BuildContext context) {
  return FutureBuilder(
    future: ApiService.fetchData(), // 每次 build 都创建新 Future
    builder: ...,
  );
}

// ✅ Future 只创建一次
late final _future = ApiService.fetchData();

Widget build(BuildContext context) {
  return FutureBuilder(future: _future, builder: ...);
}
```

### 禁止：耗时计算

```dart
// ❌ 每帧都计算
Widget build(BuildContext context) {
  final sorted = items.toList()..sort(); // O(n log n) 每帧执行
  return ListView(children: sorted.map(...).toList());
}

// ✅ 在数据变化时才计算，缓存结果
List<Item> _sortedItems = [];

void _updateItems(List<Item> newItems) {
  setState(() {
    _sortedItems = newItems.toList()..sort();
  });
}
```

### 禁止：修改状态

```dart
// ❌ build 中调用 setState 导致无限循环
Widget build(BuildContext context) {
  setState(() { _count++; }); // 无限循环！
  return Text('$_count');
}
```

## 13. Flutter DevTools 性能分析

### 启动方式

```bash
# 以 profile 模式运行（接近生产环境性能）
flutter run --profile

# 打开 DevTools
flutter pub global activate devtools
flutter pub global run devtools
```

> 注意：debug 模式下性能数据不准确，性能分析必须使用 profile 模式。

### 核心工具

**Performance 面板**
- 查看帧率（目标 60fps / 120fps）
- 识别 UI 线程（build/layout/paint）和 Raster 线程（GPU）的耗时
- 掉帧帧会标红，点击可查看详情

**Widget Rebuild Stats**
- 显示每个 Widget 的重建次数
- 快速定位过度重建的 Widget

**Highlight Repaints**
- 可视化重绘区域（闪烁的彩色边框）
- 帮助决定在哪里添加 RepaintBoundary

**Memory 面板**
- 监控内存使用趋势
- 检测内存泄漏（内存只增不减）
- 查看对象分配情况

### 常见问题诊断

| 现象 | 可能原因 | 解决方案 |
|------|---------|---------|
| UI 线程耗时高 | build() 中有耗时操作 | 移到 initState 或 compute |
| Raster 线程耗时高 | 过度绘制、复杂 shader | RepaintBoundary、简化绘制 |
| 内存持续增长 | 内存泄漏 | 检查 dispose、StreamSubscription |
| 首帧卡顿 | 图片未预加载 | precacheImage |
| 列表滚动卡顿 | itemBuilder 耗时 | 简化 item、使用 const |

## 总结：优化优先级

| 优先级 | 技术 | 收益 | 成本 |
|--------|------|------|------|
| ⭐⭐⭐ | `const` Widget | 高 | 极低 |
| ⭐⭐⭐ | `ListView.builder` | 高（大列表） | 低 |
| ⭐⭐⭐ | build() 中避免耗时操作 | 高 | 低 |
| ⭐⭐ | `ValueNotifier` 局部重建 | 中 | 低 |
| ⭐⭐ | `compute` 耗时任务 | 高（CPU 密集） | 中 |
| ⭐⭐ | `RepaintBoundary` | 中（动画场景） | 中 |
| ⭐⭐ | `shouldRepaint` 优化 | 中（自定义绘制） | 低 |
| ⭐ | `precacheImage` | 中（图片场景） | 低 |
| ⭐ | `AutomaticKeepAlive` | 中（多 Tab） | 低 |
| ⭐ | 避免 GlobalKey 滥用 | 低~中 | 低 |

> 黄金法则：**先用 DevTools 测量，再针对性优化。** 不要凭感觉优化，过度优化会增加代码复杂度，得不偿失。
