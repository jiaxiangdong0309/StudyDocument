# 建造者模式（Builder Pattern）

> 核心目标：当一个对象的创建过程很复杂、参数很多、组装步骤很多时，用 Builder 把“构建过程”拆出来，让创建过程更清晰、更安全、更可读。

## 一、它解决了什么问题？

来看一个很常见的问题：一个对象参数越来越多。

```kotlin
class RequestConfig(
    val baseUrl: String,
    val connectTimeout: Long,
    val readTimeout: Long,
    val writeTimeout: Long,
    val retry: Boolean,
    val enableLog: Boolean,
    val cacheSize: Long,
    val token: String?
)
```

如果直接这样创建：

```kotlin
val config = RequestConfig(
    "https://api.example.com/",
    10_000,
    15_000,
    15_000,
    true,
    true,
    10 * 1024 * 1024,
    null
)
```

你很快就会遇到这些问题：

- 参数太多，看不懂每一位是什么意思
- 可选参数越来越多
- 参数顺序很容易写错
- 创建过程里还可能夹杂校验逻辑、默认值逻辑、依赖组装逻辑

这就像你装修房子。
你不会希望工人一句话问你：“墙面颜色、地板材质、门锁型号、灯光色温、窗帘类型、空调功率，全部一次性告诉我。”

更自然的方式是一步一步确认：

- 先定基础结构
- 再选可选配置
- 最后统一交付

这就是 Builder 的思路。

## 二、核心思想

建造者模式会把“复杂对象的创建过程”拆成多个可读步骤：

- 目标对象通常构造器私有化或限制直接构造
- Builder 持有构建过程中需要的字段
- 通过链式方法逐步设置参数
- 最后通过 `build()` 统一生成对象

```mermaid

    B --> C[设置可选参数]
    C --> D[参数校验]
```

## 三、标准实现方案

```kotlin
class DialogConfig private constructor(
    val title: String,
    val message: String,
    val cancelable: Boolean
) {
    class Builder {
        private var title: String = ""
        private var message: String = ""
        private var cancelable: Boolean = true

        fun setTitle(value: String) = apply {
            title = value
        }

        fun setMessage(value: String) = apply {
            message = value
        }

        fun setCancelable(value: Boolean) = apply {
            cancelable = value
        }

        fun build(): DialogConfig {
            require(title.isNotBlank()) { "title 不能为空" }
            return DialogConfig(title, message, cancelable)
        }
    }
}
```

使用方式：

```kotlin
val config = DialogConfig.Builder()
    .setTitle("删除确认")
    .setMessage("确定要删除这条记录吗？")
    .setCancelable(false)
    .build()
```

这样的代码有两个明显优势：

- 一眼能看懂每个参数的含义
- 校验逻辑可以集中在 `build()` 里统一兜底

## 四、建造者模式的优势

### 1. 提升可读性

相比一长串构造参数，链式设置更容易读，也更不容易传错。

### 2. 支持复杂对象的分步创建

对象不是一次性“硬塞出来”的，而是一步一步被组装完成。

### 3. 便于集中做校验和默认值处理

在 `build()` 里统一处理：

- 必填参数是否缺失
- 参数组合是否合法
- 默认值是否需要补齐

### 4. API 体验更友好

这也是为什么很多优秀框架都喜欢用 Builder。  
它不只是“能创建对象”，而是“让调用体验更顺”。

## 五、它的代价和边界

### 1. 会增加代码量

如果对象只有 2 到 3 个参数，强行引入 Builder，收益可能不大。

### 2. 不适合过度滥用

不是所有对象都需要 Builder。  
简单对象用普通构造器、Kotlin 默认参数、具名参数，反而更直接。

### 3. Builder 也要注意状态污染

如果同一个 Builder 被复用，可能带来旧状态残留问题。  
所以很多 Builder 设计都倾向于“一次构建一次用完”。

## 六、Android 中哪些地方特别适合 Builder？

### 1. Dialog / AlertDialog 配置

这是最经典的 Android 示例之一。

```kotlin
AlertDialog.Builder(this)
    .setTitle("退出登录")
    .setMessage("确定要退出当前账号吗？")
    .setPositiveButton("确定", null)
    .setNegativeButton("取消", null)
    .show()
```

为什么这里 Builder 特别合适？

- 参数很多，而且大量是可选项
- 调用顺序比较自由
- 最终通过 `show()` 或 `create()` 统一产出结果

### 2. 网络层客户端配置

像 `OkHttpClient.Builder()`、`Retrofit.Builder()` 都是 Builder 的典型代表。

```kotlin
val okHttpClient = OkHttpClient.Builder()
    .connectTimeout(10, TimeUnit.SECONDS)
    .readTimeout(15, TimeUnit.SECONDS)
    .addInterceptor(HttpLoggingInterceptor())
    .retryOnConnectionFailure(true)
    .build()
```

它解决的是：

- 配置项太多
- 默认值太多
- 初始化逻辑太复杂

### 3. 自定义组件配置对象

比如你写一个图片选择器、埋点 SDK、下载组件，也很适合暴露 Builder 风格 API。

```kotlin
class UploadTask private constructor(
    val filePath: String,
    val retryCount: Int,
    val enableCompress: Boolean
) {
    class Builder(private val filePath: String) {
        private var retryCount = 0
        private var enableCompress = false

        fun retryCount(value: Int) = apply { retryCount = value }
        fun enableCompress(value: Boolean) = apply { enableCompress = value }

        fun build(): UploadTask {
            return UploadTask(filePath, retryCount, enableCompress)
        }
    }
}
```

## 七、Android 框架和常见库里的案例

### 1. `AlertDialog.Builder`

这是 Android 学习设计模式时最经典的入门案例。  
它的价值不只是“写起来顺手”，而是把复杂配置过程优雅地组织起来。

### 2. `OkHttpClient.Builder`

`OkHttpClient` 里有大量配置项：

- 超时
- 拦截器
- 缓存
- 连接池
- 重试策略

如果不用 Builder，这种 API 会非常难用。  
Builder 让这些配置可以自由组合，同时在 `build()` 时统一生成一个稳定对象。

### 3. `Retrofit.Builder`

`Retrofit` 也很典型：

- `baseUrl`
- `client`
- `converterFactory`
- `callAdapterFactory`

这些配置的组合关系复杂，而且要求可读性高，所以 Builder 非常合适。

### 4. `NotificationCompat.Builder`

通知配置项非常多，标题、内容、优先级、渠道、图标、点击事件等一大堆。  
Builder 正好能把这种“多参数 + 强语义”的场景处理得很优雅。

## 八、Builder 和 Kotlin 默认参数怎么选？

这是现在 Android 面试里很值得聊的点。

### Kotlin 默认参数更适合：

- 参数不多
- 语义清晰
- 可选项有限

例如：

```kotlin
data class UserUiState(
    val name: String = "",
    val loading: Boolean = false,
    val errorMessage: String? = null
)
```

这种场景没必要强行写 Builder。

### Builder 更适合：

- 参数特别多
- 创建过程需要分步骤
- 需要做参数组合校验
- 需要更强的链式 API 可读性

一句话理解：

> Kotlin 默认参数解决的是“参数声明方便”，Builder 解决的是“复杂对象构建过程清晰”。

## 九、实战经验：Builder 常见踩坑

### 1. 忘记校验必填字段

很多人写了 Builder，却把 `build()` 写成纯粹 return。  
这样只是“换了个写法”，没有真正体现 Builder 的价值。

### 2. 一个 Builder 被多处复用

如果 Builder 内部字段没重置，复用时可能把上一次的配置带到下一次。

### 3. 对简单对象过度设计

本来一个 `data class` + 默认参数就能搞定，结果硬写一个 100 行 Builder，这就是典型的过度设计。

## 十、面试里怎么答？

### 标准回答模板

> 建造者模式主要用来解决复杂对象创建的问题，尤其适合参数很多、可选项很多、创建过程需要分步骤组装的场景。  
> 它的核心做法是把对象构建过程放到 Builder 中，通过链式调用逐步设置参数，最后通过 `build()` 统一生成对象。  
> 在 Android 里很常见的例子有 `AlertDialog.Builder`、`OkHttpClient.Builder`、`Retrofit.Builder`、`NotificationCompat.Builder`。  
> 这样做的好处是可读性更高，也更方便集中做参数校验和默认值管理。

### 面试高频追问

#### 1. Builder 和工厂模式有什么区别？

工厂更关注“创建哪个对象”；Builder 更关注“这个复杂对象如何一步一步组装出来”。

#### 2. Builder 一定要链式调用吗？

不一定，但链式调用最符合它的使用体验，所以实践里几乎都会这么设计。

#### 3. Kotlin 都有默认参数了，还需要 Builder 吗？

需要分场景看。  
简单对象默认参数足够；复杂对象、强校验场景、框架 API 设计场景，Builder 依然非常有价值。

## 十一、总结

建造者模式最值得记住的一句话是：

> 当“创建对象”这件事本身已经变复杂了，就不要再把复杂度塞进构造器里。

在 Android 开发里，Builder 的价值非常直接：

- 提高 API 可读性
- 降低参数顺序错误的概率
- 让复杂配置更容易扩展
- 让框架调用体验更自然

所以它不是一个“纸上谈兵”的模式，而是你几乎每天都在用、只是以前没系统总结过的模式。
