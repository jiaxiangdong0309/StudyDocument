# EventBus 进阶篇

## 高级特性

### 事件优先级

当多个订阅者订阅同一事件时，可以通过 `priority` 控制接收顺序：

```kotlin
// 优先级高的先收到事件
@Subscribe(threadMode = ThreadMode.MAIN, priority = 100)
fun onEventHighPriority(event: MessageEvent) {
    // 先执行
}

@Subscribe(threadMode = ThreadMode.MAIN, priority = 1)
fun onEventLowPriority(event: MessageEvent) {
    // 后执行
}
```

**规则**：
- 优先级范围：整数，越大越先执行
- 默认优先级：0
- **只在同一线程模式下有效**

### 事件取消

高优先级的订阅者可以取消事件，阻止传递给后续订阅者：

```kotlin
@Subscribe(threadMode = ThreadMode.POSTING, priority = 100)
fun onEventFirst(event: MessageEvent) {
    if (shouldBlock(event)) {
        // 取消事件，后续订阅者不会收到
        EventBus.getDefault().cancelEventDelivery(event)
    }
}
```

**限制**：
- 只能在 `ThreadMode.POSTING` 模式下取消
- 只能取消当前正在分发的事件

**使用场景**：
- 权限拦截：高优先级检查权限，不满足则取消
- 登录拦截：未登录时取消事件，跳转登录页

### 索引加速（Subscriber Index）

默认情况下，EventBus 通过**反射**查找订阅方法，有性能开销。使用 APT 生成索引可以大幅提升性能。

**配置步骤**：

```groovy
// build.gradle (Module)
plugins {
    id 'kotlin-kapt'
}

dependencies {
    implementation 'org.greenrobot:eventbus:3.3.1'
    kapt 'org.greenrobot:eventbus-annotation-processor:3.3.1'
}

kapt {
    arguments {
        arg('eventBusIndex', 'com.yourpackage.MyEventBusIndex')
    }
}
```

```kotlin
// Application 中配置
class MyApplication : Application() {
    override fun onCreate() {
        super.onCreate()
        
        // 使用索引（编译时生成的 MyEventBusIndex 类）
        EventBus.builder()
            .addIndex(MyEventBusIndex())
            .installDefaultEventBus()
    }
}
```

**性能对比**：

| 方式 | 注册耗时 | 优点 | 缺点 |
|-----|---------|-----|------|
| 反射（默认） | ~1ms/订阅者 | 无需配置 | 首次注册慢，混淆需配置 |
| APT 索引 | ~0.1ms/订阅者 | 性能好，无反射 | 需要配置，增加编译时间 |

### EventBus 配置

除了索引，EventBus 还支持多种配置：

```kotlin
EventBus.builder()
    .addIndex(MyEventBusIndex())           // 使用索引
    .throwSubscriberException(true)         // 开发阶段抛出异常（默认 catch 住不抛）
    .logNoSubscriberMessages(false)         // 关闭"无订阅者"日志
    .logSubscriberExceptions(true)          // 打印订阅者异常
    .sendNoSubscriberEvent(false)           // 关闭 NoSubscriberEvent
    .sendSubscriberExceptionEvent(false)    // 关闭 SubscriberExceptionEvent
    .eventInheritance(false)                // 关闭事件继承（提升性能）
    .executorService(myExecutor)            // 自定义线程池
    .installDefaultEventBus()               // 安装为默认 EventBus
```

**重要配置说明**：

| 配置 | 默认值 | 建议 |
|-----|-------|------|
| `throwSubscriberException` | false | 开发阶段设为 true |
| `eventInheritance` | true | 不需要事件继承时设为 false（提升性能） |
| `executorService` | CachedThreadPool | 可用 FixedThreadPool 限制并发 |

### 事件继承

默认情况下，子类事件会被父类订阅者接收：

```kotlin
// 事件类继承关系
open class BaseEvent
class UserEvent : BaseEvent()
class AdminEvent : BaseEvent()

// 订阅父类，会收到所有子类事件
@Subscribe
fun onBaseEvent(event: BaseEvent) {
    // 收到 UserEvent、AdminEvent、BaseEvent
}
```

**关闭事件继承**（提升性能）：

```kotlin
EventBus.builder()
    .eventInheritance(false)  // 只接收精确类型的事件
    .installDefaultEventBus()
```

## 横向对比

### EventBus vs RxBus vs LiveDataBus vs Flow

在选择事件总线方案前，需要了解各方案的优劣：

#### 1. EventBus

```kotlin
// 发布
EventBus.getDefault().post(MyEvent(data))

// 订阅
@Subscribe(threadMode = ThreadMode.MAIN)
fun onEvent(event: MyEvent) { ... }
```

**优点**：
- 使用简单，API 直观
- 线程切换方便
- 生态成熟，文档丰富

**缺点**：
- 事件流向难以追踪
- 需要手动管理生命周期
- 没有背压处理

#### 2. RxBus（基于 RxJava）

```kotlin
// RxBus 实现（使用 PublishSubject）
object RxBus {
    private val bus = PublishSubject.create<Any>().toSerialized()
    
    fun post(event: Any) = bus.onNext(event)
    
    fun <T : Any> toObservable(eventType: Class<T>): Observable<T> {
        return bus.ofType(eventType)
    }
}

// 发布
RxBus.post(MyEvent(data))

// 订阅
RxBus.toObservable(MyEvent::class.java)
    .observeOn(AndroidSchedulers.mainThread())
    .subscribe { event -> ... }
    .addTo(compositeDisposable)
```

**优点**：
- 可以链式操作（filter、map、debounce 等）
- 背压处理
- 灵活的线程控制

**缺点**：
- RxJava 学习成本高
- 容易写出难以维护的代码
- 需要手动管理订阅

#### 3. LiveDataBus

```kotlin
// LiveDataBus 实现
object LiveDataBus {
    private val busMap = mutableMapOf<String, MutableLiveData<Any>>()
    
    @Suppress("UNCHECKED_CAST")
    fun <T> with(key: String): MutableLiveData<T> {
        return busMap.getOrPut(key) { MutableLiveData() } as MutableLiveData<T>
    }
}

// 发布
LiveDataBus.with<String>("login_event").value = "user_123"

// 订阅
LiveDataBus.with<String>("login_event").observe(this) { userId ->
    // 处理事件
}
```

**优点**：
- 生命周期感知，自动管理订阅
- 官方支持，与 Jetpack 配合好
- 天然支持粘性事件

**缺点**：
- 粘性问题（新订阅者会收到旧数据）
- 只能在主线程更新（需要 postValue 切换）
- 用字符串 key 容易出错

#### 4. Kotlin Flow（SharedFlow）

```kotlin
// 使用 SharedFlow 实现事件总线
object FlowBus {
    private val busMap = mutableMapOf<String, MutableSharedFlow<Any>>()
    
    @Suppress("UNCHECKED_CAST")
    fun <T> with(key: String): MutableSharedFlow<T> {
        return busMap.getOrPut(key) {
            MutableSharedFlow(replay = 0)  // replay=0 表示不粘性
        } as MutableSharedFlow<T>
    }
}

// 发布
lifecycleScope.launch {
    FlowBus.with<String>("login_event").emit("user_123")
}

// 订阅
lifecycleScope.launch {
    FlowBus.with<String>("login_event").collect { userId ->
        // 处理事件
    }
}
```

**优点**：
- Kotlin 协程原生支持
- 可配置粘性（replay 参数）
- 可配置背压策略
- 与 Lifecycle 配合好

**缺点**：
- 需要协程知识
- 相对较新，部分场景文档较少

## 实战经验

### 场景1：登录状态全局同步

```kotlin
// 1. 定义登录相关事件
sealed class AuthEvent {
    data class LoginSuccess(val user: User) : AuthEvent()
    object Logout : AuthEvent()
    data class TokenExpired(val reason: String) : AuthEvent()
}

// 2. 登录管理器：发布事件
object AuthManager {
    fun login(user: User) {
        // 保存用户信息
        UserPrefs.saveUser(user)
        // 发布粘性事件，让后打开的页面也能获取登录状态
        EventBus.getDefault().postSticky(AuthEvent.LoginSuccess(user))
    }
    
    fun logout() {
        UserPrefs.clear()
        // 移除登录粘性事件
        EventBus.getDefault().removeStickyEvent(AuthEvent.LoginSuccess::class.java)
        // 发布登出事件
        EventBus.getDefault().post(AuthEvent.Logout)
    }
}

// 3. 基类 Activity：统一处理登录状态
abstract class BaseActivity : AppCompatActivity() {
    
    override fun onStart() {
        super.onStart()
        EventBus.getDefault().register(this)
    }
    
    override fun onStop() {
        super.onStop()
        EventBus.getDefault().unregister(this)
    }
    
    @Subscribe(threadMode = ThreadMode.MAIN, sticky = true)
    open fun onLoginSuccess(event: AuthEvent.LoginSuccess) {
        // 子类可重写处理登录成功
    }
    
    @Subscribe(threadMode = ThreadMode.MAIN)
    fun onLogout(event: AuthEvent.Logout) {
        // 统一跳转登录页
        if (this !is LoginActivity) {
            startActivity(Intent(this, LoginActivity::class.java))
            finish()
        }
    }
    
    @Subscribe(threadMode = ThreadMode.MAIN)
    fun onTokenExpired(event: AuthEvent.TokenExpired) {
        Toast.makeText(this, "登录已过期，请重新登录", Toast.LENGTH_SHORT).show()
        AuthManager.logout()
    }
}
```

### 场景2：跨页面数据刷新

```kotlin
// 场景：订单列表页 → 订单详情页 → 取消订单 → 返回列表页需要刷新

// 1. 定义刷新事件
data class OrderRefreshEvent(
    val orderId: String,
    val action: Action
) {
    enum class Action { CREATED, UPDATED, CANCELLED, PAID }
}

// 2. 订单详情页：操作后发布事件
class OrderDetailActivity : AppCompatActivity() {
    
    private fun cancelOrder(orderId: String) {
        orderRepository.cancelOrder(orderId)
            .onSuccess {
                // 发布刷新事件
                EventBus.getDefault().post(
                    OrderRefreshEvent(orderId, OrderRefreshEvent.Action.CANCELLED)
                )
                finish()
            }
    }
}

// 3. 订单列表页：接收事件并刷新
class OrderListActivity : AppCompatActivity() {
    
    @Subscribe(threadMode = ThreadMode.MAIN)
    fun onOrderRefresh(event: OrderRefreshEvent) {
        when (event.action) {
            OrderRefreshEvent.Action.CANCELLED -> {
                // 从列表中移除该订单，或者重新加载
                adapter.removeOrder(event.orderId)
            }
            OrderRefreshEvent.Action.UPDATED -> {
                // 更新该订单的显示
                adapter.updateOrder(event.orderId)
            }
            else -> {
                // 其他情况全量刷新
                loadOrders()
            }
        }
    }
}
```

### 场景3：下载进度实时更新

```kotlin
// 1. 定义下载进度事件
data class DownloadProgressEvent(
    val taskId: String,
    val progress: Int,      // 0-100
    val state: State
) {
    enum class State { PENDING, DOWNLOADING, PAUSED, COMPLETED, FAILED }
}

// 2. 下载服务：发布进度
class DownloadService : Service() {
    
    private fun notifyProgress(taskId: String, downloaded: Long, total: Long) {
        val progress = ((downloaded * 100) / total).toInt()
        
        // 使用 BACKGROUND 模式发送，避免阻塞下载线程
        EventBus.getDefault().post(
            DownloadProgressEvent(taskId, progress, DownloadProgressEvent.State.DOWNLOADING)
        )
    }
    
    private fun notifyCompleted(taskId: String) {
        // 完成事件用粘性，确保用户返回下载页时能看到
        EventBus.getDefault().postSticky(
            DownloadProgressEvent(taskId, 100, DownloadProgressEvent.State.COMPLETED)
        )
    }
}

// 3. 下载页面：显示进度
class DownloadListFragment : Fragment() {
    
    @Subscribe(threadMode = ThreadMode.MAIN)
    fun onDownloadProgress(event: DownloadProgressEvent) {
        val holder = findViewHolderByTaskId(event.taskId) ?: return
        
        when (event.state) {
            DownloadProgressEvent.State.DOWNLOADING -> {
                holder.progressBar.progress = event.progress
                holder.statusText.text = "${event.progress}%"
            }
            DownloadProgressEvent.State.COMPLETED -> {
                holder.progressBar.progress = 100
                holder.statusText.text = "下载完成"
                holder.actionButton.text = "打开"
            }
            DownloadProgressEvent.State.FAILED -> {
                holder.statusText.text = "下载失败"
                holder.actionButton.text = "重试"
            }
            else -> { /* ... */ }
        }
    }
}
```

## 边界认知：什么时候不该用 EventBus

### 不适用场景

#### 1. 简单的父子组件通信

```kotlin
// ❌ 不该用 EventBus：Activity 和其 Fragment 通信
class MyActivity : AppCompatActivity() {
    @Subscribe
    fun onFragmentData(event: FragmentDataEvent) { ... }
}

// ✅ 应该用：直接接口或 ViewModel
class MyFragment : Fragment() {
    private val viewModel: SharedViewModel by activityViewModels()
    
    fun sendData() {
        viewModel.data.value = "some data"
    }
}
```

#### 2. 有明确调用方向的业务逻辑

```kotlin
// ❌ 不该用 EventBus：明确知道谁调用谁
EventBus.getDefault().post(SaveUserEvent(user))

// ✅ 应该用：直接调用
userRepository.saveUser(user)
```

#### 3. 需要返回值的操作

```kotlin
// ❌ EventBus 不支持返回值
EventBus.getDefault().post(QueryUserEvent(userId))
// 怎么拿到结果？

// ✅ 应该用：直接调用或回调
val user = userRepository.getUser(userId)
```

#### 4. 频繁的、高性能要求的通信

```kotlin
// ❌ 不该用 EventBus：每帧都要发送的数据
// 动画更新、实时传感器数据等
EventBus.getDefault().post(FrameUpdateEvent(frameData))

// ✅ 应该用：直接回调或 Flow
animationController.setFrameCallback { frameData ->
    updateUI(frameData)
}
```

### EventBus 的问题

| 问题 | 说明 | 缓解方法 |
|-----|------|---------|
| **事件流向难追踪** | IDE 无法直接跳转到发布者 | 规范命名、注释、文档 |
| **调试困难** | 出问题时不知道事件从哪来 | 打日志、使用 EventBusBuilder.logSubscriberExceptions |
| **隐式依赖** | 发布者不知道有没有人订阅 | 设计时明确事件的生产者和消费者 |
| **过度解耦** | 滥用导致代码"意大利面" | 只用于真正需要解耦的场景 |

### 最佳实践

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                        EventBus 使用准则                                     │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  ✅ 适合用 EventBus：                                                        │
│  • 跨模块/跨页面的通知（登录状态、支付结果）                                   │
│  • 一对多的广播（网络状态变化）                                               │
│  • 解耦独立功能模块                                                          │
│                                                                             │
│  ❌ 不该用 EventBus：                                                        │
│  • 父子组件通信（用 ViewModel/接口）                                          │
│  • 需要返回值的调用（用方法调用）                                             │
│  • 频繁的数据更新（用 Flow/LiveData）                                        │
│  • 明确的单向依赖（直接调用）                                                 │
│                                                                             │
│  📋 使用规范：                                                               │
│  • 事件类统一放在一个包下                                                     │
│  • 事件命名：[动作][对象]Event                                               │
│  • 每个事件类注释说明：谁发布、谁订阅、什么时机                                │
│  • 粘性事件用完及时清理                                                       │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 小结

| 要点 | 说明 |
|-----|------|
| 高级特性 | 优先级、取消事件、索引加速、事件继承 |
| 方案选择 | 新项目用 Flow，老项目继续 EventBus |
| 适用场景 | 跨模块通知、一对多广播、解耦独立模块 |
| 不适用场景 | 父子通信、需要返回值、高频更新 |
| 核心问题 | 事件流向难追踪，需要规范和文档 |

## 面试题检验

### Q1：EventBus 和 RxBus、LiveDataBus 各有什么优缺点？

**结论**：EventBus 简单但不感知生命周期；RxBus 灵活但学习成本高；LiveDataBus 感知生命周期但有粘性问题；新项目推荐 SharedFlow。

**对比**：
| 维度 | EventBus | RxBus | LiveDataBus |
|-----|----------|-------|-------------|
| 生命周期 | 手动管理 | 手动管理 | 自动管理 |
| 学习成本 | 低 | 高 | 低 |
| 线程切换 | 内置 5 种模式 | 操作符灵活 | 受限 |
| 数据转换 | 无 | 丰富 | 有限 |

---

### Q2：什么场景下不该用 EventBus？

**结论**：父子组件通信、需要返回值的操作、高频数据更新、明确单向依赖的场景不该用。

**原因**：
- 父子通信用 ViewModel 更直观
- EventBus 是单向的，不支持返回值
- 高频场景有性能开销
- 滥用会导致代码难以追踪

---

### Q3：EventBus 索引（Index）有什么作用？如何配置？

**结论**：索引使用 APT 在编译时生成订阅者信息，避免运行时反射，提升注册性能约 10 倍。

**配置**：
1. 添加 `eventbus-annotation-processor` 依赖
2. kapt 配置 `eventBusIndex` 参数指定生成类名
3. Application 中 `EventBus.builder().addIndex(...).installDefaultEventBus()`

---

### Q4：如何避免事件总线导致的代码难以追踪问题？

**结论**：制定命名规范、集中管理事件类、添加注释文档、限制使用场景。

**具体做法**：
1. 事件类统一放在 `events` 包下
2. 命名格式：`[动作][对象]Event`
3. 每个事件类注释说明发布者、订阅者、时机
4. 只在真正需要解耦的场景使用

---

### Q5：EventBus 的事件优先级有什么限制？

**结论**：优先级只在同一 `threadMode` 下有效，且只有 `POSTING` 模式支持取消事件。

**原因**：不同线程模式的执行时机不同，无法保证顺序。比如 `MAIN` 和 `ASYNC` 模式的订阅者可能在不同线程并发执行。

---

### Q6：粘性事件和普通事件各适合什么场景？

**结论**：
- 普通事件：实时通知，如点击事件、网络请求完成
- 粘性事件：状态同步，如登录状态、下载完成状态

**注意**：粘性事件会一直存在，需要在适当时机手动移除，否则可能导致数据错乱或内存问题。
