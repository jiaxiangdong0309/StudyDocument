# Android 版本特性与近五年演进（Android Version Features & Evolution）

> **阅读价值**：面试里“说说最近 Android 版本变化”本质是考察你是否理解**平台方向**（隐私、后台约束、大屏、兼容、AI），而不是背版本号。本文覆盖约 **Android 12（2021）→ Android 16（2025 周期）**，侧重**开发与 AI**。

---

## 1. 为什么要关心版本特性？

### 技术演进

Android 不是“每年换个皮肤”，而是持续把**系统能力、安全基线、开发者契约**往前推：

- **契约变严**：`targetSdk` 升高后，后台、闹钟、前台服务、存储访问等规则会改。
- **能力变多**：凭证统一、健康数据、端侧生成式 AI（Gemini Nano + AICore）等，决定你能用什么集成方式。
- **形态变复杂**：大屏、折叠、多窗口从 12L 开始被平台反复强调，UI 与生命周期都要跟着变。

### 通俗理解

把 Android 版本升级想成**城市交规改版**：

- 路还是那些路（Activity、Service、权限模型），但**红灯更细、限行更多、货车（后台任务）管得更严**。
- 同时城市也修了**新高架（新 API）**；你不看公告就容易“违章”（行为变更踩坑）。

---

## 2. 近五年主线：一张表抓住方向

| 大方向 | 典型变化 | 开发者要做什么 |
|--------|----------|----------------|
| 隐私与防滥用 | 权限更细、MediaStore/Intent 收紧、精确闹钟默认收紧 | 最小权限 + 适配行为变更文档 |
| 后台与功耗 | 前台服务必须声明类型、Job/广播策略调整 | 明确任务类型，避免“万能前台服务” |
| 大屏与形态 | 12L 起强化平板/折叠；后续持续要求自适应 | Window/Compose/多窗口与配置变更测试 |
| 运行时与语言 | OpenJDK 11 → 17 对齐，Java 语言特性提升 | 关注正则/UUID 等兼容性细节 |
| 兼容与性能 | 16KB 内存页、ART 更新可经 Mainline 回传 | NDK 对齐；避免依赖非 SDK 接口 |
| AI | 系统体验向 Gemini 收敛；端侧走 AICore + ML Kit GenAI | 区分云端 API 与端侧 Nano 的能力边界 |

## 3. 分版本要点（开发向 + AI 向）

### Android 12（API 31）

**开发相关**

- **Material You**：动态配色与系统主题预期变化；需要关注主题属性与控件外观。
- **AppSearch**：系统级/本地索引与检索能力，适合结构化内容搜索（可结合 Jetpack）。
- **小组件（Widgets）**：平台对 Widget 能力与交互有更新，需按官方兼容指南处理。
- **隐私仪表板等系统能力**：提升用户对权限的感知，应用侧要配合透明化说明。
- **性能分级（Performance Class）**：媒体与体验类 App 可按档位做降级策略。

**AI 相关**

- 更偏“铺垫能力”（搜索索引、媒体管线）。端侧大模型生态在后续版本更明确。

---

### Android 12L（API 32）

**开发相关**

- **大屏/折叠强化**：任务栏、多窗口、兼容模式；应用要按大屏清单处理尺寸、分屏生命周期与拖拽。

**AI 相关**

- 与 AI 弱相关；价值主要在**形态因子**与多窗口交互测试。

---

### Android 13（API 33）

**开发相关**

- **按应用语言（per-app locale）**：`setApplicationLocales()` 等公开 API；多语言应用建议配合 AndroidX 兼容层。
- **主题图标（Themed app icon）**：可选接入系统主题规范。
- **预测性返回（Predictive Back）**：后续版本持续演进，影响返回动画与返回栈处理。
- **静态广播 exported 约束**：合并清单与安全模型要复查。
- **OpenJDK 11 对齐**：核心库与 Java 11 特性逐步对齐（部分能力可通过 ART/Mainline 回传，以官方说明为准）。

**AI 相关**

- 生态上开始更强调“智能体验”的产品化，但第三方集成仍以 **ML Kit / 云端 API** 为主流路径。

---

### Android 14（API 34）

**开发相关**

- **Credential Manager**：统一登录与凭证体验，整合密码、通行密钥（passkeys）、联邦登录等（迁移需分场景评估）。
- **Health Connect 进入平台演进路径**：健康数据读写模型与系统更新方式变化（对运动健康类应用关键）。
- **前台服务类型（target 34+）更强制**：必须声明类型并满足对应约束。
- **精确闹钟策略更严**：闹钟/日程类应用要处理权限与降级。
- **OpenJDK 17 + Java 17 语言特性**：注意行为变更里提到的兼容性差异点。
- **国际化与无障碍**：字体缩放至 200%、区域偏好等，需要 UI 回归。
- **Ultra HDR 等影像能力**：图片链路相关应用需关注格式与显示。

**AI 相关**

- Google 产品层强力推进 **Gemini** 体系；平台侧更强调“能力产品化”（凭证、摘要、端侧推理路线并行）。

---

### Android 15（API 35）

**开发相关**

- **16KB 内存页支持**：对 **NDK/.so** 对齐与兼容性提出新要求（必须按官方迁移与测试）。
- **最低可安装 targetSdk**：过低 target 的应用可能被拒绝安装（推动老旧应用升级）。
- **ApplicationStartInfo**：启动阶段诊断（冷/温启动、原因等），利于性能治理。
- **PdfRenderer 等文档能力增强**：文档类应用可评估。
- **新前台服务类型 `mediaProcessing`**：媒体处理任务要正确归类。
- **OpenJDK 17 持续演进**、TLS 旧版本限制等安全基线变化。
- **卫星连接、Wallet 角色**等：特定品类关注。

**AI 相关（系统体验 / 产品交付）**

- Google I/O 周期把 **Gemini** 作为 Android 体验核心叙事之一：叠加层交互、与内容场景结合的问答、Circle to Search 等能力扩展。
- **Gemini Nano（端侧）**用于诈骗提示、TalkBack 图像描述、动态建议等（依赖机型与组件推送，≠第三方自动拥有同一套系统 UI）。
- **第三方应用**通常选择：**云端 Gemini API** 或 **端侧 Gemini Nano + AICore（ML Kit GenAI）**。

---

### Android 16（API 36，2025 周期）

> **提示**：官方文档对 **2025 年发布节奏**（大版本与同年次要 API 更新）有说明；真实设备以系统版本为准测试。

**开发相关**

- **API 级别细分**：`SDK_INT_FULL` / `VERSION_CODES_FULL`、`Build.getMinorSdkVersion()`，用于区分同年主次更新带来的能力差异。
- **Edge-to-edge 进一步收紧**：target 更高时对“退出边到边”的旧路径限制更强，需要按文档迁移。
- **Predictive Back 与返回路径**：在 Android 16+ 上行为继续调整，需要阅读 target 16+ 行为变更。
- **权限更细**：如 `BODY_SENSORS` 等细分，健康穿戴类要改声明与授权流程。
- **Safer Intents**：Intent 安全强化路线延续。
- **MediaStore#getVersion()** 等对 target 16+ 的防指纹调整。
- **16KB 页兼容模式**：降低部分旧二进制运行风险，但根因仍建议修复 native 对齐。
- **媒体与图形**：如 APV 专业视频编解码、AGSL 自定义图像效果等（按业务选用）。
- **ART 变更可能经 Mainline 回传**：再次强调避免依赖非 SDK/内部实现细节。

**AI 相关**

- 系统级 AI 能力仍大量通过 **Google 服务与组件更新**交付；第三方开发继续围绕 **AICore + Gemini Nano + ML Kit GenAI**。
- 典型限制：**推理配额、前台/后台策略、Bootloader 状态、AICore 初始化完成**等（以官方文档为准）。

## 4. 设计哲学：平台到底在坚持什么？

### 为什么隐私与后台规则越来越严？

**结论**：移动设备的资源是共享的，恶意与滥用成本更低；平台只能用**更强契约**把长尾应用“拉回正轨”。

**权衡**：更安全 vs 更繁琐。正规应用会多写适配代码，但生态整体更可控。

### 为什么大屏要单独强调？

**结论**：同一套手机 UI 直接拉大，会出现“丑但能用”的灾难体验；平台希望开发者用**自适应布局**消化复杂度。

**权衡**：开发成本上升，但一次适配多形态，长期更省。

### 为什么 AI 要拆成“系统体验”和“开发者 API”？

**结论**：系统可以做深集成与统一入口；第三方更需要稳定、可审计、可退避的集成面（云端 API、端侧 AICore）。

**权衡**：端侧隐私更好但能力受限；云端更强但要处理费用、合规与网络依赖。

## 5. 横向对比：集成 AI 时怎么选型？

| 方案 | 优点 | 缺点 | 典型场景 |
|------|------|------|----------|
| 云端 Gemini API | 能力强、迭代快 | 成本、网络、合规 | 复杂生成、检索增强 |
| 端侧 Gemini Nano（AICore） | 低延迟、隐私友好 | 配额与机型覆盖、能力边界 | 摘要、改写、端侧提示 |
| 传统 ML Kit（非 GenAI） | 成熟、场景固定 | 不等于大模型“万能” | OCR、检测、分类 |

## 6. 实战经验：升级 target 时的“最低限度清单”

1. 阅读对应版本的 **Behavior changes（all apps + target 版本）**。
2. 全量回归：**通知、闹钟、前台服务、文件/相册访问、后台定位**。
3. 有 **NDK**：优先处理 **16KB page** 相关构建与真机验证。
4. 有 **登录**：评估 **Credential Manager / Passkeys** 路线是否值得投入。
5. 做 **AI**：明确是云端还是端侧；端侧先测 **可用性探测与降级**。

## 7. 面试问答

> 答题建议（android.mdc）：**先说结论 → 再说原理/规则来源 → 最后举例或对比**。

### Q1：近两年升级 Android 版本，你们应用最常踩的坑是什么？

**结论**：集中在**后台限制、前台服务类型、精确闹钟、存储/媒体访问**四类。

**原理**：新版本往往通过 **targetSdk 行为变更**把“以前能跑”的路径收紧，目的是隐私与功耗。

**举例**：target 34+ 强制前台服务类型；闹钟类要处理 `SCHEDULE_EXACT_ALARM` 默认不预授权等问题。

---

### Q2：Android 14 引入的 Credential Manager 解决什么问题？

**结论**：把多种登录方式收敛到**统一框架**，降低集成复杂度并推动**通行密钥**等更安全方案。

**原理**：以前密码、Passkey、三方登录分散集成；Credential Manager 提供统一入口与系统体验一致性。

**举例**：新版本登录模块改造时，可以分阶段：先接入统一框架，再逐步替换旧实现。

---

### Q3：Foreground Service 为什么在 Android 14 变得更“难用”？

**结论**：平台要求你说清楚**你在干什么**（服务类型），避免“前台服务万能兜底”。

**原理**：前台服务对用户最敏感（常驻通知、强保活），必须映射到明确场景（媒体、位置、数据同步等）。

**举例**：下载/上传不一定都能用“dataSync”糊弄过去，要按类型约束设计任务拆分。

---

### Q4：Android 13 的 per-app language 对开发有什么影响？

**结论**：多语言应用应使用公开 API 管理语言偏好，并处理 **Split APK / 备份恢复**等工程化问题。

**原理**：系统希望语言偏好可声明、可同步，减少“只会改 Locale hack”带来的兼容问题。

**举例**：配合 AndroidX AppCompat 的版本策略，避免只在 Application 里手动 setLocale。

---

### Q5：16KB 内存页主要影响谁？Java 应用要不要关心？

**结论**：**强相关 NDK/so**；纯 Java/Kotlin 也可能被第三方 so 间接影响。

**原理**：页大小变化会影响 ELF 对齐与加载兼容性；平台在 Android 15/16 持续完善支持与兼容模式。

**举例**：升级后崩溃若集中在 `.so` 加载，应优先按官方 NDK 构建指引排查对齐与打包。

---

### Q6：端侧 Gemini Nano 和云端 Gemini API 怎么选？

**结论**：要隐私与低延迟优先端侧；要能力与上下文优先云端；多数产品会**混合**。

**原理**：Nano 由 **AICore** 托管，强调隔离与配额；云端模型不受同一套端侧配额限制但引入网络与成本。

**举例**：输入框本地润色可用端侧；长文档深度分析可走云端并做脱敏策略。

---

### Q7：ML Kit GenAI 和“直接调用大模型”有什么差别？

**结论**：ML Kit GenAI 更偏**工程化封装**（场景 API、与 AICore 协同），不是让你随意无界 prompt。

**原理**：移动端要控延迟、耗电、配额与安全过滤，平台倾向提供**可控集成面**。

**举例**：先做摘要/纠错这类高复用场景，比上来就做任意生成更稳。

---

### Q8：Android 12L 对业务 App 的最大价值是什么？

**结论**：提醒你必须认真做**大屏自适应**，否则平板/折叠体验会显著掉分。

**原理**：12L 强化任务栏与多窗口，系统把“可用”标准抬高。

**举例**：列表+详情双栏、拖拽、分屏下的状态保存，比单纯拉伸布局更重要。

---

### Q9：为什么 Google 反复强调 Predictive Back？

**结论**：让返回操作**可预测、可动画化**，减少“用户以为返回却去了奇怪页面”。

**原理**：传统返回栈与手势返回在复杂导航下容易不一致；平台用新动画与回调体系统一体验。

**举例**：自定义返回处理要区分 `OnBackPressedDispatcher` 与导航组件版本策略。

---

### Q10：你们如何验证版本升级没有回归？

**结论**：**自动化**覆盖核心链路 + **真机矩阵**覆盖代表系统版本 + **行为变更清单**对照。

**原理**：Android 碎片化导致“模拟器通过、真机失败”常见，尤其是 OEM 后台策略差异。

**举例**：至少覆盖：冷启动、登录、支付、推送、相册选择、后台任务。

---

## 8. 总结

- **版本特性**的本质是：**安全基线变严 + 新能力变多 + 形态变复杂**；开发者的核心是读行为变更、做矩阵测试。
- **AI** 在 Android 上要分清：**系统级 Gemini 体验** vs **应用集成（云端 API / AICore + ML Kit）**，两者目标与约束不同。
- 面试表达时，优先讲**你项目里如何适配**，比罗列版本号更有说服力。
