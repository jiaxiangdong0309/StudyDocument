# Flow 源码篇

## 前言：为什么要看源码？

**看 Flow 源码不是为了背代码，而是为了理解设计思想。**

Flow 的源码其实很简单，核心代码加起来不过几百行。理解了源码，你会发现：
- 原来 Flow 没有任何"魔法"
- 所谓的"响应式编程"就是函数调用而已
- 很多看似复杂的功能，实现原理都很朴素

> 💡 **学习建议**：源码篇不需要逐行背诵，重点理解**设计思路**和**为什么这样设计**。

---

## 第一章：Flow 的本质

### 一句话总结

**Flow 就是一个"约定"：你给我一个收集器，我往里面塞数据。**

就像快递员送快递：
- 你（Flow）：负责生产和发送包裹
- 收集器（FlowCollector）：负责签收包裹
- 整个过程就是：你不断 `emit`（发货），收集器不断接收

### 最核心的代码（只有这两个接口！）

```kotlin
// Flow 接口：我是一个数据源，你想要数据就调用 collect
interface Flow<T> {
    suspend fun collect(collector: FlowCollector<T>)
}

// FlowCollector 接口：我是一个收集器，你往我这里发数据就调用 emit
interface FlowCollector<T> {
    suspend fun emit(value: T)
}
```

**没了，就这么简单！**

整个 Flow 框架就建立在这两个接口上。其他所有复杂功能（map、filter、flowOn 等）都是在这个基础上"包装"出来的。

### 用代码感受一下

为了帮你理解，我把 lambda 语法"翻译"成更直观的写法：

```kotlin
// 这是我们平时写的代码
flow {
    emit(1)
    emit(2)
}.collect { value ->
    println(value)
}
```

上面这段代码，**本质上等价于**下面这样：

```kotlin
// 步骤1：创建一个 Flow
val myFlow = object : Flow<Int> {
    override suspend fun collect(collector: FlowCollector<Int>) {
        // 这里面就是 flow { } 大括号里的代码
        collector.emit(1)  // 对应 emit(1)
        collector.emit(2)  // 对应 emit(2)
    }
}

// 步骤2：创建一个收集器
val myCollector = object : FlowCollector<Int> {
    override suspend fun emit(value: Int) {
        // 这里就是 collect { } 大括号里的代码
        println(value)
    }
}

// 步骤3：开始收集
myFlow.collect(myCollector)
```

**看到了吗？**
- `flow { emit(1) }` 里的 `emit(1)`，其实就是调用 `collector.emit(1)`
- `collect { println(it) }` 里的代码，其实就是 `FlowCollector.emit()` 方法的实现

所谓的 Flow，就是**函数调用**，没有任何黑魔法。

### 为什么 Flow 是"冷"的？

```kotlin
val countFlow = flow {
    println("开始生产")
    emit(1)
}

// 第一次收集
countFlow.collect { }  // 输出：开始生产

// 第二次收集
countFlow.collect { }  // 又输出：开始生产
```

**原因很简单**：`flow { }` 只是把代码"存"起来，每次 `collect` 都重新执行一遍。

```
┌─────────────────────────────────────────────────┐
│              冷流 = 每次都重新执行                │
├─────────────────────────────────────────────────┤
│                                                 │
│  val flow = flow { emit(1) }                    │
│       │                                         │
│       └── 只是保存代码，不执行                    │
│                                                 │
│  flow.collect { }  ──→  执行一次                │
│  flow.collect { }  ──→  再执行一次              │
│  flow.collect { }  ──→  又执行一次              │
│                                                 │
│  就像饭店点菜：每次点，厨师都重新做一份           │
│                                                 │
└─────────────────────────────────────────────────┘
```

## 第二章：flow {} 构建器的原理

### 一句话总结

**flow {} 就是把你写的代码"包"成一个 Flow 对象，等 collect 的时候再执行。**

### 源码长什么样？

```kotlin
// flow 构建器的实现（简化版）
fun <T> flow(block: suspend FlowCollector<T>.() -> Unit): Flow<T> {
    return object : Flow<T> {
        override suspend fun collect(collector: FlowCollector<T>) {
            // 把 collector 作为接收者，执行 block
            collector.block()
        }
    }
}
```

**翻译成大白话**：
1. `flow { }` 返回一个 Flow 对象
2. 这个对象把 `{ }` 里的代码存起来
3. 当调用 `collect` 时，才执行这些代码
4. 执行时，`emit` 就是往收集器里塞数据

### 图解执行流程

```
┌─────────────────────────────────────────────────┐
│           flow { emit(1) }.collect { }          │
├─────────────────────────────────────────────────┤
│                                                 │
│  1. 创建阶段                                     │
│     flow { emit(1) }                            │
│           ↓                                     │
│     创建 Flow 对象，保存 { emit(1) } 这段代码     │
│           ↓                                     │
│     返回 Flow 对象（还没执行！）                  │
│                                                 │
│  2. 收集阶段                                     │
│     flow.collect { println(it) }                │
│           ↓                                     │
│     创建收集器：emit 时执行 println              │
│           ↓                                     │
│     执行保存的代码 { emit(1) }                   │
│           ↓                                     │
│     emit(1) → 调用收集器的 emit → println(1)    │
│                                                 │
└─────────────────────────────────────────────────┘
```

### 小结：Flow 的执行模型

| 阶段 | 做了什么 | 类比 |
|-----|---------|------|
| 创建 Flow | 存储代码，不执行 | 写菜谱，不做菜 |
| 调用 collect | 执行存储的代码 | 照着菜谱做菜 |
| emit | 把数据传给收集器 | 做好一道菜就端出来 |
| 收集器处理 | 处理接收到的数据 | 客人吃菜 |

## 第三章：操作符的实现原理

### 一句话总结

**每个操作符都是创建一个"新 Flow"，在收集时先处理数据，再传给下游。**

就像流水线：
- 原料（上游数据）→ 加工站（操作符）→ 成品（下游数据）
- 每个加工站都是一个新的 Flow

### map 操作符的实现

`map` 是最基础的操作符，理解了它，其他操作符都是类似的套路。

```kotlin
// map 的简化实现
fun <T, R> Flow<T>.map(transform: (T) -> R): Flow<R> {
    val upstream = this  // 保存上游 Flow
    
    return flow {
        // 收集上游
        upstream.collect { value ->
            // 转换数据
            val newValue = transform(value)
            // 发射到下游
            emit(newValue)
        }
    }
}
```

**解读**：
1. `map` 返回一个**新的 Flow**
2. 新 Flow 在 collect 时，会去收集上游的数据
3. 收到数据后，先转换，再 emit 出去

### 图解操作符链

```kotlin
flowOf(1, 2, 3)
    .map { it * 2 }      // ① 
    .filter { it > 2 }   // ②
    .collect { }         // ③
```

```
┌──────────────────────────────────────────────────────────┐
│                    操作符链执行过程                        │
├──────────────────────────────────────────────────────────┤
│                                                          │
│  【构建阶段】从左往右包装                                   │
│                                                          │
│  flowOf(1,2,3)  →  MapFlow  →  FilterFlow                │
│     原始Flow        ↑           ↑                        │
│                  包装原始Flow  包装MapFlow                  │
│                                                          │
│  【执行阶段】从右往左触发                                   │
│                                                          │
│  collect 触发                                             │
│      ↓                                                   │
│  FilterFlow: "我要数据" → 去找 MapFlow                    │
│      ↓                                                   │
│  MapFlow: "我要数据" → 去找 flowOf                        │
│      ↓                                                   │
│  flowOf: 发射 1 → MapFlow 转成 2 → FilterFlow 判断        │
│          发射 2 → MapFlow 转成 4 → FilterFlow 通过 → emit │
│          发射 3 → MapFlow 转成 6 → FilterFlow 通过 → emit │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 操作符的设计思想

| 设计点 | 说明 |
|-------|------|
| **组合而非继承** | 每个操作符创建新 Flow，不是通过继承实现 |
| **惰性执行** | 操作符只是构建流水线，collect 时才真正执行 |
| **可插拔** | 想加操作就加，想去掉就去掉，非常灵活 |

> 💡 **面试考点**：操作符不是在"修改"原来的 Flow，而是在"包装"它。就像俄罗斯套娃，一层套一层。

## 第四章：flowOn 如何切换线程

### 一句话总结

**flowOn 通过 Channel 把数据从一个线程"传送"到另一个线程。**

### 为什么需要 flowOn？

```kotlin
// 问题：整个 Flow 默认在 collect 所在的线程执行
viewModelScope.launch(Dispatchers.Main) {
    flow {
        // ⚠️ 这里也在 Main 线程！
        val data = 网络请求()  // 会卡住 UI！
        emit(data)
    }.collect { updateUI(it) }
}

// 解决：用 flowOn 让上游在 IO 线程执行
viewModelScope.launch(Dispatchers.Main) {
    flow {
        val data = 网络请求()  // 在 IO 线程
        emit(data)
    }
    .flowOn(Dispatchers.IO)  // 切换上游的线程
    .collect { updateUI(it) }  // 在 Main 线程
}
```

### flowOn 的核心原理

```
┌─────────────────────────────────────────────────┐
│              flowOn 工作原理                     │
├─────────────────────────────────────────────────┤
│                                                 │
│  flow { emit(data) }                            │
│         │                                       │
│         │  ← 在 Dispatchers.IO 执行             │
│         ↓                                       │
│  ┌─────────────┐                                │
│  │   Channel   │  ← 数据中转站（跨线程传递）      │
│  └─────────────┘                                │
│         │                                       │
│         │  ← 在 Dispatchers.Main 执行           │
│         ↓                                       │
│  collect { updateUI(it) }                       │
│                                                 │
└─────────────────────────────────────────────────┘
```

**原理解释**：
1. flowOn 创建一个 Channel（管道）
2. 上游在指定的线程（如 IO）中运行，数据发到 Channel
3. 下游在原来的线程（如 Main）中从 Channel 取数据

就像**两个人隔着窗口传递文件**：
- 一个人在仓库（IO 线程）找文件
- 通过窗口（Channel）递出来
- 另一个人在前台（Main 线程）接收

### 为什么不能在 flow 内部用 withContext？

```kotlin
// ❌ 这样会报错！
flow {
    withContext(Dispatchers.IO) {
        emit(data)  // 💥 IllegalStateException
    }
}
```

**原因**：Flow 设计了一个规则——**emit 必须在创建 Flow 的上下文中调用**。

这叫做**上下文保持原则**（Context Preservation），目的是：
1. 保证线程安全（不会在奇怪的线程 emit）
2. 异常传播路径可预测
3. 简化心智模型（你知道 emit 一定在哪个线程）

**解决方案**：用 `flowOn`，它通过 Channel 安全地跨线程传递数据。

## 第五章：StateFlow 的核心设计

### 一句话总结

**StateFlow = 永远有值 + 相同值不重复发射 + 多个订阅者共享同一份数据。**

### StateFlow vs 普通 Flow

| 特性 | Flow | StateFlow |
|-----|------|-----------|
| 有初始值？ | ❌ 没有 | ✅ 必须有 |
| 可以直接读值？ | ❌ 只能 collect | ✅ 可以直接读 `.value` |
| 相同值会发射？ | ✅ 会 | ❌ 不会（去重） |
| 多个收集者？ | 每人一份独立数据 | 共享同一份数据 |

### StateFlow 为什么不发射相同的值？

源码中有这么一段：

```kotlin
private fun updateState(newState: Any): Boolean {
    val oldState = _state.value
    
    // 关键：新值和旧值相同，直接返回，不通知订阅者
    if (oldState == newState) return true
    
    _state.value = newState
    // ... 通知所有订阅者
}
```

**设计意图**：
- StateFlow 是用来表示"状态"的
- 状态没变化 = 不需要更新 UI
- 避免无效的重复渲染

**如果你需要发射相同的值**：用 SharedFlow（它不会去重）。

### StateFlow 的数据结构

```
┌─────────────────────────────────────────────────┐
│             StateFlow 内部结构                   │
├─────────────────────────────────────────────────┤
│                                                 │
│  StateFlowImpl                                  │
│  ├── _state: AtomicReference  ← 存储当前值       │
│  │          （原子操作，保证线程安全）            │
│  │                                              │
│  └── slots: Array<Slot>  ← 所有订阅者的"座位"    │
│            ├── Slot1: 订阅者A 的位置和续体       │
│            ├── Slot2: 订阅者B 的位置和续体       │
│            └── Slot3: 订阅者C 的位置和续体       │
│                                                 │
│  当 value 改变时：                               │
│  1. 更新 _state                                 │
│  2. 唤醒所有 slot 中等待的订阅者                  │
│                                                 │
└─────────────────────────────────────────────────┘
```

## 第六章：SharedFlow 与 stateIn/shareIn

### SharedFlow：可配置的热流

```kotlin
MutableSharedFlow<T>(
    replay = 0,           // 新订阅者能收到几个历史值
    extraBufferCapacity = 0,  // 额外缓冲区大小
    onBufferOverflow = SUSPEND  // 缓冲区满了怎么办
)
```

| 参数 | 说明 | 类比 |
|-----|------|-----|
| replay | 新人进群能看到几条历史消息 | 聊天记录 |
| extraBufferCapacity | 发消息太快时能缓存多少 | 消息队列 |
| onBufferOverflow | 缓存满了怎么办 | SUSPEND=等待，DROP=丢弃 |

### stateIn：冷流变热流

```kotlin
// 把普通 Flow 转成 StateFlow
val stateFlow: StateFlow<Data> = coldFlow.stateIn(
    scope = viewModelScope,        // 在哪个作用域收集
    started = SharingStarted.WhileSubscribed(5000),  // 什么时候开始/停止
    initialValue = Loading         // 初始值
)
```

**原理图解**：

```
┌─────────────────────────────────────────────────┐
│              stateIn 工作原理                    │
├─────────────────────────────────────────────────┤
│                                                 │
│  coldFlow (冷流：每次 collect 都重新执行)         │
│      │                                          │
│      │  stateIn 做的事：                        │
│      │  1. 创建一个 StateFlow                   │
│      │  2. 启动协程去 collect 冷流              │
│      │  3. 把收到的值更新到 StateFlow            │
│      ↓                                          │
│  StateFlow (热流：所有订阅者共享)                │
│      │                                          │
│      ├──→ UI 组件A：collect                      │
│      ├──→ UI 组件B：collect                      │
│      └──→ UI 组件C：collect                      │
│                                                 │
│  好处：冷流只执行一次，所有人共享结果             │
│                                                 │
└─────────────────────────────────────────────────┘
```

### WhileSubscribed 策略

```kotlin
SharingStarted.WhileSubscribed(
    stopTimeoutMillis = 5000  // 没人订阅后等 5 秒再停止
)
```

**工作流程**：

```
订阅者数量:  0 → 1 → 2 → 1 → 0 ──(5s)──→ 0 → 1
              ↓   ↓   ↓   ↓              ↓   ↓
动作:       等待 开始 继续 继续 开始倒计时 停止 重新开始

如果 5 秒内有新订阅者，就不会停止
```

**为什么设计 5 秒延迟？**
- 屏幕旋转时 Activity 会重建，这期间订阅者数量会短暂变成 0
- 5 秒的缓冲期可以避免不必要的重新加载

## 第七章：设计亮点与借鉴

### 1. 极简接口设计

```kotlin
// 整个 Flow 框架的基础就是这两个接口
interface Flow<T> { suspend fun collect(collector: FlowCollector<T>) }
interface FlowCollector<T> { suspend fun emit(value: T) }
```

**启发**：核心接口越简单越好，复杂功能通过扩展实现。

### 2. 组合优于继承

操作符不是通过继承实现，而是通过**包装**：

```kotlin
// 每个操作符都是：创建新 Flow → 收集上游 → 处理 → 发射下游
fun Flow<T>.map(transform: (T) -> R): Flow<R> = flow {
    collect { emit(transform(it)) }
}
```

**启发**：组合更灵活，可以自由插拔，不受继承层级限制。

### 3. 挂起函数实现背压

```kotlin
// emit 和 collect 都是挂起函数
suspend fun emit(value: T)
suspend fun collect(collector: FlowCollector<T>)
```

**背压自动实现**：
- 收集者处理慢 → emit 挂起等待 → 生产者自动减速
- 不需要显式的背压 API，代码写起来像同步代码

### 4. 上下文保持原则

```kotlin
// emit 必须在同一上下文，不能随意切换线程
flow {
    withContext(Dispatchers.IO) {
        emit(1)  // ❌ 报错
    }
}
```

**设计意图**：约束带来安全。限制了灵活性，但换来了线程安全和可预测性。

## 面试检验

### Q1：Flow 的 collect 是怎么工作的？

> **答案**：Flow 只有一个方法 `collect(collector)`。
> 
> 当调用 collect 时：
> 1. 执行 Flow 内部的代码（生产者逻辑）
> 2. 每次 emit(value) 就是调用 collector.emit(value)
> 3. collector.emit 就是我们传入的处理逻辑
> 
> **本质是函数调用**，没有任何魔法。

### Q2：操作符链是如何执行的？

> **答案**：每个操作符创建一个新 Flow，包装原来的 Flow。
> 
> 执行时像剥洋葱：最外层的 collect 触发里层的 collect，一层一层往里调用，数据从最里层一层一层往外传。
>
> ```
> 构建：flowOf → map 包装 → filter 包装
> 执行：filter.collect → map.collect → flowOf.collect → 数据往回传
> ```

### Q3：flowOn 是如何切换线程的？

> **答案**：通过 Channel 实现。
> 
> 1. 创建一个 Channel 作为中转
> 2. 在指定线程启动协程收集上游，数据发到 Channel
> 3. 下游从 Channel 取数据
> 
> 本质是**两个协程通过 Channel 通信**，实现跨线程传递。

### Q4：StateFlow 为什么不发射相同的值？

> **答案**：源码中有判断 `if (oldState == newState) return`。
> 
> **设计意图**：StateFlow 表示"状态"，状态没变就不需要通知。这样可以避免无效的 UI 更新。
> 
> 如果需要发射相同值，用 SharedFlow。

### Q5：为什么 Flow 不允许在内部用 withContext？

> **答案**：这是 Flow 的"上下文保持原则"。
> 
> **原因**：
> 1. 保证 emit 在可预测的线程执行
> 2. 简化异常处理和线程安全
> 3. 让代码更容易理解
> 
> **解决方案**：用 flowOn，它通过 Channel 安全地跨线程传递。
