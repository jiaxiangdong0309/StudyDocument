# Lifecycle 进阶篇

## 高级特性

### ProcessLifecycleOwner：监听应用前后台

有时候我们需要知道整个应用（而不是单个 Activity）是否在前台。比如：
- 用户切到后台时暂停音乐
- 统计应用使用时长
- 后台时断开 WebSocket 节省流量

**ProcessLifecycleOwner** 就是为这个场景设计的：

```kotlin
// 添加依赖
// implementation("androidx.lifecycle:lifecycle-process:2.7.0")

class MyApplication : Application() {
    
    override fun onCreate() {
        super.onCreate()
        
        // 监听应用级别的生命周期
        ProcessLifecycleOwner.get().lifecycle.addObserver(AppLifecycleObserver())
    }
}

class AppLifecycleObserver : DefaultLifecycleObserver {
    
    override fun onStart(owner: LifecycleOwner) {
        // 应用进入前台（至少有一个 Activity 可见）
        Log.d("AppLifecycle", "应用进入前台")
        Analytics.trackAppForeground()
        WebSocketManager.connect()
    }
    
    override fun onStop(owner: LifecycleOwner) {
        // 应用进入后台（所有 Activity 不可见）
        Log.d("AppLifecycle", "应用进入后台")
        Analytics.trackAppBackground()
        WebSocketManager.disconnect()
    }
}
```

**ProcessLifecycleOwner 的特点**：

| 特性 | 说明 |
|-----|------|
| 不会触发 ON_DESTROY | 进程死亡时不会回调 |
| ON_START 延迟约 700ms | 避免 Activity 切换时的误判 |
| 整个应用只有一个实例 | 单例模式 |

```
┌─────────────────────────────────────────────────────────────────┐
│              ProcessLifecycleOwner 工作原理                      │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   Activity A          Activity B                                │
│   ┌────────┐          ┌────────┐                                │
│   │ onStart │──────►  │ onStart │   ProcessLifecycle: STARTED   │
│   │ onStop  │◄──────  │ onStop  │   (保持前台)                   │
│   └────────┘          └────────┘                                │
│                                                                 │
│   从 A 切换到 B 时，应用始终是 STARTED 状态                        │
│   不会触发 ProcessLifecycle 的 onStop                            │
│                                                                 │
│   ─────────────────────────────────────────────────────────     │
│                                                                 │
│   所有 Activity 都 onStop:                                       │
│                                                                 │
│   Activity A          Activity B                                │
│   ┌────────┐          ┌────────┐                                │
│   │ onStop  │          │ onStop  │   → 等待约 700ms              │
│   └────────┘          └────────┘   → ProcessLifecycle: onStop   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 自定义 LifecycleOwner

有时候我们需要让非 Activity/Fragment 的组件也能发出生命周期事件。

**核心类解释**：

| 类名 | 作用 | 大白话 |
|-----|------|-------|
| **LifecycleRegistry** | Lifecycle 的具体实现类，负责管理状态和分发事件 | 广播站的控制台，你按按钮（触发事件），它就广播 |
| **LifecycleOwner** | 接口，表示"我有生命周期" | 广播站的招牌，告诉别人"这里能订阅" |

**场景一：Service 中使用 Lifecycle**

> **提示**：实际开发中推荐直接继承 `LifecycleService`（Jetpack 已提供），下面的代码是为了理解原理。

```kotlin
// 先定义一个观察者（用于演示）
class LogObserver : DefaultLifecycleObserver {
    override fun onStart(owner: LifecycleOwner) {
        Log.d("LogObserver", "Service 启动了")
    }
    override fun onStop(owner: LifecycleOwner) {
        Log.d("LogObserver", "Service 停止了")
    }
}

// 自定义 LifecycleOwner 的 Service
class MyLifecycleService : Service(), LifecycleOwner {
    
    // LifecycleRegistry：Lifecycle 的实现类，负责：
    // 1. 保存当前状态（State）
    // 2. 管理所有观察者
    // 3. 状态变化时通知观察者
    private val lifecycleRegistry = LifecycleRegistry(this)
    
    // 实现 LifecycleOwner 接口，返回我们的 LifecycleRegistry
    override val lifecycle: Lifecycle
        get() = lifecycleRegistry
    
    override fun onCreate() {
        super.onCreate()
        // 通过事件驱动状态变化（推荐方式）
        lifecycleRegistry.handleLifecycleEvent(Lifecycle.Event.ON_CREATE)
        // 现在可以添加观察者了
        lifecycle.addObserver(LogObserver())
    }
    
    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        // Service 没有 onStart()，用 onStartCommand 触发 ON_START 事件
        lifecycleRegistry.handleLifecycleEvent(Lifecycle.Event.ON_START)
        return START_STICKY
    }
    
    override fun onDestroy() {
        // 先触发 STOP，再触发 DESTROY（模拟完整生命周期）
        lifecycleRegistry.handleLifecycleEvent(Lifecycle.Event.ON_STOP)
        lifecycleRegistry.handleLifecycleEvent(Lifecycle.Event.ON_DESTROY)
        super.onDestroy()
    }
    
    override fun onBind(intent: Intent?): IBinder? = null
}

// ✅ 更简单的方式：直接用 Jetpack 提供的 LifecycleService
class SimpleLifecycleService : LifecycleService() {
    override fun onCreate() {
        super.onCreate()
        lifecycle.addObserver(LogObserver())  // 直接用，不用自己管理
    }
}
```

**场景三：任意对象的生命周期管理**

```kotlin
// 比如管理一个任务的生命周期
class TaskLifecycleOwner : LifecycleOwner {
    
    private val lifecycleRegistry = LifecycleRegistry(this)
    
    override val lifecycle: Lifecycle
        get() = lifecycleRegistry
    
    fun startTask() {
        lifecycleRegistry.currentState = Lifecycle.State.STARTED
    }
    
    fun pauseTask() {
        lifecycleRegistry.currentState = Lifecycle.State.CREATED
    }
    
    fun finishTask() {
        lifecycleRegistry.currentState = Lifecycle.State.DESTROYED
    }
}

// 使用
val taskOwner = TaskLifecycleOwner()
taskOwner.lifecycle.addObserver(object : DefaultLifecycleObserver {
    override fun onStart(owner: LifecycleOwner) {
        Log.d("Task", "任务开始")
    }
    override fun onStop(owner: LifecycleOwner) {
        Log.d("Task", "任务暂停")
    }
    override fun onDestroy(owner: LifecycleOwner) {
        Log.d("Task", "任务结束")
    }
})

taskOwner.startTask()  // 触发 onStart
taskOwner.pauseTask()  // 触发 onStop
taskOwner.finishTask() // 触发 onDestroy
```

### Lifecycle 与协程深度集成

```kotlin
class ModernActivity : AppCompatActivity() {
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        
        // 方式一：lifecycleScope - 跟随 Activity 生命周期
        lifecycleScope.launch {
            // Activity destroy 时自动取消
            loadInitialData()
        }
        
        // 方式二：repeatOnLifecycle - 只在特定状态执行
        lifecycleScope.launch {
            // 只在 STARTED 状态时收集，STOPPED 时暂停
            // Activity 重新 START 时自动恢复
            repeatOnLifecycle(Lifecycle.State.STARTED) {
                viewModel.uiState.collect { state ->
                    updateUI(state)
                }
            }
        }
        
        // 方式三：flowWithLifecycle - Flow 扩展
        lifecycleScope.launch {
            viewModel.events
                .flowWithLifecycle(lifecycle, Lifecycle.State.STARTED)
                .collect { event ->
                    handleEvent(event)
                }
        }
    }
}
```

**repeatOnLifecycle vs launchWhenStarted**

```kotlin
// ❌ 不推荐：launchWhenStarted（已废弃）
// 问题：只是挂起，不会取消上游 Flow，可能浪费资源
lifecycleScope.launchWhenStarted {
    coldFlow.collect { /* ... */ }
}

// ✅ 推荐：repeatOnLifecycle
// 生命周期低于 STARTED 时，整个 block 取消并重新启动
lifecycleScope.launch {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        coldFlow.collect { /* ... */ }
    }
}
```

## 实战经验

### 经验一：多 Activity 场景下的数据同步

```kotlin
// 使用全局事件总线 + ProcessLifecycleOwner
class AppEventBus : DefaultLifecycleObserver {
    
    private val _events = MutableSharedFlow<AppEvent>()
    val events: SharedFlow<AppEvent> = _events
    
    private var scope: CoroutineScope? = null
    
    override fun onStart(owner: LifecycleOwner) {
        scope = CoroutineScope(SupervisorJob() + Dispatchers.Main)
    }
    
    override fun onStop(owner: LifecycleOwner) {
        scope?.cancel()
        scope = null
    }
    
    fun emit(event: AppEvent) {
        scope?.launch {
            _events.emit(event)
        }
    }
    
    companion object {
        val instance by lazy { AppEventBus() }
        
        fun init(application: Application) {
            ProcessLifecycleOwner.get().lifecycle.addObserver(instance)
        }
    }
}
```

### 经验二：避免生命周期回调中的耗时操作

```kotlin
class MyObserver : DefaultLifecycleObserver {
    
    // ❌ 不好：onStart 里做耗时操作会阻塞 UI
    override fun onStart(owner: LifecycleOwner) {
        // 这会阻塞主线程！
        val data = heavyComputation()
        updateUI(data)
    }
    
    // ✅ 好的：异步处理
    override fun onStart(owner: LifecycleOwner) {
        (owner as? LifecycleOwner)?.lifecycleScope?.launch {
            val data = withContext(Dispatchers.IO) {
                heavyComputation()
            }
            // 检查生命周期，避免在 STOPPED 后更新 UI
            if (owner.lifecycle.currentState.isAtLeast(Lifecycle.State.STARTED)) {
                updateUI(data)
            }
        }
    }
}
```

### 经验三：处理快速生命周期变化

用户可能快速切换页面，导致生命周期方法快速连续调用：

```kotlin
class StableNetworkObserver : DefaultLifecycleObserver {
    
    private var connectJob: Job? = null
    private var disconnectJob: Job? = null
    
    override fun onStart(owner: LifecycleOwner) {
        // 取消断开连接的任务
        disconnectJob?.cancel()
        
        connectJob = (owner as LifecycleOwner).lifecycleScope.launch {
            // 延迟一小段时间，避免快速切换时重复连接
            delay(300)
            if (isActive) {
                NetworkClient.connect()
            }
        }
    }
    
    override fun onStop(owner: LifecycleOwner) {
        // 取消连接任务
        connectJob?.cancel()
        
        disconnectJob = (owner as LifecycleOwner).lifecycleScope.launch {
            // 延迟断开，给用户切换 Activity 的时间
            delay(500)
            if (isActive) {
                NetworkClient.disconnect()
            }
        }
    }
}
```

### 经验四：Fragment 的双重生命周期处理

```kotlin
class ComplexFragment : Fragment() {
    
    // 与 Fragment 生命周期绑定的组件
    private val fragmentScopedObserver = object : DefaultLifecycleObserver {
        override fun onCreate(owner: LifecycleOwner) {
            Log.d("TAG", "Fragment 创建，初始化非 UI 资源")
        }
        override fun onDestroy(owner: LifecycleOwner) {
            Log.d("TAG", "Fragment 销毁，释放非 UI 资源")
        }
    }
    
    // 与 View 生命周期绑定的组件
    private val viewScopedObserver = object : DefaultLifecycleObserver {
        override fun onStart(owner: LifecycleOwner) {
            Log.d("TAG", "View 可见，开始动画/监听")
        }
        override fun onStop(owner: LifecycleOwner) {
            Log.d("TAG", "View 不可见，停止动画/监听")
        }
    }
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        lifecycle.addObserver(fragmentScopedObserver)
    }
    
    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        viewLifecycleOwner.lifecycle.addObserver(viewScopedObserver)
    }
}
```

## 横向对比

### Lifecycle vs RxJava 的 Disposable 管理

| 方面 | Lifecycle | RxJava CompositeDisposable |
|-----|----------|---------------------------|
| 学习成本 | 低，Android 原生 | 中，需要学习 RxJava |
| 自动化程度 | 自动感知，无需手动调用 | 需要在 onDestroy 手动 dispose |
| 粒度 | Activity/Fragment 级别 | 任意粒度 |
| 依赖 | AndroidX（默认包含） | 额外依赖 |
| 与 Flow 集成 | 完美集成 | 需要转换 |

```kotlin
// RxJava 方式
class RxActivity : AppCompatActivity() {
    private val disposables = CompositeDisposable()
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        disposables.add(
            api.getData()
                .subscribeOn(Schedulers.io())
                .observeOn(AndroidSchedulers.mainThread())
                .subscribe { data -> updateUI(data) }
        )
    }
    
    override fun onDestroy() {
        disposables.dispose()  // 必须手动调用！
        super.onDestroy()
    }
}

// Lifecycle + Flow 方式
class FlowActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        lifecycleScope.launch {
            repeatOnLifecycle(Lifecycle.State.STARTED) {
                api.getDataFlow().collect { data -> updateUI(data) }
            }
        }
        // 不需要手动释放，自动跟随生命周期
    }
}
```

### Lifecycle vs Jetpack Compose 的生命周期

```kotlin
// 传统 View 系统：Lifecycle + LifecycleObserver
class TraditionalActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        lifecycle.addObserver(MyObserver())
    }
}

// Compose：DisposableEffect + LifecycleEventEffect
@Composable
fun MyScreen() {
    val lifecycleOwner = LocalLifecycleOwner.current
    
    // 方式一：DisposableEffect
    DisposableEffect(lifecycleOwner) {
        val observer = LifecycleEventObserver { _, event ->
            when (event) {
                Lifecycle.Event.ON_START -> { /* 开始 */ }
                Lifecycle.Event.ON_STOP -> { /* 停止 */ }
                else -> {}
            }
        }
        lifecycleOwner.lifecycle.addObserver(observer)
        onDispose {
            lifecycleOwner.lifecycle.removeObserver(observer)
        }
    }
    
    // 方式二：LifecycleEventEffect（更简洁，需要依赖）
    LifecycleEventEffect(Lifecycle.Event.ON_START) {
        // 页面进入前台
    }
    LifecycleEventEffect(Lifecycle.Event.ON_STOP) {
        // 页面进入后台
    }
}
```

## 边界认知

### Lifecycle 不适用的场景

| 场景 | 问题 | 替代方案 |
|-----|------|---------|
| 后台长时间任务 | Activity 销毁后任务中断 | WorkManager |
| 跨进程生命周期 | Lifecycle 只在单进程有效 | AIDL + 自定义协议 |
| 精确计时 | 生命周期回调有延迟 | Handler / AlarmManager |
| 前台服务 | Service 生命周期和 Activity 不同 | 自定义 LifecycleOwner |

### 常见误区

**误区一：Lifecycle 能防止所有内存泄漏**

```kotlin
// ❌ 错误认知
class LeakyObserver(private val activity: Activity) : DefaultLifecycleObserver {
    // 即使实现了 LifecycleObserver，持有 Activity 引用仍然可能泄漏
    // 如果这个 Observer 被其他长生命周期对象引用...
}

// ✅ Lifecycle 只是在 DESTROYED 时移除观察者
// 真正防止泄漏需要：
// 1. 不持有 Activity/View 的直接引用
// 2. 使用弱引用
// 3. 或使用 Application Context
```

**误区二：onDestroy 一定会被调用**

```kotlin
class MyObserver : DefaultLifecycleObserver {
    override fun onDestroy(owner: LifecycleOwner) {
        // ⚠️ 进程被杀死时，这里不会被调用！
        saveImportantData()
    }
}

// 关键数据应该在 onStop 保存
override fun onStop(owner: LifecycleOwner) {
    saveImportantData()  // ✅ 更可靠
}
```

**误区三：ProcessLifecycleOwner 能检测应用退出**

```kotlin
// ❌ 这样检测应用退出是不可靠的
class AppObserver : DefaultLifecycleObserver {
    override fun onStop(owner: LifecycleOwner) {
        // 这只表示所有 Activity 不可见
        // 可能是切到后台，也可能是打开了另一个 App 的 Activity
        // 不代表应用真的退出了
    }
    
    override fun onDestroy(owner: LifecycleOwner) {
        // ProcessLifecycleOwner 永远不会触发 onDestroy！
    }
}
```

### 性能考量

```kotlin
// ❌ 不好：每次 onStart 都创建新对象
class InefficientObserver : DefaultLifecycleObserver {
    override fun onStart(owner: LifecycleOwner) {
        val listener = object : SomeListener {
            // 每次都创建新的匿名类实例
        }
        register(listener)
    }
}

// ✅ 好的：复用对象
class EfficientObserver : DefaultLifecycleObserver, SomeListener {
    override fun onStart(owner: LifecycleOwner) {
        register(this)  // 复用自身
    }
    
    override fun onStop(owner: LifecycleOwner) {
        unregister(this)
    }
}
```

## 面试检验

### 进阶应用题

**Q1：如何监听应用进入前台/后台？有什么注意事项？**

> **答案**：使用 `ProcessLifecycleOwner`：
> ```kotlin
> ProcessLifecycleOwner.get().lifecycle.addObserver(object : DefaultLifecycleObserver {
>     override fun onStart(owner: LifecycleOwner) { /* 前台 */ }
>     override fun onStop(owner: LifecycleOwner) { /* 后台 */ }
> })
> ```
> **注意事项**：
> 1. ON_START 有约 700ms 延迟，避免 Activity 切换时误判
> 2. ON_DESTROY 永远不会触发
> 3. 进程被杀死时不会有任何回调

**Q2：Fragment 的 lifecycle 和 viewLifecycleOwner.lifecycle 有什么区别？什么时候用哪个？**

> **答案**：
> - `lifecycle`：Fragment 自身的生命周期，从 attach 到 detach
> - `viewLifecycleOwner.lifecycle`：Fragment View 的生命周期，从 onCreateView 到 onDestroyView
> 
> **区别场景**：Fragment 在返回栈中时，View 被销毁但 Fragment 还活着。
> 
> **使用建议**：
> - 观察 LiveData → 用 `viewLifecycleOwner`（避免重复订阅）
> - 非 UI 资源管理 → 用 `lifecycle`

**Q3：如何让自定义 View 感知生命周期？**

> **答案**：两种方式：
> 1. View 实现 LifecycleObserver，在 Activity 中手动注册
> 2. 使用 `findViewTreeLifecycleOwner()` 自动获取
> ```kotlin
> class MyView : View {
>     override fun onAttachedToWindow() {
>         findViewTreeLifecycleOwner()?.lifecycle?.addObserver(myObserver)
>     }
>     override fun onDetachedFromWindow() {
>         findViewTreeLifecycleOwner()?.lifecycle?.removeObserver(myObserver)
>     }
> }
> ```

**Q4：repeatOnLifecycle 和 launchWhenStarted 有什么区别？为什么推荐前者？**

> **答案**：
> - `launchWhenStarted`：生命周期低于 STARTED 时**挂起**协程，但不取消上游 Flow
> - `repeatOnLifecycle`：生命周期低于 STARTED 时**取消**整个 block，恢复时重新执行
> 
> **推荐 repeatOnLifecycle 的原因**：
> 1. launchWhenStarted 只是挂起，上游 Flow 继续发射，浪费资源
> 2. 冷 Flow 的数据会堆积，恢复时可能收到过时数据
> 3. launchWhenStarted 已被标记废弃

**Q5：LifecycleRegistry 的 setCurrentState 方法有什么限制？**

> **答案**：
> 1. 只能在主线程调用（除非使用线程安全版本）
> 2. 状态只能按正确顺序转换：
>    - 正向：INITIALIZED → CREATED → STARTED → RESUMED
>    - 逆向：RESUMED → STARTED → CREATED → DESTROYED
> 3. 不能跳跃状态，比如直接从 INITIALIZED 到 RESUMED

**Q6：多个 Observer 的回调顺序是怎样的？**

> **答案**：
> - **正向事件**（ON_CREATE、ON_START、ON_RESUME）：先添加的先收到
> - **逆向事件**（ON_PAUSE、ON_STOP、ON_DESTROY）：后添加的先收到（LIFO）
> 
> 这种设计符合"嵌套"的资源管理语义：先申请的资源后释放。
