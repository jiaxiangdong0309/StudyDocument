# 协程基础篇

## 技术演进：为什么需要协程？

### 痛点一：回调地狱（Callback Hell）

Android 开发中，网络请求、数据库操作等都是耗时操作，必须在后台线程执行。传统方式是用回调：

```kotlin
// 😱 回调地狱：登录 → 获取用户信息 → 获取订单列表
loginApi.login(username, password, object : Callback<Token> {
    override fun onSuccess(token: Token) {
        userApi.getUserInfo(token, object : Callback<User> {
            override fun onSuccess(user: User) {
                orderApi.getOrders(user.id, object : Callback<List<Order>> {
                    override fun onSuccess(orders: List<Order>) {
                        // 终于拿到了...但如果还要继续嵌套呢？
                        runOnUiThread {
                            showOrders(orders)
                        }
                    }
                    override fun onFailure(e: Exception) {
                        // 还要处理异常...
                    }
                })
            }
            override fun onFailure(e: Exception) { /* ... */ }
        })
    }
    override fun onFailure(e: Exception) { /* ... */ }
})
```

问题：
- **嵌套深**：逻辑层层嵌套，代码横向发展，难以阅读
- **异常处理散落**：每层回调都要处理异常
- **难以取消**：用户离开页面了，回调还在执行
- **难以组合**：想并行请求多个接口，然后合并结果？噩梦！

### 痛点二：线程管理复杂

```kotlin
// 手动管理线程
class OldSchoolActivity : AppCompatActivity() {
    
    private val executor = Executors.newFixedThreadPool(4)
    private val handler = Handler(Looper.getMainLooper())
    
    fun loadData() {
        executor.execute {
            try {
                val data = fetchFromNetwork()  // 后台线程
                handler.post {                  // 切回主线程
                    updateUI(data)
                }
            } catch (e: Exception) {
                handler.post {
                    showError(e)
                }
            }
        }
    }
    
    override fun onDestroy() {
        super.onDestroy()
        executor.shutdown()  // 别忘了关闭！
        // 但是正在执行的任务怎么办？可能会更新已销毁的 UI！
    }
}
```

### 痛点三：RxJava 学习曲线陡峭

RxJava 确实解决了回调地狱，但引入了新的问题：

```kotlin
// RxJava 版本：好多操作符要记...
loginApi.login(username, password)
    .flatMap { token -> userApi.getUserInfo(token) }
    .flatMap { user -> orderApi.getOrders(user.id) }
    .subscribeOn(Schedulers.io())
    .observeOn(AndroidSchedulers.mainThread())
    .subscribe(
        { orders -> showOrders(orders) },
        { error -> showError(error) }
    )
// 还要处理 Disposable，不然内存泄漏...
```

- **操作符太多**：`map`、`flatMap`、`switchMap`、`zip`... 选择困难症
- **调试困难**：堆栈信息难以阅读
- **库体积大**：增加 APK 大小

### 协程的诞生

Google 在 2019 年宣布协程成为 Android 官方推荐的异步方案。用协程重写上面的例子：

```kotlin
// ✅ 协程：像写同步代码一样
suspend fun loadData() {
    val token = loginApi.login(username, password)  // 挂起，等待
    val user = userApi.getUserInfo(token)            // 挂起，等待
    val orders = orderApi.getOrders(user.id)         // 挂起，等待
    showOrders(orders)                               // 更新 UI
}

// 在 ViewModel 中调用
fun onLoadClick() {
    viewModelScope.launch {
        try {
            loadData()
        } catch (e: Exception) {
            showError(e)  // 异常处理就是 try-catch！
        }
    }
}
```

**协程的优势**：
- **同步写法**：代码从上到下执行，逻辑清晰
- **异常处理简单**：直接 try-catch
- **自动生命周期管理**：配合 viewModelScope，页面销毁自动取消
- **轻量级**：一个线程可以跑几十万个协程

## 核心概念：用大白话说清楚

### 协程 vs 线程

很多人问"协程和线程有什么区别？"，其实这个问题本身就有点问题——它们不是同一层面的东西。

| 维度 | 线程 | 协程 |
|-----|------|------|
| **本质** | 操作系统调度的执行单元 | 用户态的代码执行单元 |
| **创建开销** | 较大（约 1MB 栈内存） | 极小（约几十字节对象） |
| **数量限制** | 几百到几千 | 几十万甚至更多 |
| **切换开销** | 较大（内核态切换） | 极小（用户态切换） |
| **调度方式** | 操作系统抢占式调度 | 程序员协作式调度 |

**大白话理解**：
- **线程**就像餐厅里的服务员，每个服务员要占一定资源（工资、工位），人数有限
- **协程**就像服务员手里的订单，一个服务员可以同时处理多张订单，遇到等待（比如后厨做菜）就先处理其他订单

```
┌─────────────────────────────────────────────────────────────────┐
│                    线程 vs 协程 形象对比                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  线程模型（一对一）                协程模型（多对一）              │
│  ┌───────────┐                   ┌───────────┐                  │
│  │  任务 A   │ → 线程 1          │  任务 A   │ ┐                │
│  └───────────┘                   ├───────────┤ │                │
│  ┌───────────┐                   │  任务 B   │ ├─→ 线程 1       │
│  │  任务 B   │ → 线程 2          ├───────────┤ │                │
│  └───────────┘                   │  任务 C   │ ┘                │
│  ┌───────────┐                   └───────────┘                  │
│  │  任务 C   │ → 线程 3          ┌───────────┐                  │
│  └───────────┘                   │  任务 D   │ ┐                │
│                                  ├───────────┤ ├─→ 线程 2       │
│  需要 3 个线程                    │  任务 E   │ ┘                │
│                                  └───────────┘                  │
│                                                                 │
│                                  只需要 2 个线程                 │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 什么是"挂起"（Suspend）？

**挂起不是阻塞！** 这是理解协程的关键。

```kotlin
// 阻塞：线程傻等，什么都干不了
Thread.sleep(1000)  // 线程被占用 1 秒

// 挂起：协程暂停，线程去干别的事
delay(1000)  // 协程挂起，线程可以执行其他协程
```

**生活例子**：
- **阻塞**：你在银行排队，轮到你办业务时发现要等审核，但你不能离开，只能傻站着等
- **挂起**：你在银行取号后，发现前面还有 50 人，于是你去旁边喝杯咖啡，等叫号再回来

```
┌─────────────────────────────────────────────────────────────────┐
│                      挂起 vs 阻塞 对比                           │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  阻塞（线程被占用）              挂起（线程被释放）                │
│                                                                 │
│  线程 ────────────────           线程 ────────────────           │
│         │         │                    │         │              │
│         │ 任务 A   │                    │ 任务 A  │              │
│         │ 等待中   │                    │   ↓     │              │
│         │ (傻等)   │                    │ 挂起    │              │
│         │         │                    │   │     │              │
│         ▼         │                    │ 任务 B  │ ← 执行其他任务 │
│                   │                    │   │     │              │
│  线程利用率：低    │                    │ 任务 A  │ ← 恢复         │
│                   │                    │   ↓     │              │
│                                        │ 继续    │              │
│                                                                 │
│                                  线程利用率：高                   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### suspend 关键字

`suspend` 修饰的函数叫做**挂起函数**，它可以在内部调用其他挂起函数。

```kotlin
// suspend 函数：可以挂起，可以恢复
suspend fun fetchUser(): User {
    delay(1000)  // 挂起 1 秒（模拟网络请求）
    return User("张三")
}

// 普通函数不能直接调用 suspend 函数
fun normalFunction() {
    // fetchUser()  // ❌ 编译错误！
}

// suspend 函数可以调用其他 suspend 函数
suspend fun loadData() {
    val user = fetchUser()  // ✅ 正确
    println(user)
}
```

**suspend 的本质**：
- `suspend` 只是一个**标记**，告诉编译器"这个函数可能会挂起"
- 编译器会对 suspend 函数进行 **CPS 转换**（Continuation Passing Style），生成状态机代码
- suspend 函数本身**不会**切换线程，切换线程是 Dispatcher 的工作

### CoroutineScope：协程的"管理员"

每个协程都需要一个**作用域**（Scope）来管理，这是**结构化并发**的基础。

```kotlin
// 协程作用域：管理协程的生命周期
class MyViewModel : ViewModel() {
    
    fun loadData() {
        // viewModelScope：ViewModel 自带的作用域
        // ViewModel 销毁时，里面的协程自动取消
        viewModelScope.launch {
            val data = fetchData()
            _uiState.value = data
        }
    }
}

class MyActivity : AppCompatActivity() {
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        
        // lifecycleScope：Activity/Fragment 自带的作用域
        // Activity 销毁时，里面的协程自动取消
        lifecycleScope.launch {
            val data = loadData()
            showData(data)
        }
    }
}
```

**为什么需要作用域？**

没有作用域的世界（假设）：
```kotlin
// ❌ 危险：协程泄漏
fun loadData() {
    GlobalScope.launch {  // 全局作用域，不跟随任何生命周期
        delay(10000)      // 10 秒后
        updateUI()        // Activity 早销毁了，崩溃！
    }
}
```

有作用域的世界：
```kotlin
// ✅ 安全：协程跟随生命周期
fun loadData() {
    lifecycleScope.launch {  // 跟随 Activity 生命周期
        delay(10000)
        updateUI()  // Activity 销毁了，这个协程早被取消了
    }
}
```

### 常见的 CoroutineScope

| 作用域 | 来源 | 生命周期 | 使用场景 |
|-------|------|---------|---------|
| `viewModelScope` | ViewModel | ViewModel 存活期间 | ViewModel 中的数据加载 |
| `lifecycleScope` | Activity/Fragment | Activity/Fragment 存活期间 | UI 相关操作 |
| `GlobalScope` | 全局 | 应用存活期间 | 极少使用，容易泄漏 |
| `CoroutineScope()` | 手动创建 | 手动管理 | 特殊场景，如 Service |

### 2. launch：启动协程

`launch` 是最常用的协程启动方式，适合**不需要返回值**的场景。

```kotlin
class NewsViewModel : ViewModel() {
    
    private val _news = MutableStateFlow<List<News>>(emptyList())
    val news: StateFlow<List<News>> = _news
    
    fun loadNews() {
        // launch 返回 Job，用于控制协程
        val job: Job = viewModelScope.launch {
            // 这里是协程体，运行在主线程（viewModelScope 默认）
            try {
                val newsList = newsRepository.getNews()  // suspend 函数
                _news.value = newsList
            } catch (e: Exception) {
                // 处理异常
                Log.e("NewsVM", "加载失败", e)
            }
        }
        
        // 可以取消协程
        // job.cancel()
    }
}
```

### 3. async：获取返回值

`async` 用于**需要返回值**的场景，它返回 `Deferred` 对象，通过 `await()` 获取结果。

```kotlin
class ProfileViewModel : ViewModel() {
    
    fun loadProfile() {
        viewModelScope.launch {
            // 并行请求用户信息和订单
            val userDeferred: Deferred<User> = async { 
                userRepository.getUser()  // suspend 函数
            }
            val ordersDeferred: Deferred<List<Order>> = async { 
                orderRepository.getOrders()  // suspend 函数
            }
            
            // await() 获取结果，会挂起直到结果返回
            val user = userDeferred.await()
            val orders = ordersDeferred.await()
            
            // 两个请求并行完成后，更新 UI
            _profileState.value = ProfileState(user, orders)
        }
    }
}
```

### launch vs async 对比

| 特性 | launch | async |
|-----|--------|-------|
| 返回类型 | `Job` | `Deferred<T>` |
| 获取结果 | 无法获取 | `await()` |
| 异常传播 | 立即传播 | `await()` 时传播 |
| 使用场景 | 不需要返回值 | 需要返回值 |

```kotlin
// 场景：用户点击按钮，保存数据（不需要返回值）
button.setOnClickListener {
    lifecycleScope.launch {
        repository.saveData(data)  // launch 够用
        showToast("保存成功")
    }
}

// 场景：并行请求多个接口，合并结果（需要返回值）
suspend fun loadDashboard(): Dashboard {
    return coroutineScope {
        val user = async { getUser() }
        val stats = async { getStats() }
        val notifications = async { getNotifications() }
        
        Dashboard(
            user = user.await(),
            stats = stats.await(),
            notifications = notifications.await()
        )
    }
}
```

### 4. withContext：切换线程

```kotlin
class ImageProcessor(private val context: Context) {
    
    // 在 IO 线程处理图片，返回主线程
    suspend fun processImage(uri: Uri): Bitmap {
        // withContext 会挂起当前协程，切换到指定线程执行
        return withContext(Dispatchers.IO) {
            // 这个块在 IO 线程执行
            val inputStream = context.contentResolver.openInputStream(uri)
            val bitmap = BitmapFactory.decodeStream(inputStream)
            
            // 耗时的图片处理
            applyFilter(bitmap)
        }
        // 返回后自动回到原来的线程
    }
}

// 使用
lifecycleScope.launch {
    // 主线程
    showLoading()
    
    val bitmap = imageProcessor.processImage(uri)  // 自动切到 IO 再切回来
    
    // 主线程
    imageView.setImageBitmap(bitmap)
    hideLoading()
}
```

### 5. Dispatchers：调度器

调度器决定协程在**哪个线程**执行。

| 调度器 | 线程 | 使用场景 |
|-------|------|---------|
| `Dispatchers.Main` | Android 主线程 | 更新 UI |
| `Dispatchers.IO` | IO 线程池 | 网络请求、文件读写、数据库操作 |
| `Dispatchers.Default` | 计算线程池 | CPU 密集型任务（排序、解析） |
| `Dispatchers.Unconfined` | 不限定（当前线程） | 很少使用 |

```kotlin
viewModelScope.launch {
    // 默认在 Main 线程
    
    val data = withContext(Dispatchers.IO) {
        // 切到 IO 线程，执行网络请求
        api.fetchData()
    }
    
    val processed = withContext(Dispatchers.Default) {
        // 切到 Default 线程，执行 CPU 密集计算
        heavyProcessing(data)
    }
    
    // 自动回到 Main 线程
    updateUI(processed)
}
```

**最佳实践**：让 Repository/DataSource 决定使用什么调度器

```kotlin
// ✅ 好的设计：Repository 内部处理线程切换
class UserRepository(
    private val api: UserApi,
    private val ioDispatcher: CoroutineDispatcher = Dispatchers.IO
) {
    suspend fun getUser(): User = withContext(ioDispatcher) {
        api.getUser()
    }
}

// ViewModel 不需要关心线程
class UserViewModel(private val repo: UserRepository) : ViewModel() {
    fun loadUser() {
        viewModelScope.launch {
            val user = repo.getUser()  // 不用关心在哪个线程
            _user.value = user
        }
    }
}
```

class SearchViewModel : ViewModel() {

## 实际应用场景

### 场景一：网络请求（Retrofit + 协程）

```kotlin
// 1. 定义 API 接口
interface UserApi {
    @GET("users/{id}")
    suspend fun getUser(@Path("id") id: String): User
    
    @GET("users/{id}/orders")
    suspend fun getOrders(@Path("id") userId: String): List<Order>
}

// 2. Repository
class UserRepository(
    private val api: UserApi,
    private val ioDispatcher: CoroutineDispatcher = Dispatchers.IO
) {
    suspend fun getUserWithOrders(userId: String): UserWithOrders {
        return withContext(ioDispatcher) {
            // 并行请求
            coroutineScope {
                val user = async { api.getUser(userId) }
                val orders = async { api.getOrders(userId) }
                UserWithOrders(user.await(), orders.await())
            }
        }
    }
}

// 3. ViewModel
class UserViewModel(private val repo: UserRepository) : ViewModel() {
    
    private val _uiState = MutableStateFlow<UiState>(UiState.Loading)
    val uiState: StateFlow<UiState> = _uiState
    
    fun loadUser(userId: String) {
        viewModelScope.launch {
            _uiState.value = UiState.Loading
            
            try {
                val data = repo.getUserWithOrders(userId)
                _uiState.value = UiState.Success(data)
            } catch (e: Exception) {
                _uiState.value = UiState.Error(e.message ?: "未知错误")
            }
        }
    }
}

// 4. UI 层（Activity/Fragment）
class UserActivity : AppCompatActivity() {
    
    private val viewModel: UserViewModel by viewModels()
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        
        lifecycleScope.launch {
            repeatOnLifecycle(Lifecycle.State.STARTED) {
                viewModel.uiState.collect { state ->
                    when (state) {
                        is UiState.Loading -> showLoading()
                        is UiState.Success -> showData(state.data)
                        is UiState.Error -> showError(state.message)
                    }
                }
            }
        }
        
        viewModel.loadUser("123")
    }
}
```

### 场景二：Room 数据库 + 协程

```kotlin
// 1. 定义 DAO
@Dao
interface UserDao {
    @Query("SELECT * FROM users WHERE id = :id")
    suspend fun getUser(id: String): User?
    
    @Query("SELECT * FROM users")
    fun getAllUsers(): Flow<List<User>>  // 返回 Flow，数据变化时自动更新
    
    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun insertUser(user: User)
}

// 2. Repository
class UserRepository(private val userDao: UserDao) {
    
    // 单次查询
    suspend fun getUser(id: String): User? = userDao.getUser(id)
    
    // 观察数据变化
    fun observeUsers(): Flow<List<User>> = userDao.getAllUsers()
    
    suspend fun saveUser(user: User) = userDao.insertUser(user)
}

// 3. ViewModel
class UserListViewModel(private val repo: UserRepository) : ViewModel() {
    
    // StateFlow：从 Flow 转换，配合 stateIn 设置初始值
    val users: StateFlow<List<User>> = repo.observeUsers()
        .stateIn(
            scope = viewModelScope,
            started = SharingStarted.WhileSubscribed(5000),
            initialValue = emptyList()
        )
}
```

### 场景三：超时控制

suspend fun fetchDataWithTimeout(): Result<Data> {
    return try {
        // 5 秒超时
        withTimeout(5000) {
            val data = api.fetchData()
            Result.success(data)
        }

    }

### 场景四：重试机制

```kotlin
// 通用重试函数
suspend fun <T> retry(
    times: Int = 3,
    initialDelay: Long = 1000,
    factor: Double = 2.0,
    block: suspend () -> T
): T {
    var currentDelay = initialDelay
    repeat(times - 1) { attempt ->
        try {
            return block()
        } catch (e: Exception) {
            Log.w("Retry", "第 ${attempt + 1} 次重试失败: ${e.message}")
        }
        delay(currentDelay)
        currentDelay = (currentDelay * factor).toLong()
    }
    return block()  // 最后一次，如果失败就抛异常
}

// 使用
suspend fun fetchUserWithRetry(): User {
    return retry(times = 3, initialDelay = 1000) {
        api.getUser()
    }
}
```

## 常见问题与陷阱

### 1. 不要使用 GlobalScope

```kotlin
// ❌ 错误：GlobalScope 不跟随任何生命周期
fun badPractice() {
    GlobalScope.launch {
        delay(10000)
        // 10 秒后 Activity 可能已经销毁，继续执行可能崩溃
        updateUI()
    }
}

// ✅ 正确：使用带生命周期的 scope
fun goodPractice() {
    viewModelScope.launch {
        // ViewModel 销毁时自动取消
    }
    // 或
    lifecycleScope.launch {
        // Activity/Fragment 销毁时自动取消
    }
}
```

### 2. suspend 函数不会自动切线程

```kotlin
// ❌ 错误理解：以为 suspend 会自动到后台线程
suspend fun fetchData(): Data {
    // 这里还是在调用者的线程！
    return URL("https://api.example.com/data").readText()  // 可能阻塞主线程！
}

// ✅ 正确：明确指定调度器
suspend fun fetchData(): Data = withContext(Dispatchers.IO) {
    URL("https://api.example.com/data").readText()
}
```

### 3. 异常处理要小心

```kotlin
// ❌ 问题：async 的异常在 await 时才抛出
viewModelScope.launch {
    val deferred = async {
        throw Exception("出错了")  // 这里不会立即崩溃
    }
    
    delay(1000)
    
    deferred.await()  // 这里才会抛出异常！
}

// ✅ 正确处理
viewModelScope.launch {
    try {
        val deferred = async {
            throw Exception("出错了")
        }
        deferred.await()
    } catch (e: Exception) {
        // 处理异常
    }
}
```

### 4. 取消不会立即生效

```kotlin
// 问题：密集计算不会响应取消
suspend fun heavyWork() {
    var count = 0
    while (count < 1_000_000) {
        // 这个循环不会响应取消！
        count++
    }
}

// ✅ 正确：检查取消状态
suspend fun heavyWork() {
    var count = 0
    while (count < 1_000_000) {
        // 定期检查是否被取消
        if (count % 1000 == 0) {
            ensureActive()  // 如果被取消，抛出 CancellationException
        }
        count++
    }
}
```

### 5. 在 Activity/Fragment 中收集 Flow 的正确方式

```kotlin
// ❌ 错误：Activity 在后台时仍在收集，浪费资源
lifecycleScope.launch {
    viewModel.uiState.collect { state ->
        updateUI(state)
    }
}

// ✅ 正确：使用 repeatOnLifecycle，只在前台时收集
lifecycleScope.launch {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.uiState.collect { state ->
            updateUI(state)
        }
    }
}

// 或者使用扩展函数（更简洁）
lifecycleScope.launch {
    viewModel.uiState
        .flowWithLifecycle(lifecycle, Lifecycle.State.STARTED)
        .collect { state ->
            updateUI(state)
        }
}
```

## 面试检验

### 基础概念题

**Q1：协程是什么？和线程有什么区别？**

> **答案**：协程是一种用户态的轻量级并发方案，可以理解为"可以暂停和恢复的函数"。
> 
> 与线程的区别：
> 1. **层次不同**：线程是操作系统调度单位，协程是用户态的执行单元
> 2. **开销不同**：线程创建开销大（约 1MB），协程极小（几十字节对象）
> 3. **数量限制**：线程受系统限制（几千），协程可以有几十万
> 4. **调度方式**：线程是抢占式（OS 调度），协程是协作式（程序员控制挂起点）
> 5. **关系**：协程运行在线程上，一个线程可以运行多个协程

**Q2：suspend 关键字的作用是什么？**

> **答案**：`suspend` 是一个函数修饰符，作用：
> 1. **标记函数可能挂起**：告诉编译器这个函数内部可能会有挂起操作
> 2. **限制调用位置**：suspend 函数只能在协程或其他 suspend 函数中调用
> 3. **触发编译器转换**：编译器会对 suspend 函数进行 CPS 转换，生成状态机代码
> 
> 注意：suspend 本身不会切换线程，只是一个标记。真正的线程切换由 Dispatcher 完成。

**Q3：launch 和 async 有什么区别？**

> **答案**：
> | | launch | async |
> |--|--------|-------|
> | 返回值 | Job（不携带结果） | Deferred<T>（携带结果） |
> | 获取结果 | 无法获取 | await() 获取 |
> | 异常传播 | 立即向上传播 | await() 时传播 |
> | 使用场景 | 不需要返回值的任务 | 需要返回值，或并行任务 |
> 
> 简单说：需要返回值用 async，不需要用 launch。

**Q4：什么是 CoroutineScope？为什么需要它？**

> **答案**：CoroutineScope 是协程作用域，用于管理协程的生命周期。
> 
> 为什么需要：
> 1. **结构化并发**：父协程取消时，子协程自动取消
> 2. **防止泄漏**：作用域取消时，里面所有协程都取消
> 3. **生命周期绑定**：viewModelScope 跟随 ViewModel，lifecycleScope 跟随 Activity
> 
> 不使用作用域（如 GlobalScope）会导致协程无法被管理，可能造成内存泄漏或崩溃。

**Q5：Dispatchers.IO 和 Dispatchers.Default 有什么区别？什么场景用哪个？**

> **答案**：
> - **Dispatchers.IO**：用于 IO 密集型任务（网络、文件、数据库）。线程池可以动态扩展（最多 64 个线程），因为 IO 操作大部分时间在等待，不占用 CPU
> - **Dispatchers.Default**：用于 CPU 密集型任务（排序、解析、计算）。线程数等于 CPU 核心数，避免过多线程切换开销
> 
> 简单判断：**等待多用 IO，计算多用 Default**
