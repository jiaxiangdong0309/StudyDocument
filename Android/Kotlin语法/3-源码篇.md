# Kotlin 语法源码篇（Kotlin Syntax Internals）

## 设计哲学：Kotlin 为什么敢把语法做这么“顺手”？

Kotlin 很多看起来很丝滑的写法，背后其实不是“运行时黑魔法”，而是两条主线：

1. **编译器替你生成样板代码**。
2. **在合适的时候把抽象在编译期展开**。

所以理解 Kotlin 语法，不能只停留在“会写”：

- `data class` 为什么几行代码就有 `equals/hashCode/copy`？
- lambda 到底会不会生成对象？
- `inline` 为什么会在每个调用点展开一份？
- `reified` 为什么必须和 `inline` 绑定？

这些问题，本质上都指向：**编译器到底生成了什么。**

## 一句话先说结论

| 写法 | 大致编译结果 | 成本特征 |
|-----|-------------|---------|
| 普通函数 | 生成一份方法实现 | 多处调用共用同一个方法 |
| 非内联 lambda | 通常生成函数对象/类实例 | 可能有对象分配与间接调用 |
| `inline` 函数 | 在调用点直接展开函数体 | 少一次调用和对象开销，但代码体积可能变大 |
| `reified inline` | 调用点同时展开函数体和真实类型信息 | 解决泛型擦除的一部分问题 |
| `const val` | 编译期常量内联到使用处 | 读取快，但跨模块改值要注意编译同步 |

## 普通函数：通常只生成一份

### 示例

```kotlin
fun sum(a: Int, b: Int): Int {
    return a + b
}
```

### 编译视角

这类普通函数的典型特点是：

- 编译后生成一个方法
- 所有调用点都去调这一个方法

伪代码理解：

```kotlin
// 调用点 1
val x = sum(1, 2)

// 调用点 2
val y = sum(3, 4)
```

底层更接近：

```java
int x = ExampleKt.sum(1, 2);
int y = ExampleKt.sum(3, 4);
```

### 这类写法的优缺点

优点：

- 代码体积稳定
- 复用性好
- 适合逻辑明确、无需特殊编译期优化的函数

缺点：

- 需要真实的方法调用
- 某些高频小函数在极致场景下会有一点调用成本

## Lambda：到底会不会生成额外对象？

## 先说结论

大多数情况下，**非内联 lambda 会被编译成函数对象**。

### 示例

```kotlin
fun doAction(action: () -> Unit) {
    action()
}

doAction {
    println("hello")
}
```

### 伪代码理解

编译器大致可能生成类似结构：

```kotlin
class ExampleKt$main$1 : Function0<Unit> {
    override fun invoke() {
        println("hello")
    }
}

doAction(ExampleKt$main$1.INSTANCE)
```

### 为什么要生成对象？

因为 lambda 不是“凭空的一段代码”，它需要被当成值传来传去：

- 赋给变量
- 当参数传递
- 甚至闭包捕获外部变量

既然它要像对象一样被传递，编译器就要给它找一个“实体载体”。

## 捕获变量的 lambda，成本通常更高

```kotlin
fun report(name: String) {
    doAction {
        println(name)
    }
}
```

这里 lambda 用到了外部变量 `name`，这叫**捕获（capture）**。

编译器通常需要：

1. 生成一个 lambda 对象
2. 把 `name` 存成这个对象里的字段

伪代码理解：

```kotlin
class ReportLambda(private val name: String) : Function0<Unit> {
    override fun invoke() {
        println(name)
    }
}
```

### 设计亮点

这就是闭包的本质：

> 不只是“记住一段逻辑”，还要“顺手把当时环境也打包带上”。

## `inline`：为什么会在每个调用点展开一份代码？

这正是你提到的那个重点。

## 示例

```kotlin
inline fun measure(block: () -> Unit) {
    val start = System.currentTimeMillis()
    block()
    println(System.currentTimeMillis() - start)
}

measure {
    println("task A")
}

measure {
    println("task B")
}
```

### 非 `inline` 的思路

如果它不是 `inline`，编译器更可能做的是：

1. 生成一个 `measure()` 方法
2. 为每个 lambda 生成对象
3. 调用 `measure(lambda)`

### `inline` 的思路

加了 `inline` 后，编译器更倾向于把函数体直接塞进调用点，变成近似：

```kotlin
val start1 = System.currentTimeMillis()
println("task A")
println(System.currentTimeMillis() - start1)

val start2 = System.currentTimeMillis()
println("task B")
println(System.currentTimeMillis() - start2)
```

### 为什么 Kotlin 要支持这种能力？

因为高阶函数很强大，但如果每次都：

- 额外生成 lambda 对象
- 额外走一层 `invoke()`

那很多本该“很轻”的抽象，就可能在高频调用里产生明显成本。

`inline` 的设计哲学就是：

> 既想要高阶函数的表达力，又不想总为抽象付运行时成本。

## 但 `inline` 不是白送的

优点：

1. 少一次函数调用层级。
2. 很多场景下避免 lambda 对象分配。
3. 支持非局部返回和 `reified`。

代价：

1. **代码膨胀**，调用点越多，展开越多。
2. 函数体太大时，反而可能得不偿失。
3. 会增加字节码体积，影响方法数和可读性。

### 最优写法建议

适合 `inline` 的函数：

- 小而高频
- 参数里有 lambda
- 明显是工具型控制流程封装

```kotlin
inline fun <T> T.runIf(condition: Boolean, block: T.() -> T): T {
    return if (condition) block() else this
}
```

不适合 `inline` 的函数：

- 函数体很大
- 不是高频路径
- 根本没有 lambda 参数，只是为了“显得高级”

## `noinline`：为什么内联函数里还允许“不内联”的参数？

### 示例

```kotlin
inline fun request(
    url: String,
    noinline onFail: (Throwable) -> Unit,
    onSuccess: (String) -> Unit
) {
    try {
        onSuccess("ok")
    } catch (e: Throwable) {
        onFail(e)
    }
}
```

### 为什么需要 `noinline`？

因为有些 lambda 你不只是想“当场执行”，还想：

- 存起来
- 传给别的普通函数
- 放到字段里

但一旦函数被完全内联，这个 lambda 可能就不再是一个独立对象了，自然没法随手拿去存储。

所以 `noinline` 的意思是：

> 这个参数别展开，保留成普通函数对象。

## `crossinline`：限制的到底是什么？

### 先理解“非局部返回”

```kotlin
inline fun runTask(block: () -> Unit) {
    block()
}

fun test() {
    runTask {
        return // 直接从 test 返回
    }
}
```

因为 `block` 被内联进 `test()`，所以这个 `return` 合法，它不是从 lambda 返回，而是从外层函数返回。

### 为什么有时要禁止它？

如果这个 lambda 不是立即同步执行，而是要在另一个上下文执行，就不能允许它“跳出外层函数”。

于是有了 `crossinline`：

```kotlin
inline fun postTask(crossinline block: () -> Unit) {
    val runnable = Runnable {
        block()
    }
    runnable.run()
}
```

这里 `block` 会被放进另一个对象环境里执行，所以禁止非局部返回更合理。

## `reified`：为什么必须和 `inline` 一起用？

## 先说 Java / JVM 的历史包袱

JVM 泛型有**类型擦除**，也就是说：

```kotlin
fun <T> parse(json: String): T
```

运行时并不知道 `T` 到底是 `User`、`Order` 还是别的类型。

### 普通写法只能显式传类型

```kotlin
fun <T> fromJson(json: String, clazz: Class<T>): T {
    TODO()
}
```

### `reified inline` 的写法

```kotlin
inline fun <reified T> Gson.fromJsonTyped(json: String): T {
    return fromJson(json, T::class.java)
}
```

调用时：

```kotlin
val user: User = gson.fromJsonTyped(json)
```

### 为什么必须 `inline`？

因为只有展开到调用点，编译器才知道此时的 `T` 具体是什么。

比如调用点是：

```kotlin
gson.fromJsonTyped<User>(json)
```

编译器把函数体展开时，就能直接替换成：

```kotlin
gson.fromJson(json, User::class.java)
```

如果不内联，函数体只有一份，运行到里面时 `T` 已经被擦除了，编译器没法神奇地把真实类型再变回来。

## `const val`：为什么读取时像“写死在调用处”？

### 示例

```kotlin
object Api {
    const val HOST = "https://api.example.com"
}
```

使用处：

```kotlin
val url = Api.HOST + "/user"
```

### 编译视角

`const val` 的值可能直接内联到使用处，近似效果像：

```kotlin
val url = "https://api.example.com" + "/user"
```

### 好处

- 读取快
- 真正的编译期常量
- 可用于注解参数等要求常量的场景

### 风险

如果它定义在库模块里，值改了但调用方没重新编译，调用方可能还拿着旧值。

所以：

- 适合稳定常量
- 不适合“可能频繁改”的动态配置

## 扩展函数的本质：看起来像成员，其实更像静态函数

### 示例

```kotlin
fun String.lastChar(): Char = this[length - 1]
```

调用：

```kotlin
val c = "Kotlin".lastChar()
```

### 编译视角

它更接近：

```kotlin
char lastChar(String receiver) {
    return receiver.charAt(receiver.length() - 1);
}
```

### 这解释了两个现象

1. 扩展函数不能访问接收者的私有成员。
2. 扩展函数不是动态分发。

这也是为什么说它更像“语法糖 + 更好的组织方式”，而不是运行时真的给类打补丁。

## 最该掌握的性能权衡

## 1. 普通函数 vs `inline`

| 维度 | 普通函数 | `inline` |
|-----|---------|---------|
| 代码生成 | 一份方法 | 多个调用点展开 |
| 调用开销 | 有 | 更少 |
| 代码体积 | 更稳定 | 可能变大 |
| 适用场景 | 通用逻辑 | 小而高频的高阶函数 |

## 2. 非捕获 lambda vs 捕获 lambda

| 维度 | 非捕获 | 捕获外部变量 |
|-----|-------|-------------|
| 额外状态 | 少 | 多 |
| 对象生成压力 | 可能较低 | 通常更高 |
| 可读性 | 简单 | 要注意闭包带来的上下文依赖 |

## 3. `const val` vs 普通 `val`

| 维度 | `const val` | 普通 `val` |
|-----|-------------|-----------|
| 求值时机 | 编译期 | 运行期 |
| 能否内联到调用处 | 可以 | 不行 |
| 适合场景 | 真正常量 | 运行期计算或对象属性 |

## 面试题

### 1. 为什么 `inline` 会在每个调用点展开一份代码？

**结论**：因为它的目标就是用编译期展开换运行时成本。

**原理**：编译器把函数体和可内联 lambda 直接复制到调用位置，这样可以少掉函数调用和函数对象开销，但会导致字节码变大。

**例子**：两个地方调用 `inline fun measure {}`，底层更接近生成两段展开后的代码，而不是只调用一个公共方法。

### 2. 普通函数和 `inline` 函数怎么选？

**结论**：默认普通函数，只有在“小而高频的高阶函数”场景下再考虑 `inline`。

**原理**：普通函数只生成一份实现，体积稳定；`inline` 用空间换时间，不是越多越好。

**例子**：`apply/let/use` 这类小工具函数适合内联，大段业务逻辑一般不适合。

### 3. `reified` 为什么必须配合 `inline`？

**结论**：因为只有内联到调用点，编译器才知道真实泛型类型。

**原理**：JVM 泛型会擦除，普通泛型函数运行时拿不到 `T` 的具体类型；内联展开时，编译器可以把 `T` 替换成真实类型字面量。

**例子**：`fromJsonTyped<User>()` 展开后可以直接变成 `User::class.java`。

### 4. 扩展函数为什么说本质上是静态分发？

**结论**：因为编译后更像一个普通静态函数，接收者只是第一个参数。

**原理**：它不会真的写进类定义里，也不能参与成员函数那种动态分派。

**例子**：父类引用指向子类对象时，调用哪个扩展函数，取决于引用静态类型，而不是运行时对象类型。

### 5. 哪些写法会“每个调用处一份”，哪些通常“只生成一份”？

**结论**：`inline`、`reified inline`、`const val` 更偏向调用处展开；普通函数、普通 `val`、大多数非内联逻辑通常是集中生成一份实现。

**原理**：前者本质是编译期替换或展开，后者本质是正常方法/字段访问。

**例子**：`inline fun lock {}` 会被展开，`fun lock()` 通常就是一个普通方法被多处复用。
