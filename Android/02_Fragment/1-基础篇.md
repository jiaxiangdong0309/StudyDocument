# Fragment 基础篇

## 技术演进：为什么需要 Fragment？

### Android 3.0 之前的痛点

在 Fragment 出现之前（Android 3.0，2011年），开发者面临这些问题：

```
┌────────────────────────────────────────────────────────────┐
│              没有 Fragment 时的痛点                         │
├────────────────────────────────────────────────────────────┤
│                                                            │
│  痛点1：平板适配困难                                        │
│  ┌──────────┐     ┌──────────────────────────────┐         │
│  │  手机    │     │           平板               │         │
│  │ ┌──────┐ │     │  ┌──────┐      ┌──────────┐  │         │
│  │ │列表页│ │     │  │列表页│      │  详情页   │  │         │
│  │ └──────┘ │     │  └──────┘      └──────────┘  │         │
│  └──────────┘     └──────────────────────────────┘         │
│  一个Activity      同一个页面要显示两个Activity的内容？      │
│                                                            │
│  痛点2：界面复用困难                                        │
│  同样的登录表单，在 Activity A 和 Activity B 都要用         │
│  → 只能复制粘贴代码，或者抽取自定义 View（但没有生命周期）    │
│                                                            │
│  痛点3：Activity 太重                                       │
│  每个页面都是一个 Activity，启动开销大、切换动画难控制       │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

### Fragment 的设计目标

Fragment 的诞生就是为了解决这些问题：

| 设计目标 | 实现方式 |
|---------|---------|
| 平板适配 | 同一套 Fragment，手机上单独显示，平板上并排显示 |
| 界面复用 | Fragment 有独立生命周期，可以在多个 Activity 中使用 |
| 轻量级页面 | Fragment 比 Activity 轻量，切换更流畅 |
| 模块化 | 把 UI 拆成独立模块，便于维护和测试 |

### 一句话理解 Fragment

> Fragment 就像乐高积木，每块积木有自己的形状和功能，你可以把它们组合成不同的作品。Activity 是底板，Fragment 是积木块。

## Fragment 生命周期

### 每个回调该做什么？

| 回调 | 调用时机 | 你该做什么 | 注意事项 |
|-----|---------|-----------|---------|
| `onAttach` | 与 Activity 关联 | 获取 Activity 引用、接口回调 | 此时 Activity 的 onCreate 可能还没执行完 |
| `onCreate` | Fragment 创建 | 初始化非 View 相关的数据 | View 还不存在，别操作 View |
| `onCreateView` | 创建 View | inflate 布局并返回 | 只创建 View，别做初始化 |
| `onViewCreated` | View 创建完成 | 初始化 View、设置监听器 | **推荐在这里操作 View** |
| `onStart` | 变为可见 | 开始动画、注册监听 | - |
| `onResume` | 可交互 | 恢复暂停的操作 | - |
| `onPause` | 失去焦点 | 暂停动画、保存临时数据 | 要快，别做耗时操作 |
| `onStop` | 不可见 | 释放资源 | - |
| `onDestroyView` | View 销毁 | **清理 View 引用**，避免内存泄漏 | Fragment 可能还活着，View 却销毁了 |
| `onDestroy` | Fragment 销毁 | 最后的清理 | - |
| `onDetach` | 与 Activity 解除关联 | 清理对 Activity 的引用 | - |

### 代码示例：生命周期监控

```kotlin
class LifecycleFragment : Fragment() {
    
    companion object {
        private const val TAG = "FragmentLifecycle"
        
        // 推荐的创建方式：使用 newInstance 模式
        fun newInstance(param: String): LifecycleFragment {
            return LifecycleFragment().apply {
                arguments = Bundle().apply {
                    putString("param", param)
                }
            }
        }
    }
    
    // 用于演示的参数
    private var param: String? = null
    
    // View Binding（推荐）
    private var _binding: FragmentLifecycleBinding? = null
    private val binding get() = _binding!!  // 只在 View 存在时使用
    
    override fun onAttach(context: Context) {
        super.onAttach(context)
        Log.d(TAG, "onAttach: 与 Activity 建立关联")
        // 可以在这里获取 Activity 引用或接口
    }
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        Log.d(TAG, "onCreate: Fragment 创建")
        
        // 在这里获取参数，初始化非 View 相关的数据
        param = arguments?.getString("param")
    }
    
    override fun onCreateView(
        inflater: LayoutInflater,
        container: ViewGroup?,
        savedInstanceState: Bundle?
    ): View {
        Log.d(TAG, "onCreateView: 创建 View")
        
        // 创建并返回 View，不要在这里做初始化
        _binding = FragmentLifecycleBinding.inflate(inflater, container, false)
        return binding.root
    }
    
    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        Log.d(TAG, "onViewCreated: View 创建完成，可以初始化 UI 了")
        
        // ★ 推荐在这里初始化 View
        binding.textView.text = param
        binding.button.setOnClickListener {
            // 处理点击
        }
    }
    
    override fun onStart() {
        super.onStart()
        Log.d(TAG, "onStart: 可见")
    }
    
    override fun onResume() {
        super.onResume()
        Log.d(TAG, "onResume: 可交互")
    }
    
    override fun onPause() {
        super.onPause()
        Log.d(TAG, "onPause: 失去焦点")
    }
    
    override fun onStop() {
        super.onStop()
        Log.d(TAG, "onStop: 不可见")
    }
    
    override fun onDestroyView() {
        super.onDestroyView()
        Log.d(TAG, "onDestroyView: View 销毁")
        
        // ★ 重要：清理 View Binding 引用，避免内存泄漏
        _binding = null
    }
    
    override fun onDestroy() {
        super.onDestroy()
        Log.d(TAG, "onDestroy: Fragment 销毁")
    }
    
    override fun onDetach() {
        super.onDetach()
        Log.d(TAG, "onDetach: 与 Activity 解除关联")
    }
}
```

### 关键点：View 生命周期 vs Fragment 生命周期

这是很多 Bug 的根源：**Fragment 的生命周期和它的 View 生命周期是分开的！**

```
┌────────────────────────────────────────────────────────────┐
│              Fragment vs View 生命周期                      │
├────────────────────────────────────────────────────────────┤
│                                                            │
│   场景：ViewPager 中的 Fragment 被划走又划回来              │
│                                                            │
│   Fragment 生命周期：                                       │
│   onCreate ──────────────────────────────────► onDestroy   │
│            （Fragment 对象一直存在）                         │
│                                                            │
│   View 生命周期：                                           │
│   onCreateView ─► onDestroyView ─► onCreateView ─► ...     │
│                  （View 可能被销毁重建多次）                 │
│                                                            │
│   ★ 结论：                                                  │
│   1. 不要在 onCreate 中访问 View（View 还不存在）           │
│   2. 在 onDestroyView 中清理 View 引用（避免泄漏）          │
│   3. 使用 viewLifecycleOwner 而不是 this（观察 LiveData）   │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

```kotlin
// ❌ 错误：使用 Fragment 的生命周期观察 LiveData
viewModel.data.observe(this) { data ->
    binding.textView.text = data  // View 可能已经销毁！
}

// ✅ 正确：使用 View 的生命周期观察 LiveData
viewModel.data.observe(viewLifecycleOwner) { data ->
    binding.textView.text = data  // 安全，View 销毁后自动取消观察
}
```

## Fragment 事务

### 什么是 Fragment 事务？

Fragment 的添加、移除、替换等操作都要通过事务（Transaction）完成，就像数据库事务一样，可以包含多个操作，要么全部成功，要么全部失败。

```kotlin
// Fragment 事务的基本用法
supportFragmentManager.beginTransaction()
    .add(R.id.container, MyFragment())      // 添加
    .replace(R.id.container, OtherFragment()) // 替换
    .remove(fragment)                        // 移除
    .hide(fragment)                          // 隐藏
    .show(fragment)                          // 显示
    .addToBackStack("tag")                   // 加入返回栈
    .commit()                                // 提交
```

### add vs replace vs hide/show

这是高频面试题，一定要搞清楚区别：

| 操作 | 效果 | 生命周期 | 适用场景 |
|-----|------|---------|---------|
| `add` | 添加 Fragment 到容器 | 执行 onAttach → onResume | 在容器中添加新 Fragment |
| `replace` | 移除容器中所有 Fragment，再添加新的 | 旧的 onPause → onDestroyView（或 onDestroy），新的 onAttach → onResume | 切换页面，不需要保留旧页面 |
| `hide` | 隐藏 Fragment（View.GONE） | **不触发任何生命周期** | 切换 Tab，需要保留页面状态 |
| `show` | 显示 Fragment | **不触发任何生命周期** | 配合 hide 使用 |

```kotlin
class MainActivity : AppCompatActivity() {
    
    private val fragmentA = FragmentA()
    private val fragmentB = FragmentB()
    private var currentFragment: Fragment = fragmentA
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)
        
        // 方式1：使用 replace（切换时会销毁旧 Fragment 的 View）
        fun switchWithReplace(fragment: Fragment) {
            supportFragmentManager.beginTransaction()
                .replace(R.id.container, fragment)
                .commit()
        }
        
        // 方式2：使用 hide/show（切换时保留所有 Fragment 的 View）
        // 首次添加所有 Fragment
        if (savedInstanceState == null) {
            supportFragmentManager.beginTransaction()
                .add(R.id.container, fragmentA, "A")
                .add(R.id.container, fragmentB, "B")
                .hide(fragmentB)  // 默认隐藏 B
                .commit()
        }
        
        fun switchWithHideShow(targetFragment: Fragment) {
            supportFragmentManager.beginTransaction()
                .hide(currentFragment)
                .show(targetFragment)
                .commit()
            currentFragment = targetFragment
        }
    }
}
```

### commit vs commitAllowingStateLoss vs commitNow

| 方法 | 执行时机 | 状态保存 | 适用场景 |
|-----|---------|---------|---------|
| `commit()` | 异步（post 到主线程队列） | 如果在 onSaveInstanceState 后调用会崩溃 | 常规使用 |
| `commitAllowingStateLoss()` | 异步 | 可能丢失状态，不会崩溃 | 不介意状态丢失时 |
| `commitNow()` | 同步（立即执行） | 会崩溃 | 需要立即生效，不能加 BackStack |
| `commitNowAllowingStateLoss()` | 同步 | 可能丢失状态 | 需要立即生效且不介意状态丢失 |

```kotlin
// ❌ 错误：在异步回调中直接 commit 可能崩溃
apiService.getData(object : Callback {
    override fun onSuccess(data: Data) {
        // 此时 Activity 可能已经 onSaveInstanceState
        supportFragmentManager.beginTransaction()
            .replace(R.id.container, DetailFragment())
            .commit()  // 💥 IllegalStateException
    }
})

// ✅ 方案1：使用 commitAllowingStateLoss（可能丢失状态）
supportFragmentManager.beginTransaction()
    .replace(R.id.container, DetailFragment())
    .commitAllowingStateLoss()

// ✅ 方案2：检查状态（推荐）
if (!supportFragmentManager.isStateSaved) {
    supportFragmentManager.beginTransaction()
        .replace(R.id.container, DetailFragment())
        .commit()
}

// ✅ 方案3：使用 Lifecycle（最推荐）
lifecycleScope.launch {
    lifecycle.repeatOnLifecycle(Lifecycle.State.STARTED) {
        // 只在 STARTED 状态后执行，自动处理状态问题
        supportFragmentManager.beginTransaction()
            .replace(R.id.container, DetailFragment())
            .commit()
    }
}
```

### 返回栈（Back Stack）

返回栈决定了用户按返回键时的行为：

```kotlin
// 不加入返回栈：按返回键直接退出 Activity
supportFragmentManager.beginTransaction()
    .replace(R.id.container, DetailFragment())
    .commit()

// 加入返回栈：按返回键回到上一个 Fragment
supportFragmentManager.beginTransaction()
    .replace(R.id.container, DetailFragment())
    .addToBackStack("detail")  // 给这个事务起个名字
    .commit()

// 手动弹出返回栈
supportFragmentManager.popBackStack()  // 弹出栈顶
supportFragmentManager.popBackStack("detail", 0)  // 弹到指定位置
supportFragmentManager.popBackStack("detail", FragmentManager.POP_BACK_STACK_INCLUSIVE)  // 包含指定的也弹出
```

```
┌────────────────────────────────────────────────────────────┐
│                      返回栈示意图                           │
├────────────────────────────────────────────────────────────┤
│                                                            │
│   操作序列：A → B（addToBackStack）→ C（addToBackStack）    │
│                                                            │
│   返回栈状态：                                              │
│   ┌─────┐                                                  │
│   │  C  │  ← 栈顶（当前显示）                               │
│   ├─────┤                                                  │
│   │  B  │                                                  │
│   ├─────┤                                                  │
│   │  A  │  ← 栈底                                          │
│   └─────┘                                                  │
│                                                            │
│   按返回键：C 出栈 → 显示 B                                 │
│   再按返回键：B 出栈 → 显示 A                               │
│   再按返回键：A 是栈底 → 退出 Activity                      │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

## 基本用法

### 静态添加（XML 方式）

```xml
<!-- activity_main.xml -->
<LinearLayout xmlns:android="http://schemas.android.com/apk/res/android"

    android:orientation="vertical">

        android:layout_width="match_parent"

    <androidx.fragment.app.FragmentContainerView

        android:layout_weight="1" />

</LinearLayout>
```

> **注意**：静态添加的 Fragment 不能被动态移除或替换，灵活性差，现在很少使用。

### 动态添加（代码方式，推荐）

```kotlin
class MainActivity : AppCompatActivity() {
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)
        
        // ★ 关键：检查 savedInstanceState，避免配置变更后重复添加
        if (savedInstanceState == null) {
            supportFragmentManager.beginTransaction()
                .add(R.id.fragment_container, HomeFragment.newInstance())
                .commit()
        }
    }
}
```

### Fragment 参数传递

```kotlin
// ★ 推荐：使用 newInstance 模式传递参数
class UserFragment : Fragment() {
    
    companion object {
        private const val ARG_USER_ID = "user_id"
        private const val ARG_USER_NAME = "user_name"
        
        // 工厂方法，参数类型明确，便于使用
        fun newInstance(userId: Long, userName: String): UserFragment {
            return UserFragment().apply {
                arguments = Bundle().apply {
                    putLong(ARG_USER_ID, userId)
                    putString(ARG_USER_NAME, userName)
                }
            }
        }
    }
    
    // 使用 by lazy 延迟获取参数
    private val userId: Long by lazy {
        requireArguments().getLong(ARG_USER_ID)
    }
    
    private val userName: String by lazy {
        requireArguments().getString(ARG_USER_NAME) ?: ""
    }
    
    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        super.onViewCreated(view, savedInstanceState)
        
        // 使用参数
        binding.textUserId.text = "ID: $userId"
        binding.textUserName.text = "Name: $userName"
    }
}

// 使用
val fragment = UserFragment.newInstance(123L, "张三")
supportFragmentManager.beginTransaction()
    .replace(R.id.container, fragment)
    .commit()
```

**为什么要用 newInstance 模式？**

```kotlin
// ❌ 错误：通过构造函数传参
class BadFragment(private val userId: Long) : Fragment() {
    // 配置变更后，系统用无参构造函数重建 Fragment
    // 结果：userId 变成默认值 0，数据丢失！
}

// ✅ 正确：通过 arguments 传参
class GoodFragment : Fragment() {
    companion object {
        fun newInstance(userId: Long) = GoodFragment().apply {
            arguments = Bundle().apply { putLong("userId", userId) }
        }
    }
    // arguments 会被系统自动保存和恢复
}
```

### 获取 Fragment 引用

```kotlin
// 方式1：通过 id 查找（静态添加的 Fragment）
val fragment = supportFragmentManager.findFragmentById(R.id.fragment_header)

// 方式2：通过 tag 查找（动态添加时设置的 tag）
supportFragmentManager.beginTransaction()
    .add(R.id.container, MyFragment(), "my_tag")  // 添加时设置 tag
    .commit()

val myFragment = supportFragmentManager.findFragmentByTag("my_tag")

// 方式3：类型安全的获取（Kotlin 扩展）
inline fun <reified T : Fragment> FragmentManager.findFragment(): T? {
    return fragments.filterIsInstance<T>().firstOrNull()
}

// 使用
val homeFragment = supportFragmentManager.findFragment<HomeFragment>()
```

## 常见问题与陷阱

### 1. getActivity() 返回 null

**问题**：在异步回调中调用 `getActivity()` 返回 null，导致空指针崩溃。

```kotlin
// ❌ 错误：异步回调中直接使用 activity
apiService.getData(object : Callback {
    override fun onSuccess(data: Data) {
        // Fragment 可能已经 detach，activity 为 null
        activity?.runOnUiThread {  // 可能为 null
            updateUI(data)
        }
    }
})

// ✅ 方案1：使用 isAdded 检查
if (isAdded && activity != null) {
    updateUI(data)
}

// ✅ 方案2：使用 viewLifecycleOwner.lifecycleScope（推荐）
viewLifecycleOwner.lifecycleScope.launch {
    val data = apiService.getData()
    // 自动取消，不会有空指针问题
    updateUI(data)
}

// ✅ 方案3：使用 requireActivity()，明确表示需要 Activity
// 如果 Activity 为 null 会抛 IllegalStateException，便于排查问题
requireActivity().runOnUiThread { updateUI(data) }
```

### 2. Fragment 重叠

**问题**：屏幕旋转后，页面上出现多个 Fragment 重叠。

```kotlin
// ❌ 错误：没有检查 savedInstanceState
override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    setContentView(R.layout.activity_main)
    
    // 每次 onCreate 都添加，旋转后就重复添加了
    supportFragmentManager.beginTransaction()
        .add(R.id.container, HomeFragment())
        .commit()
}

// ✅ 正确：检查是否是首次创建
override fun onCreate(savedInstanceState: Bundle?) {
    super.onCreate(savedInstanceState)
    setContentView(R.layout.activity_main)
    
    // 只有首次创建才添加，配置变更时系统会自动恢复
    if (savedInstanceState == null) {
        supportFragmentManager.beginTransaction()
            .add(R.id.container, HomeFragment())
            .commit()
    }
}
```

### 3. View 引用泄漏

**问题**：Fragment 的 View 销毁后，仍持有 View 引用，导致内存泄漏。

```kotlin
// ❌ 错误：没有清理 binding
class LeakyFragment : Fragment() {
    private lateinit var binding: FragmentLeakyBinding
    
    override fun onCreateView(inflater: LayoutInflater, container: ViewGroup?, savedInstanceState: Bundle?): View {
        binding = FragmentLeakyBinding.inflate(inflater, container, false)
        return binding.root
    }
    
    // View 销毁后，binding 仍然持有 View 引用
}

// ✅ 正确：在 onDestroyView 中清理
class SafeFragment : Fragment() {
    private var _binding: FragmentSafeBinding? = null
    private val binding get() = _binding!!
    
    override fun onCreateView(inflater: LayoutInflater, container: ViewGroup?, savedInstanceState: Bundle?): View {
        _binding = FragmentSafeBinding.inflate(inflater, container, false)
        return binding.root
    }
    
    override fun onDestroyView() {
        super.onDestroyView()
        _binding = null  // ★ 清理引用
    }
}
```

### 4. 嵌套 Fragment 的 childFragmentManager

**问题**：在 Fragment 中添加子 Fragment 时用错了 FragmentManager。

```kotlin
// ❌ 错误：使用 parentFragmentManager 添加子 Fragment
parentFragmentManager.beginTransaction()
    .add(R.id.child_container, ChildFragment())
    .commit()
// 结果：ChildFragment 被添加到 Activity 的 FragmentManager

// ✅ 正确：使用 childFragmentManager
childFragmentManager.beginTransaction()
    .add(R.id.child_container, ChildFragment())
    .commit()
```

**记忆技巧**：

| FragmentManager | 获取方式 | 用途 |
|----------------|---------|------|
| Activity 的 | `supportFragmentManager` | 管理 Activity 中的 Fragment |
| 父 Fragment 的 | `parentFragmentManager` | 与父 Fragment 或 Activity 通信 |
| 当前 Fragment 的 | `childFragmentManager` | 管理当前 Fragment 中的子 Fragment |

## 面试检验

### 基础题

**Q1: Fragment 的生命周期有哪些回调？哪些是 Fragment 特有的？**

> **答案**：
> Fragment 的生命周期回调：onAttach → onCreate → onCreateView → onViewCreated → onStart → onResume → onPause → onStop → onDestroyView → onDestroy → onDetach
> 
> Fragment 特有的回调：
> - `onAttach`/`onDetach`：与 Activity 关联/解除关联
> - `onCreateView`/`onDestroyView`：View 创建/销毁
> - `onViewCreated`：View 创建完成（推荐在这里初始化 View）

**Q2: add、replace、hide/show 的区别是什么？**

> **答案**：
> - `add`：添加 Fragment，不影响已有的 Fragment
> - `replace`：移除容器中所有 Fragment，再添加新的（会触发旧 Fragment 的 onDestroyView）
> - `hide/show`：只是设置 View 的可见性，**不触发任何生命周期回调**
> 
> 使用场景：
> - 页面切换不需要保留状态：用 replace
> - Tab 切换需要保留状态：用 hide/show
> - 动态添加新内容：用 add

**Q3: commit 和 commitAllowingStateLoss 的区别是什么？什么时候用哪个？**

> **答案**：
> - `commit()`：如果在 onSaveInstanceState 之后调用，会抛出 IllegalStateException
> - `commitAllowingStateLoss()`：不会崩溃，但可能丢失状态（配置变更后 Fragment 状态可能不正确）
> 
> 使用建议：
> - 正常情况下用 `commit()`，它能帮你发现生命周期问题
> - 在异步回调中，如果不介意状态丢失，可以用 `commitAllowingStateLoss()`
> - 更好的做法是用 Lifecycle 感知的协程，避免这个问题

**Q4: 为什么 Fragment 要用 newInstance 模式传参，而不是构造函数？**

> **答案**：
> 因为系统在重建 Fragment 时（如配置变更）会调用**无参构造函数**，通过构造函数传入的参数会丢失。而 `arguments` 是一个 Bundle，会被系统自动保存和恢复。

**Q5: ViewLifecycleOwner 是什么？为什么要用它？**

> **答案**：
> `viewLifecycleOwner` 是 Fragment 中 View 的生命周期所有者，它的生命周期在 onCreateView 和 onDestroyView 之间。
> 
> 为什么要用：Fragment 的生命周期和 View 的生命周期是分开的。在 ViewPager 等场景下，Fragment 可能活着，但 View 被销毁了。如果用 Fragment 的生命周期观察 LiveData，View 销毁后数据更新会导致崩溃。用 `viewLifecycleOwner` 则会自动取消观察。
